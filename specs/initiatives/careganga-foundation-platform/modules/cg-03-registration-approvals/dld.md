## Data ownership and independent initial workflow

CG-03 owns its approval process configuration, cases, decisions, and immutable history. It never owns branch/member/provider/financial source data. The first fully functional owner integration targets verified existing CG-01 accounts/roles: CG-03 creates the application and owns its proposed protected change, approval steps and decision. Only after final approval does CG-03 call CG-01's guarded idempotent grant application; CG-01 did not need a prior pending-only request. CG-19 evidence verification is added when real protected file storage is available; a no-attachment initial access case must work without CG-19.

## First complete case — source revision, process and grant owner

**Real existing sources, no CG-01 pending request:** CG-03 introduces the protected-access-change *proposal* itself. It validates the actual existing CG-01 account and eligible target role using CG-01's scoped owner facade, freezes a CG-03 proposal revision 1 and canonical digest of `{realm,account,operation,targetRole,expectedCG01AccountAccessVersion,expectedCG01RoleVersion,submitter}`. Store **both observed CG-01 account/access and role revisions** in the immutable case alongside this CG-03 proposal revision and digest. This is **not** a fabricated CG-01 source submission row or a dummy CG-02 branch. A returned proposal is superseded and corrected into a new CG-03 case/proposal revision; older decisions can never be replayed against it. At final application CG-01 compares frozen expected versions to its **actual current authoritative state**; a drifted account/role fails with `OWNER_BLOCKED_SOURCE_CHANGED` and a new proposal/review, never silently authorizes a changed privilege.

**Complete process without unimplemented setup:** CG-03 ships one legitimate **protected CG-01 access-change approval-process version** during its own bootstrap migration/configuration, with final CG-01 protected Super Admin review requiring fresh MFA and a distinct proposer; optional preceding reviewer steps are chosen from genuinely implemented CG-01 permissions. The permitted process editor/versioning belongs to CG-03. Process revisions are immutable once used, and new process versions do not rewrite an existing application's pinned route. **Concrete initial approval-needed change:** assign an existing eligible non-root CG-01 account to an existing custom (not protected/root) role containing `roles.manage`, which CG-01's stable security capability policy classifies as **sensitive-but-assignable only through CG-03 approved finalization**. Ordinary non-sensitive custom-role assignment is independently supported by CG-01's direct US-003 flow; the built-in protected Super Admin role and non-assignable security-policy.manage capability are **never** granted through CG-03. With only the actual CG-01 Foundation-root role catalog, an eligible proposer distinct from the current Super Admin reviewer, this complete protected-role-change flow works without CG-02/19 or third-party services. A one-operator environment that cannot satisfy distinct-actor security shows an explicit unavailable/reviewer-required state, **not** a bypassed approval.

**Source owner effect extension (part of delivery of CG-03, not CG-01 bootstrap):** The introducing CG-03 implementation must add/review a **CG-01-owned protected** `applyApprovedAccessChange` typed facade within the existing modular monolith. CG-03 does not import CG-01 repositories or directly update accounts/role grants. Input has trusted verified current CG-03 final decision identity, frozen proposal and source digest/revisions, idempotency/effect key and original proposer/reviewer proofs. CG-01 recomputes actor/final reviewer/current protected authority and fresh MFA policy, validates current account/role/realm/version/last-root constraints, then atomically applies **one** valid grant and its original CG-01 security audit/version bump under its existing transaction. It rejects a forged, expired, returned or replayed mismatched decision, changed CG-01 target or protected role escalation. A copied approval flag or client-provided `FINAL_APPROVED` cannot invoke this command. The real combined CG-03/CG-01 path is demonstrated by CG-03 US-003 QA, not a CG-01 US-001 dependency.

**Review-read boundary:** Only real CG-01 root scope and actual CG-03 case owner keys are available initially. A case list exposes source-owned safe account/role labels, approval reference/status and limited redacted actor history after per-row authorization. Protected remarks, submitted change payloads and bulk exports have separate permissions; draft/returned/rejected cases are not public. Client deep links and private case/capability discovery never reveal hidden cases.

## Canonical approval model and typed transitions

- approval_process(id, process_type, owner_kind, scope_policy, version, enabled): **UNIQUE(process_type,owner_kind,scope_policy,version)** and one active effective version per real process/scope, with a seeded eligible CG-01 protected access-change process. approval_step(process_id, ordinal, reviewer_capability, area_scope_policy) has **UNIQUE(process_id,ordinal)** and validates actual current CG-01 reviewer permissions; initial scope is FOUNDATION_ROOT only. Once used, process and step revisions are immutable; updating configuration creates a new version. The case pins the exact process+steps version and cannot inherit later grants or routes.
- application_case(id, owner_kind, owner_ref, source_submission_key, source_submission_revision, source_payload_digest, source_account_access_version, source_role_version, previous_case_ref, process_id, process_version, status, current_step, revision, submitted_at, frozen_proposed_change): **UNIQUE(owner_kind,owner_ref,source_submission_key)** and a real CG-03 proposal submission revision/canonical digest for the initial protected CG-01 intent, pinned to the actual CG-01 account/access and target role versions. No CG-01 pending source table is invented. Later CG-02/04/10/14 cases use their real owner-provided immutable revision/digest only after those owners exist. Existing same-key/same-digest returns original; mismatched key/digest conflicts; returned correction gets a new case with explicit previous_case_ref, previous case terminal and all prior reviewer history preserved. Case ref never becomes a fake owner external ID.
- case_decision(id, case_id, step_ordinal, actor_account_ref, action, remarks, expected_revision, idempotency_key, at): append-only, `UNIQUE(case_id,idempotency_key)`, step and case revision guards. Decision-time CG-01 session/role/capability/actual scope verification is mandatory, including current reviewer role, protected-final-authority requirements and prevention of actor self-approval escalation. Record RETURN/REJECT/APPROVE/FORWARD and any bulk decisions as *independently validated* case decisions, never grant blanket bulk authorization from one selected row. Concurrent reviewers at the same step yield one accepted transition and a safe CONFLICT for stale attempts.
- **No initial document_verification table or CG-19 reference:** The CG-01 protected change is a no-file process and works with no CG-19 database, object store, optional file field or upload/verify UI. CG-19 later introduces real protected file bytes/reference and tests the approved case's permission-scoped file-read and verified-evidence integration; only when a real later source requires per-document approval does the introducing owner add a reviewed minimal CG-03-owned verification decision migration. No raw file bytes/tokens in CG-03 tables, logs or unauthorized previews, and no speculative FK/table in the initial CG-03 migration.
- application_finalization(id, case_id, final_decision_ref, source_submission_revision, owner_outcome_key, state, attempt_count, next_retry_at, last_result_class): **UNIQUE(case_id), UNIQUE(final_decision_ref), UNIQUE(owner_outcome_key)** for a single immutable accepted final decision/effect. The finalization binds exact CG-03 proposal digest/source revision and observed CG-01 access/role revisions. After CG-03 final approval commit it remains PENDING_OWNER; a bounded idempotent coordinator invokes the CG-01-owned source finalizer **outside SQL row locks**, and uses original outcome key to requery on network uncertainty, never repeat destructive mutations under a fresh key. Completed only after CG-01 confirms actual grant and its own access audit; terminal stale-revision denial is OWNER_BLOCKED, not granted. Due-only bounded retry with claimed rows, finite attempts and restart recovery; zero eligible work means no fast per-user/per-case scanning.

States: DRAFT → SUBMITTED (immutable source revision+digest) → IN_REVIEW → RETURNED / REJECTED / FINAL_APPROVED. A returned application is corrected through **a new submitted revision/case** linked to its predecessor (not reopening the old signed proposal); only the current eligible case can finalize a source. CASE_FINAL_APPROVED → PENDING_OWNER → OWNER_COMPLETED / OWNER_FAILED_RETRYABLE / OWNER_BLOCKED is a separate effect axis. One short DB transaction locks the case, checks expected revision/step/process version and reviewer authorization, appends the decision and moves the case once. CG-01 accepts the approved decision through a trusted typed command with idempotency, not via a client-supplied approval flag. Configuration revisions never rewrite submitted case reviewer routes; the initial no-attachment access process remains runnable without CG-19.

API contracts: POST approval/process-version (super-admin protected); POST cases (real source owner adapter + source key); GET scoped cases/steps/options; POST case/{case}/decision (action, remark, expected_revision, idempotency_key); GET case/{case}/history; GET source outcome. Provider unavailable, stale actor, repeat decision, missing real source, unauthorized document access and last-root escalation all fail safely without a fake APPROVED+ACTIVE state.

## Typed API and coordination

An authenticated `/api/registration-approvals` owner facade provides protected case creation/decision/history/source-status with small authorized reviewer and owner selectors. **No CG-03 public listing or general publication endpoint**; public self-service tracking is introduced by the actual later owner using a narrow authenticated/tracking-capability contract. Private subject, account, decision reason, file and reviewer data remain restricted. In initial release, only Foundation-root CG-01 capabilities/scopes exist; never require future branch/center/patient records. Each PRD command contract:
- **FR-006** — Member/volunteer/employee/CSR/branch/provider submits: Give application number and tracking; support application-specific documents, verifications, notes, evidence and configurable stepwise routing. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.
- **FR-007** — Authorized reviewer decides: Approve, reject, return for correction or forward; show pending and prior steps, reviewer, remarks and time; prevent action by unrelated or revoked reviewer. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.
- **FR-008** — Final authorized approval occurs: Produce exactly one owner-domain effect (member/employee/provider/branch activation, entitlement or authorized financial outcome), never from a pending stage. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.

Business outcome categories: `SUCCESS/SUBMITTED_PENDING/VALIDATION/DUPLICATE/FORBIDDEN/NOT_FOUND_OR_HIDDEN/CONFLICT/UNAVAILABLE/UNKNOWN_WRITE_STATUS`. External provider failure never becomes fake success. Use a DB transaction for state+audited result, optimistic revisions or narrowly scoped row locks for races and unique source idempotency. Cross-owner effects go through typed facades, not another module's repository. Approved HLD pattern (plain state guard, policy, adapter, facade) only where actual variation justifies it; reject universal DSL, speculative microservice or duplicated ledger. No unbounded idle polling or uncontrolled retries.

## CRITICAL PostgreSQL design, minimal patterns and independent QA gates

- **Actual schema and uniqueness:** `approval_process` immutable versions, `approval_step` unique ordinal+process FK, one active process per real type/scope, `application_case` unique source key and frozen revision/digest with CG-01 current expected versions, `case_decision` unique case/idempotency, and `application_finalization` unique case/final decision/outcome key. Case/decision/step/result references must use **real existing CG-03 or CG-01 owners**. No CG-02/04/10/14/19 FK, table, nullable "future owner" rows or universal polymorphic source registry. Actual path-target scope is server-enforced; CASE actor permissions are not client-declared.
- **Atomic transaction and concurrency:** Choose a minimal **guarded state machine + optimistic case revision/CAS + short row-level lock** for each accepted reviewer step; append one immutable case_decision and CG-03 source-owned redacted audit in the same transaction. A concurrent same-step decision loses safely without second accepted step. Protected process edit is a new immutable version, not in-place rewrite. Final approved case+finalization record is committed once in CG-03; CG-01 applies its grant+access_audit **inside its own** short transaction. CG-01/CG-03 owner facade and external provider calls run **outside** these locks; no speculative distributed transaction or generic Saga engine.
- **Indexes/bounded reads:** initial Foundation-root cases by `(root_ref,status,current_step,submitted_at DESC,id)`, reviewer-eligible queue/source+time with stable cursor; `case_decision(case_id,at,id)`; finalization due partial index `(next_retry_at,id) WHERE state='FAILED_RETRYABLE'`; source-intent uniqueness and owner-outcome uniqueness. Cap result size and export; exclude hidden/foreign source rows before counting KPIs. Review actual EXPLAIN, row/byte counts, p95 and idle egress only after a real database exists; currently NOT_MEASURED.
- **Migrations and restore:** CG-03 adds owned tables to **the one real CG-01 migration history**, additive constraint/index migrations and permission capability registration only for `approvals.*` actions really implemented here. Test disposable forward migrate/backfill (if existing real cases), unique conflicts, safe forward repair and isolated restore with protected case/decision history. Independent qualified **CRITICAL database reviewer** and migration/restore/concurrency runs remain NOT_RUN.
- **Patterns chosen:** plain typed process configuration and existing guarded CG-01 authorization facade, small immutable source snapshot and versioned state machine. Reject copied approval logic per module, Template Method inheritance, generic rule-language interpreter, alternate account/authorization service, microservices, shadow branch/member/finance masters and speculative broker/workers.
- **Operational NFR and QA:** Revalidate current CG-01 actor, MFA, root scope and actual account/role versions at each decisive boundary, protect confidential proposal/reviewer remarks/case export, reject last-root privilege escalation, preserve status PENDING_OWNER on uncertain finalizer reply and zero duplicated effects. No case notification, file upload, fake payment, future owner metrics or provider dependency in the first CG-01-case acceptance. When no pending retryable case exists across many backend instances, no repeated full-user/full-case scans or provider calls; only bounded due-row claim/retry is permitted. Source QA includes Web and native Internal Android, original U11–U13/B29 styling and screen states, 403/conflict/unknown-result paths; no device/render/SQL PASS without independent execution.
