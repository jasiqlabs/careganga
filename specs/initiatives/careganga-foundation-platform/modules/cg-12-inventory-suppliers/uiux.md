**Quick actions exactly sourced from B19:** New Request, New Item, Stock Adjustment, Request Approvals; these become enabled **only** when their actual story and permission are delivered. **Filter/Export**, status/type/priority/date filters, search, category chips, low-stock alert panels and stock/request counts are also B19 source-visible. Add Receive Stock/Issue/Return/Transfer as necessary domain actions **within original Inventory Management / Stock Transactions**, styled with the same shared source components; don't misrepresent them as directly visible specific screenshot buttons. Nothing in B19 proves a barcode scanner, warehouse map, cash voucher, auto-purchase order, automatic email alert or per-tab wizard design: those are NOT implied first-release requirements.

## 3. Exact fields, actions, transitions and feedback

**US-001 Items + stores:** Original style compact table with Item Name, SKU, Category, Base Unit, Stock status, current real Store, Available Qty and Action. Add New Item panel validates name/normalized SKU, category, unit and quantity precision (pieces integer, kg decimal if allowed), low-stock threshold; no initial stock entry via the item form—stock arrives only via actual receipt. Stores use human Foundation or CG-02 ACTIVE branch/location labels, not technical UUID or healthcare center. Suppliers show legal/display name, supplier code, public business category, status, optional restricted contacts/tax fields in permission-only form. An inactive item cannot be received without reactivation, and changing unit after movements requires actual guarded source conversion policy, not raw Edit.

**US-002 Receive Stock:** Use current original shared right drawer or accessible modal pattern, with real eligible Supplier, Location, Item search, received Qty/unit per line, optional CG-19 validated invoice/delivery proof, source date and safe confirmation. Input validation before confirmation, server checks afterward; show Receipt Confirmed only after immutable stock event/balance commit. Scanning pending/owner down/not received are distinct. The finance payment status is not shown as completed merely because physical stock was received. Stock Transactions displays one legitimate RECEIPT event/history with current on-hand/available and human labels.

**US-003 Requests/approvals:** New Request fields requester=current verified account, real permitted store/branch, item repeaters/qty/unit, priority, needed-by date and internal reason. Submission creates actual CG-03 MATERIAL_REQUEST_REVIEW pending case and immutable source revision. Original B19 status tabs/filter/priority/status/date/search and **Request Approvals** quick action open real authorized CG-03 reviewer status; no self-approval, unconfigured process auto-success or fabricated reviewer. On APPROVED, display **Requested / Approved / Held / Fulfilled** columns separately and current on-hand/reserved/available. If approved but short stock, show **Approved — Awaiting Stock**, not Issued. Cancellation/release must visibly return reserved qty to Available.

**US-004 Physical movement:** Within B19 Stock Transactions provide action-specific panes rather than inventing a new root menu: `Issue` with approved request line or actual authorized direct issue and quantity, `Return` requiring original issued event/remaining returnable, `Transfer` two real stores and source unit, `Stock Adjustment` with observed count/actual system stock/difference/reason/proof and source review status. For approved request 10, first issue 6 displays Partially Fulfilled 6/10 and held 4; second issue 4 displays Fully Fulfilled 10/10, not a second request or two balance masters. On transfer show genuine pair event and confirmation, not an in-transit phantom. Negative adjustment denied when would consume reserved stock, with readable available/held figures. Permission-hidden forbidden actions and authoritative 403.

**US-005 Distribution/reports/alerts:** B19 Distribution Log actual issue/date/recipient/item/store/issued/returned and source status with no beneficiary/referral clone. Category/alerts show threshold computed from **available stock** with separate current physical and held quantities; settings permitted per active item/store. Real in-context Search/Filter/Export (status/type/priority/date/item/store/category) caps results, protects supplier contact and recipient reason, escapes CSV formula cells and audits private export. No separately editable “distribution quantity” or manual “balance correction” through report view; numbers derive from stock event and approved holds. No CG-20 analytical dashboard required to finish one scoped B19 report.

## 4. Responsive Admin Web, Android native and shared CareGanga brand

**Admin desktop (source B19):** Match existing shared searchable/selected-blue sidebar, content header, summary metrics cards, narrow toolbar, six tab labels, compact table density and source filters/actions/category/alerts. The audit does not contain pixel coordinates or actual token HEX: developers must use the actual CG-01 bootstrap `packages/design-tokens` implementation, compare original B19 PNG and actual frame/video before visual QA PASS. On narrow Web use responsive tab selector/scroll that preserves **all six** named tabs, readable stacked rows, full-screen accessible input sheets, sticky confirmation where appropriate, not illegible 6-column table. Screen reader, keyboard focus, contrast, status text, reduced-motion and semantic accessible labels are nonnegotiable.

**Native Internal Android:** Use native screen stack and true task-first names Stock Overview, Receive Stock, My Requests, Stock Movements, Low Stock, Distribution History. Put user-selected current permitted Store in visible context and retrieve only secure current CG-12 DTO. Large tap targets, appropriate decimal keyboard, Back/safe area, loading/true empty/shortage/conflict/permission-revoked state, pull-to-refresh and clear queued-offline vs server-confirmed status. No camera permission on app launch or mandatory barcode; scanner optional only if separately approved/source-tested. Unapproved request/receipt proof must never show green successful delivered status. No personal employee or vendor bank info in native caches/logs.

**State language across Web and Android:** Saved Draft, Submitted for Review, Returned, Rejected, Approved Unreserved, Held, Partially Fulfilled, Fulfilled, Cancelled, Receipt Confirmed, Issue Confirmed, Return Accepted, Transfer Confirmed, Adjustment Awaiting Approval/Applied, Threshold Low, Insufficient Available, Permission Denied, Current Source Unavailable, Stale Record — Reload, Network Result Unknown — Check Status. Avoid exposing enum keys or SQL IDs. Success toasts require confirmed original source; 202 means genuine pending and a lost response is never blindly retried under new key.

**Data/privacy UX:** Ordinary selector minimal human item/supplier/location labels, not private contact/bank/tax, file key, raw event UUID or invisible foreign-branch store. Every visible action is actually enforceable by backend current CG-01 action + CG-02 location status + CG-12 source, including export/deep link. Public Web/Android contains no private warehouse routes. Location permissions aren't needed merely to select an approved warehouse by name.
