## CRITICAL financial database invariants and first-source contract

**Scope:** All CG-09 authoritative tables inherit the actual CG-01 Foundation-root realm through a NOT NULL root key or strongly constrained same-root composite parent FK. Every branch/account/period/source reference must belong to that root; current CG-02 branch must be ACTIVE for a new effect, but closing it never deletes immutable past journal lines. Do not add future CG-04/05/07/08/10/11/12/14/15/16/17/18/20 foreign keys, staff/vendor/member/project/patient/center masters or placeholder rows. Never use a generic “tenant/patient/center” permission on first Foundation finance; later owners add privacy-checked scope-specific source integration when delivered.

**Accounts, years, opening:** CG-09 owns financial_year(id,root,start,end,status,version), account_group(id,root,category,parent_id), account(id,root,normalized_code,group_id,normal_side,scope_kind,branch_id,status,version) and cash_bank_account(id,root,account_id,masked_details,status). Ensure UNIQUE(root,normalized_code), non-overlapping financial-year ranges, category/normal-side/branch-presence CHECK, same-root FKs and protected bank information. Opening balances use exactly one real authorized balanced opening journal, not a separately editable “balance.” No CLOSED period posting, backdating or silent account deactivation when referenced by live operations.

**Balanced immutable posting:** Use one authoritative journal(id,root,source_owner,source_ref,posting_kind,immutable_source_event_key,immutable_payload_digest,financial_year_id,status,posted_at,reversal_of_id) with UNIQUE(root,source_owner,source_ref,posting_kind,immutable_source_event_key), and journal_line(id,root,journal_id,account_id,branch_id,debit_minor,credit_minor). Each line has exactly one strictly positive side, >=2 lines per accepted POSTED journal, same root/financial year/currency, sum(debit)=sum(credit)>0. Money arithmetic uses safe integer minor units for an agreed single reporting currency or exact decimal with a documented per-currency policy; no floating point or mixed-currency posting without approved conversion. One short transaction checks real account/period authorization and line validity, then a database-enforced transition guard/deferrable integrity validation prevents unbalanced POSTED visibility and subsequent line mutation. An old source event replay returns the first effect for the same immutable digest, a different digest conflicts, and an adjustment/refund uses a new linked reversal event; NEVER edit an accepted POSTED line.

**Voucher, reimbursement, invoice and payment:** CG-09 owns voucher/voucher_line, expense_claim, invoice/receipt and corresponding immutable linked journal effects. The original approved source revision, number/root/period, payee identity snapshot, real finance claimant CG-01 account, quantity/unit/rate/tax/charges/calculated total, payment mode, approved actor, bank/cash evidence and linked posted effect are preserved. A transaction-specific external payee identity snapshot is *not* a second CG-12 supplier master. Stage statuses distinguish DRAFT, SUBMITTED, APPROVED, POSTED, PAYMENT_REQUESTED, PAID_VERIFIED, SETTLED and REVERSED; a reviewer approval, receipt issue, provider acceptance or payment request alone is never a verified payment. PAID_VERIFIED needs genuine authorized bank/cash proof and creator/verifier policy, not user checkbox; different Web and Android submissions produce one source result. Finance operator with existing eligible CG-01 account may make the first real reimbursement claim without CG-10/04. **CG-10 employee and CG-04 volunteer later supply eligibility and user-facing original form to CG-09's same expense_claim**; they must not persist another claim master/financial payable, even if the UI is inside HR/membership. No second bank register, issued PDF or notification sender.

**Budgets:** CG-09 alone stores budget(root,actual_branch_id_or_foundation,category,period,approved_amount,status,version) and immutable budget_event(kind,source_event_key,amount,finance_source_ref), with same-root FKs, unique scope/category/period and unique original event key. Define the precise source-backed difference among APPROVED ceiling, ALLOCATED earmark, COMMITTED obligation, UTILIZED actual recognized expense, RELEASED authorized movement and AVAILABLE/OVER_BUDGET. Neither approved grant nor a pledge is bank cash. Row-locked current budget/period/source checks prevent two concurrent allocations or the same source posting from overspending; avoid a shadow branch allocation table. A CG-05 project association is introduced only by CG-05 after a real project exists.

**Reconciliation, security and operations:** Bank reconciliation stores actual statement-item reference/snapshot, matched posted journal and variance, with unique verified bank item key and protected account authority; GL/cash/bank/day book/trial balance derive only from POSTED CG-09 lines. No fabricated future payroll/donor/CSR/patient/provider amounts, and CG-20 later consumes permission-filtered source projection only. Indexed root/branch/period first pagination, bounded exports and real EXPLAIN planning; no perpetual per-branch/tenant polling or unnecessary payment-provider calls when idle. Sanitize sensitive money/bank/PII logs; audit final source effects, safe retry/unknown-commit lookup, independent migration/restore/reconciliation tests. Current actual code, SQL, migrations, independent specialist and runtime checks **NOT_RUN**.

## Concrete finance contracts (mandatory DLD refinement)

**Schema:** `accounts(id,code,group,normal_balance,active,scope)` (unique normalized code); `journals(id,source_owner,source_ref,posting_kind,source_event_key,financial_year,status,posted_at,revision)` unique immutable source-effect key `(source_owner, source_ref, posting_kind, source_event_key)`; mutable row revision is **not** an idempotency dimension. Require NOT NULL immutable source_event_key for an accepted POSTED event and a real uniqueness constraint; draft edits can change row revision without minting a new financial event; `journal_lines(journal_id,account_id,debit,credit,branch_or_project_scope)`. Both debit and credit are nonnegative; each line has exactly one nonzero side. **Before POSTED, the same transaction must verify sum(debits)=sum(credits)** and all accounts active/in scope. Rejected/unbalanced journal has no posting and no misleading success.

**Voucher/claim/invoice:** versioned `voucher` + `voucher_lines` with quantity, rate, unit, charges/tax and calculated subtotal/total; `expense_claim` links its single authorized payable/voucher/journal/payment; `invoice` retains approval and issued/paid states separately. A claim cannot create a fresh expense on every workflow stage. A posted journal/receipt is immutable; reverse with a linked correction journal.

**Budget:** `budget` plus allocation/release/utilization events, with separate proposed, committed, approved, allocated, utilized, released and remaining/over-budget projections. Source cash/bank balance is never inferred from pledges. Safe `accounts/options` returns authorized labels for payment-entry pickers without granting full account ledger view (BrickOps selector lesson).

**Transactions/review:** narrow row locks on source-idempotency and account/period where needed, append-only audit, source callback dedupe, branch/project scope in all queries, and approved financial-year controls. QA source trace includes simultaneous source replay, unbalanced debit/credit, approved-but-unpaid voucher, refund/reversal, duplicate payroll/donation posting, protected ledger export, broken selector and reporting reconciliation.

**Pattern decision:** one double-entry posting service + typed owner posting facade + guarded status transitions. Reject per-module mini-ledgers, universal accounting-rule DSL, silently editable posted rows and independent mobile calculation.

## Idempotent money event and version rules

Draft journal revision may change during correction, but posting identity is the immutable external/source financial event. UNIQUE(source_owner,source_ref,posting_kind,source_event_key) must be enforced by DB; a retried callback with a different API revision still returns the first committed posting. Any reversal uses its own linked source_event_key and original_journal_ref, with immutable posted lines; never mutate a posted total. Financial year closure, entry date, approved budget scope, correct debit/credit sign and restricted account selectors are hard DB/domain checks.

**Core tests:** Create balanced debit/credit lines; reject unbalanced, inactive-account and wrong-branch journals before POSTED. The same immutable source financial event (including gateway webhook or payroll payout) can post only once even if callback/query revision changes. Reversal/adjustment is a new explicitly authorized linked event, not editing posted rows. Validate pending approval separately from paid/settled and finance reports reconcile to journal lines.

**Integrations:** Use verified CG-01/CG-02/CG-03 roles, scopes and decisions. Provide safe authorized account/options separately from general-ledger viewing; consumers may integrate only with real journal/posting facade.

## Typed API and coordination

An authenticated `/api/finance-accounting` owner facade exposes business commands, filtered read-only queries, and minimal `options/search` projections for permitted selectors. Public reads require approved publication allowlist. Each PRD command contract:
- **FR-023** — Finance Admin opens accounts: Configure chart of accounts/groups, financial year, branch/project allocation, cash/bank accounts, opening balances and controlled statuses. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.
- **FR-024** — Finance user posts a transaction: Enter authorized balanced journal, payment/expense/contra voucher with item/rate/tax/charges, payee, source, attachments and applicable approval/paid state. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.
- **FR-025** — Employee/volunteer requests reimbursement: Submit claim with purpose/amount/date/project and bill; route approval then single linked payable, voucher, payment and posting, not multiple expenses. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.
- **FR-026** — Authorized user invoices or receipts: Use staged invoice/receipt preparation, items, dates/amounts, attachments, verifier and payment terms; save, approve, print/share securely and link actual money states. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.
- **FR-027** — Finance allocates budget: Create/approve budgets and reveal committed, allocated, utilized, released, available/over-budget amounts with funding/project/branch drill-down. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.
- **FR-028** — Reviewer checks statements: See scoped general ledger, cash/bank/day books, trial balance, vendor/CSR/project views, payables, corrections and reconciled reports with audit. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.

Business outcome categories: `SUCCESS/SUBMITTED_PENDING/VALIDATION/DUPLICATE/FORBIDDEN/NOT_FOUND_OR_HIDDEN/CONFLICT/UNAVAILABLE/UNKNOWN_WRITE_STATUS`. External provider failure never becomes fake success. Use a DB transaction for state+audited result, optimistic revisions or narrowly scoped row locks for races and unique source idempotency. Cross-owner effects go through typed facades, not another module's repository. Approved HLD pattern (plain state guard, policy, adapter, facade) only where actual variation justifies it; reject universal DSL, speculative microservice or duplicated ledger. No unbounded idle polling or uncontrolled retries.
