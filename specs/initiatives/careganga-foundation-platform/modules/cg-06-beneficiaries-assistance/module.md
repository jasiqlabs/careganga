## 1. Exact business ownership and scope

**CG-06 owns** private Foundation beneficiary identity/profile and eligibility (not patient/employee/member identity), optional beneficiary-to-real-project affiliation, beneficiary verification source revision, approved assistance request/case, each immutable actual assistance/delivery/reversal event, private assistance history, beneficiary-safe dashboard and original source aggregate projection. It owns **no** physical inventory balance/transaction (CG-12), Foundation expense/bank/receipt posting (CG-09), project/activity/field visit (CG-05), campaign (CG-07), file bytes (CG-19), approval case/route (CG-03), public editorial publication (CG-18) or generic MIS data warehouse (CG-20).

**Real prerequisites by story:** US-001 requires current CG-01 Foundation-root identity/role + CG-02 geography. A first private beneficiary is registrable, searchable, editable and reviewable **without CG-05 project, CG-12 item, CG-09 paid event or CG-20 MIS**. When the user chooses an eligible project, use actual delivered CG-05 current source and same-root/branch authorization; no forced project or field visit. CG-03 verifies source when Foundation approval policy requires and CG-19 owns any genuine protected proof. US-002 uses real US-001 beneficiary and actor/eligibility; physical deliveries require CG-12 actual approved issue/return; monetary deliveries require CG-09 genuinely posted **and payment/disbursement-confirmed** financial source, not merely a voucher request. Optional CG-05 visit/activity and permitted CG-07 campaign attribution are validated at entry only when those actual sources exist, with no new masters. US-003 reports actual US-001/002 sources **without waiting for CG-20** and lets CG-18 publish only an explicitly approved de-identified impact projection.

**Core end-to-end policy:** Distinguish beneficiary verification status from active/inactive lifecycle and assistance REQUESTED, REVIEW_PENDING, APPROVED, PENDING_STOCK/PENDING_FINANCE, PARTIALLY_DELIVERED, DELIVERED, RETURNED/CORRECTED, CANCELLED/UNAVAILABLE. Beneficiary/aid visibility is purpose/role/branch/project constrained. Repeated actual assistance to a person is allowed, but a retry/duplicate business source cannot create another stock issue, payment or assistance event. Aid is DELIVERED only after a real original owner source confirms receipt/issue; an accepted request, reservation, accounting voucher draft or payment initiation is not delivered.

## 3. Three independently testable vertical stories

### US-001 — Private beneficiary intake, verification, project links and authorized search

Register and edit one limited person profile (name/contact/geography/beneficiary type, optional demographics only when necessary), explicit purpose/consent and, for a minor where policy demands, authorized parent/guardian or representative consent evidence without mandatory national ID; current CG-01/02 scope governs all reads and edits. A person's lack of mobile, a shared family phone, name similarity, or optional project cannot silently merge/erase another person's record. Show duplicate *suggestions only to entitled actors*. Actual CG-03 approval case/revision and authorized verification determine Verified; inactive never means rejected. Link/unlink one or many genuine CG-05 projects with current branch and effective status when chosen; no CG-05 future dependency to first profile. A07/A08 complete Admin Web + Internal Android equivalent with safe errors. **20 manual source QA cases**, all PLANNED.

### US-002 — Legitimate aid request, approval, stock/cash fulfillment, partial delivery and history

For a real eligible beneficiary, enter approved category/quantity/value/unit/date/responsible staff/optional legitimate CG-05 project/visit/activity and optional current CG-07 campaign attribution; record one source request and policy-required CG-03 case. Material fulfillment invokes the original **CG-12** same-root aid-scoped stock issue **and authorized actual recipient handover** (a warehouse-to-worker transfer alone is not beneficiary delivery), plus later return; monetary fulfillment invokes original **CG-09** authorized expense/payment source and verified disbursement, never a duplicate CG-06 ledger. An immutable CG-06 delivery-event links each truly confirmed source once; partials sum to no more than approved; reversal/correction never deletes old proof. A05 context uses safe min-field source link; B19 cannot expose beneficiary PII. Admin Web and Internal Android equivalent source actions. **20 QA**, all PLANNED.

### US-003 — Private beneficiary dashboard, assistance history, source-led impact projection

Implement A07/A08 current real KPI/status/project breakdown, authorized searchable aid/person history, accurate source-backed distribution totals and bounded export/print for permitted staff. Counter/filters and detail links are scoped before aggregation. Reconcile every DELIVERED/RETURNED material event to CG-12 and money effect to CG-09; pending requests must never count as delivered/spent. Dashboard is independently usable before CG-20; current CG-05 A05 viewer sees only an authorized minimal contextual count/link. Provide CG-18 a **separate policy-approved aggregated non-identifying projection** (small-cohort suppression), never raw cases or unrestricted names. Admin Web and Internal Android have equivalent authorized reads, filters and export action. **20 QA**, all PLANNED.
