## Canonical source, authorization and data ownership

CG-21 owns versioned platform settings, integration verification metadata and protected credential references, read-only *central audit presentation* of genuine owner events plus CG-21's own setting/recovery audit, and privileged backup/recovery requests with genuine outcome evidence. CG-01 remains the sole authority for its original login/session/role/access audit facts and privileged MFA/access-policy enforcement. CG-21 must not create a competing security audit master, identity service, or dependence on future CG-03/CG-02/CG-18 records.

## Delivery-isolation contract — no future business owner required

**Predecessor (real, delivered before CG-21):** CG-01 is the only mandatory module API/data source: actual `access_realm` Foundation root, verified accounts/roles, current sessions/MFA/default-deny scope and its protected access-audit read facade. The CG-21 schema may have FKs to these existing CG-01 root/account identities only. CG-21 never creates a new user, session, password policy, Foundation legal profile, approval case, branch, document store, merchant/payment source, communications ledger or CMS publication.

**CG-21's first-release persistence and APIs:** versioned nonsecret `platform_setting` + history, `integration_connection` credential-*reference* and on-demand verification state, `platform_operation_audit` for **CG-21 changes only**, read-only bounded CG-01+CG-21 audit projection, and guarded `recovery_operation` availability/request/status for actual secured backup facilities. All owner writes use CG-01 permission and root scope, with no FK, imports, queries or start-up flags for CG-02/03/04/05/09/10/14/15/17/18/19. The schema/migration must work with zero records from these future owners.

**Non-owned sources:** CG-01-BR11 security policy, CG-02 legal Foundation profile, CG-18 public visibility, CG-19 sending/delivery and CG-09/17 financial effects remain in their respective owner modules. CG-21 never imports or copies their writable schemas; each later owner adds and tests its genuine bounded read-only audit integration when implemented.

**Independently verifiable paths:** with real CG-01 root accounts and CG-21's own persisted data, test setting save/history, CAS race, credential-reference configuration and honest `NOT_CONFIGURED`/failed/verified-if-really-checked state; original CG-01 and new CG-21 audits with scoped export/partial outage; recovery `NOT_AVAILABLE` without configured secured facility and guarded real request with one if present. A test environment does **not** need later CG modules or placeholder third-party responses. An actual provider-connected VERIFIED check and successful recovery drill are **conditional separately evidenced integration/operations QA**, not an invented source-review PASS. Missing provider credentials must not prevent CG-21 startup or its independent settings/audit feature.

## First usable CG-21 setting — fixed initial allow-list, not a generic configuration framework

The first supported independently testable operational setting is **`audit.default_page_size`** (integer; safe default **25**; permitted range **10–100**). Its value is read, edited and revision-audited in CG-21 US-001, and the **same effective value actually controls CG-21's own bounded central audit list in US-002**; all server queries independently cap maximum page size at 100 even when a malicious client sends a larger limit. Before any configured row exists, GET returns effective default 25/version 0; the first accepted expected-version write creates one real row, revision 1 and CG-21 audit event atomically. An unknown key (including `auth.*`, `cms.*`, `messages.*`, `payments.*` or another owner policy) is rejected rather than stored for “future use.”

Do **not** add speculative general settings, recovery policies, system-wide switchboards or per-module key namespaces. Any additional CG-21-owned operational setting requires a separately reviewed actual source requirement and corresponding typed validation, visible effect and independent QA. Provider credentials are configured via `integration_connection`, **not** platform_setting; CG-01 security policy is configured through its own service. This seed key makes CG-21's initial setting-edit story verifiable without any CG-02–20 records or a connected third-party provider.

## Concrete security settings, audit and recovery contracts

platform_setting(id,foundation_root_realm_ref,key,value_class,typed_value,effective_version,updated_by,status,updated_at) is the **one effective typed nonsecret value per actual CG-01 Foundation-root/key**, enforced by UNIQUE(foundation_root_realm_ref,key) and allow-listed key/type/value. platform_setting_revision(id,setting_id,version,allowed_redacted_value,actor_ref,changed_at,correlation_ref) is append-only immutable version history with UNIQUE(setting_id,version), retaining only safe values, never raw credentials. Expected-version CAS writes effective value, one historical revision and redacted platform owner audit in a short transaction. CG-02 legal profile, CG-18 public toggles and CG-01 authentication-policy values are not duplicated; CG-01-BR11/US-004 owns the complete effective password/session/MFA policy, API, Web/Internal Android editor and enforcement; CG-21 does not expose a security-policy status or editable control in its own platform-settings API.

integration_connection(id,provider,purpose,scope_kind,scope_ref,secret_reference,credential_revision,status,last_checked_at,last_checked_credential_revision,last_result_class,version) stores only a protected external secret-manager reference, never the credential itself or raw provider payload. Initial scope_kind=FOUNDATION with nonnull actual CG-01 root scope_ref, enforced by CHECK and UNIQUE(scope_kind,scope_ref,provider,purpose); NULL-scope uniqueness bypass is forbidden. Future center-specific merchant is introduced only by its genuine later owner. Credential rotation increments credential_revision, resets status CONFIGURED_NOT_VERIFIED and invalidates earlier check. A genuine bounded on-demand provider check reports VERIFIED only when last_checked_credential_revision matches current credential_revision, with actual observed time; FAILED/UNAVAILABLE otherwise. Never use check to assert payment or delivery success, or schedule recurring provider calls while idle.

**Source audit ownership:** CG-01 original access_audit and **its own implemented, permissioned, bounded source-audit read facade (CG-01 DLD §2B / US-002-QA11, US-003-QA13)** are the real delivered predecessor; CG-21 queries that typed facade only, never imports/copies CG-01 audit rows to a CG-21 table. CG-21 owns only append-only platform_operation_audit(id,foundation_root_realm_ref,actor_account_ref,operation_kind,resource_ref,outcome,correlation_ref,at,redacted_summary) committed with real settings/provider/recovery changes. The initial central read-only view composes **CG-01 and CG-21 only** with bounded calls, server-side scope, stable time+source+event cursor and capped export. No future-owner data adapter or table is needed for CG-21 acceptance; each later source owner adds and QA-traces its projection only when implemented. On source outage, response is PARTIAL/UNAVAILABLE rather than an apparently complete empty log; future owners opt in only after actual delivery. Restrict high-risk audit export/detail separately and redact credential values, tokens, contacts, sensitive before/after content, private links, patient/bank/payroll records and diagnostic payloads.

recovery_operation(id,foundation_root_realm_ref,operation_type,backup_reference,requested_by,authorized_by,status,provider_operation_ref,verified_proof_ref,idempotency_key,requested_at,updated_at,version) uses UNIQUE(foundation_root_realm_ref,idempotency_key) and current-revision CAS. Each request/authorization requires genuine CG-01 active Super Admin/fresh MFA, with a distinct authorized approver only when adopted operational policy requires it. No CG-03 case, CG-19 document or other future owner is required. Only CG-01 authentication/MFA and independently configured operational backup evidence may authorize protected recovery. REQUESTED → PRIVILEGED_AUTHORIZED → RUNNING → VERIFIED_SUCCEEDED/FAILED/UNKNOWN is a guarded state machine. Missing actual secured backup/provider returns NOT_AVAILABLE, never fake RUNNING. Only the trusted operational adapter with real provider_operation_ref can mark RUNNING; VERIFIED_SUCCEEDED requires independently confirmed **actual** recovery-provider completion plus post-restore integrity/health verification of the restored target. A prior independently authorized **isolated recovery drill** is an operational readiness gate before production use, not a substitute for evidence that a particular requested recovery actually completed. Unknown external result is re-queried with original idempotency key, never repeated destructively. Real production restore requires separate operations authorization, not a UI button/DB transaction; RPO/RTO are not claimed without measurements.

**QA:** unauthorized/expired-MFA recovery request; duplicate/concurrent setting and credential revision races; backend denial despite hidden UI; secret and token redaction; provider check unavailable/configured-only never shown VERIFIED; initial root-only CG-01 audit without CG-03/02/18; eventual owner feed PARTIAL; pagination/export scope/egress; no idle polling; false backup PASS and uncertain restore outcome.

## Real source integration and module-specific QA

**Critical acceptance:** CG-01 protected admin changes one permitted versioned setting with conflict protection, performs a real on-demand provider check **if configured**, and sees accurate VERIFIED/NOT_VERIFIED/UNAVAILABLE. Central audit reads existing protected CG-01 access events, not copied new audit records. Unauthorized restore, missing MFA, cross-scope export, concurrent writes and false restore PASS remain blocked; verified restore success requires independent evidence not created by planning.

**Contract availability:** CG-01 and CG-21 own the entire initial settings, revision-history, root audit projection and guarded recovery-availability/request journey. No real file/branch/approval/finance/center/CMS owner or configured external provider account is required to develop or test core CG-21. Optional verification/restore outcomes require genuine configured providers and separate authorized integration/operations QA; later owner domains add their own bounded read projections and test integrations when delivered. CG-21 does not implement future adapters in advance.

**API acceptance:** Commands validate current action + actual record scope, owner/source ref, expected revision and idempotency key on irreversible writes; responses distinguish confirmed, pending, invalid, forbidden, conflict, provider unavailable and unknown write status. Scoped options/search may show readable authorized labels without full master read. Each named story QA case traces the real channel -> request -> authorization -> transaction -> stored status -> permitted report/published view.

## Typed API and coordination

An authenticated `/api/platform-configuration-audit` owner facade exposes settings and provider operations, guarded recovery-request state, and a protected **bounded audit read projection** over real owners. Platform settings, secrets, recovery and audit are private; **there is no public CG-21 read or publication allowlist endpoint**. External/public visibility is decided only by the actual CG-18 owner when delivered. Each PRD command contract:
- **FR-075** — Super Admin configures only CG-21 versioned operational settings and optional secured provider-reference/readiness metadata. CG-02 legal profile, CG-18 public navigation, CG-19 delivery, CG-09/17 financial effects and CG-01 security policy have their own source modules. Validate current actor/root, typed key, expected revision, secret-reference safety and idempotent true result.
- **FR-076** — CG-21 reads the real delivered CG-01/CG-21 audit projection, logs only CG-21 operations, and guards actual backup/recovery availability/request/status using CG-01 current protected Super Admin + fresh MFA. No other business log ownership or policy-editor API is provided here; authorize root scope, original event ref, immutable key and verified provider proof.

Business outcome categories: `SUCCESS/SUBMITTED_PENDING/VALIDATION/DUPLICATE/FORBIDDEN/NOT_FOUND_OR_HIDDEN/CONFLICT/UNAVAILABLE/UNKNOWN_WRITE_STATUS`. External provider failure never becomes fake success. Use a DB transaction for state+audited result, optimistic revisions or narrowly scoped row locks for races and unique source idempotency. Cross-owner effects go through typed facades, not another module's repository. Approved HLD pattern (plain state guard, policy, adapter, facade) only where actual variation justifies it; reject universal DSL, speculative microservice or duplicated ledger. No unbounded idle polling or uncontrolled retries.


## CG-21 scenario-to-pattern decisions (CG-01 benchmark)

| Material scenario | Selected minimal pattern and authoritative owner | Rejected alternatives (including plain option) | Extension and test |
| --- | --- | --- | --- |
| Typed settings and concurrent edits | Plain CG-21 typed validator, CAS transaction, append-only history/audit | Unguarded single-value update loses edits; generic policy/settings DSL adds unjustified complexity | Review one allow-listed key and safe default per new setting; replay, race and history tests |

**Design economy:** no second auth stack, security audit ledger, generic event framework, new microservice, speculative queue or forced Strategy/Template Method inheritance. Add only a provider adapter when actual approved variation justifies it.

## CRITICAL PostgreSQL architecture, migration and recovery

- **Constraints:** One actual CG-01 root realm FK and UNIQUE(root,key) effective setting; append-only setting_revision UNIQUE(setting_id,version); integration CHECK(nonnull real_root scope) with UNIQUE(scope_kind,scope_ref,provider,purpose); recovery UNIQUE(root,idempotency_key), version-guarded status transitions and original CG-21 operation audit. No future CG-02/03/14/18 FK or duplicate CG-01 access_audit.
- **Atomicity:** CAS effective setting+revision+source audit in one short transaction, credential rotation+invalidated verification+audit in one transaction and recovery state change+audit under revision guard. Validate current CG-01 root/fresh MFA, source permission and trustworthy external proof. CG-01 facade, external secret-manager/provider and actual restore I/O occur **outside SQL locks**; unknown reply resolves by original key/status and never a duplicate destructive action.
- **Indexes and cost:** scoped settings(root,key), version history(setting_id,version DESC), integration(scope_kind,scope_ref,provider,purpose), platform audit(root,at,id) and recovery(root,status,updated_at,id), plus owner-idempotency UNIQUE. Stable paged audit filters and bounded per-owner source projection; cap export and avoid per-row N+1 / future owner fanout. Verify real index choices via disposable EXPLAIN, SQL counts, request bytes/egress and concurrency (all NOT_MEASURED until actual QA).
- **Migration:** CG-21 adds only owned tables to the **one CG-01 bootstrapped PostgreSQL migration history**. Actual DB engine/ORM version is UNVERIFIED. Additive migrations, staged backfill only when legitimate records already exist, safe re-apply and forward repair, no destructive down-migration of actual history, and independently tested disposable rollback/isolated restore. No fake production backup/restore facility, and independent qualified CRITICAL DB review, migration/run/restore remain NOT_RUN.
- **Security/idleness:** root server-scope guard for every list/option/detail/export/write; stricter current Super Admin/fresh MFA for recovery. Password/session policy remains CG-01 owned. No raw secrets/logs/PII, no false verified provider or restore state. Zero eligible provider/recovery work across many instances means zero CG-21 fast tenant scans or wake-up provider calls; bounded due claims when genuine work exists. Actual latency/RPO/RTO/egress are NOT_MEASURED.
