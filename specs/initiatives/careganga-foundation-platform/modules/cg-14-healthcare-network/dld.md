## 4. Full transaction, verification, approval and public revocation

**Registration US-001:** CG-01 verifies current Foundation healthcare registration capability OR a permitted authenticated applicant with actual source relation; derive root from session and selected real CG-02 geography, not user branch/root. Draft→submitted provider/location survives CG-19 pre-verification evidence upload. Actual CG-19 adapter is introduced in US-001 **inside CG-19** for CG14_PROVIDER_DRAFT source (provider/application/location version), accepting protected MIME/size/scan/checksum and private preview without inventing CG-03 case. Save provider/location/submission/audit in short transaction, idempotency by (root,source_kind,request_key,digest), lost-response status lookup and no actual review claim yet. A location's code/name is unique within its parent provider; center applicant cannot impersonate another provider. First story works with zero doctors, booking, CMS or approved center role.

**Provider decision US-002:** CG-03 process and source adapter CG14_PROVIDER_VERIFICATION introduced in CG-03, reviewer policy configured under actual Foundation authorization. The submitted immutable provider/center revision+digest and current CG-19 VALIDATED proof are pinned to case. RETURNED changes require new revision/new case; approved old revision never approves later mutation. CG-14 guarded finalizer applies a genuine current CG-03 final outcome to *its own* provider/location in short shared PostgreSQL transaction with real read-only owner-facade evidence fence and stable locks (CG-03/19 proof first, then CG-14 source). Reject stale approval, revoked reviewer, foreign-root, wrong location, duplicated callback and concurrent suspend vs approve. Login access through CG-01 active verified center-scope grant is distinct from provider verification; center suspension fences next eligible Center Portal action, CGI booking eligibility and public listing immediately. A center may be approved but NOT_PUBLIC; publication is an independent Foundation permissioned transition and source revision, never automatic upon approval. CG-14 public single-center status read suffices for US-002 QA; full discovery/search lives in US-004.

**Doctor US-003:** One professional identity keyed by genuine registration jurisdiction/normalized number; if credential absent, source stays UNVERIFIED and never claims verified badge or public availability. CG14_DOCTOR_VERIFICATION case and protected doctor-credential CG-19 adapter introduced here (not assumed baseline). Approve exact profile revision; center operator with own current scope may *request* doctor-center affiliation, not edit global doctor credentials/other center fee. A doctor can have location A and B with separate accepted fee/mode and validity; revoking affiliation A does not deactivate B. Fee create/change uses active current CG-01 permission, genuine verified active doctor-center, no overlapping approved effective periods; append a new version, don't mutate historical fee. CG-15 later consumes immutable accepted fee/mode snapshot in real bookings, never CG-14 creating booking.

**Public US-004:** Expose solely current active APPROVED/PUBLISHED provider/location with verified, active, approved doctor-center relation, current effective approved fee and public service flags. Public **standalone** Next.js directory and Public Android native list/detail from CG-14 allowlisted DTO; no prerequisite CG-18 CMS. If CG-18 is actually integrated, it supplies approved editorial slot/heading/visibility but never doctor, fee, source eligibility or public record. Public search supports category (nine reference types), state/district/block/PIN where actual source, specialty/qualification/experience/fee, facilities, verified status, safe sort/pagination, optional map/directions based on genuine coordinates. **CG-15 slot/availability filters, CG-16 test/package catalog, CG-17 current benefit amount and rating source must be absent/unavailable until those true owners implement them.** A published capability label (24×7, home sample, medicine, insurance, online booking) appears only if genuinely verified and is not transactional promise. A doctor without an active location is never bookable or falsely shown at that location. No patient data or provider bank/credential in public DTO.

**Center portal US-005:** Current CG-01 center-scope grant + CG-14 actual active location permits own profile draft; source canonical center service/hours/contact/FAQ/media referenced to CG-19 real approved rights. Submitted version freezes; CG-14 introduces center-content case in CG-03 with current real Foundation reviewer, and applies only exact approved revision to CG-14's public center-detail source. Center self-edit cannot change previous published detail, verification, legal credential, approved fee or CG-17 support policy until reviewed; Center A cannot access B. Center Portal may embed CG-19's **one** center-scoped helpdesk, using actual CG-14 verified center assignment and a narrow later CG-19 owner extension; no CG-14 ticket/message data. Optional CG-18 page placement, if implemented, is a separate editorial frame; owner profile remains independently publishable in CG-14 own directory.

**Network effects:** API/profile writes + source event + audit/outbox claim commit together (if existing source outbox available), external image scan/geo/map/email and CDN purge occur outside DB lock. No external HTTP/network call under locked transaction; owner facades need same-DB transactional proof or a reviewed claim/fence with revalidation to avoid revocation races. Revoked eligibility no stale search/deep link in public Web or native app; CDN invalidation/event is a secondary recoverable effect, not permission. Avoid per-center idle polling/worker jobs.
