## What the development agent must do first

1. Read root [AGENTS.md](../../../AGENTS.md) and this order file at the start of work. Use the **latest current feature-branch PRD/HLD/module/UIUX/DLD/tasks** even if drafts. Confirm current Harness main/pin; a GitHub source review is not resolver PASS. Run the authenticated resolver for formal stage entry when available; when unavailable, record `RESOLVER_NOT_RUN`. Only specifically owner-authorized `DRAFT_SOURCE_ONLY` source edits may proceed provisionally without formal approval; never claim stage PASS.
2. Read the newest working-branch [PRD](prd.md), [HLD](hld.md), then selected current `module.md`, `uiux.md`, `dld.md`, `tasks.md` and reference evidence **regardless of approval state**; never revert to stale approved versions. Formal `READY`/`SOURCE_COMPLETE` requires actual current-hash approvals and recorded QA source evidence. For an explicitly owner-authorized provisional story, `REVIEW_REQUIRED` or `BLOCKED` **only because planning approval is pending** permits `DRAFT_SOURCE_ONLY` implementation with visible `DRAFT_UNAPPROVED` evidence, not formal completion. Missing required real predecessor/source owner, unresolved security/finance contract, or unavailable work authority still BLOCKS coding.
3. Deliver the **one-time technical bootstrap as CG-01/US-001** (HLD §4.0; CG-01 DLD §1A): single npm workspace and lockfile, one NestJS backend/PostgreSQL migration history, one Next.js Web app, separate Public/Internal Expo Android apps, safe shared API schemas and a single original CareGanga theme/motion token source. Do not create a CG-00 business module or 20 empty business folders.
4. Complete the **F0–F5 foundation before parallel business-module work**. Thereafter use the P1–P6 ready-work waves below with up to **three independent feature branches/developers**. The numbered index is a valid topological reference, **not** a requirement to serialize modules whose prerequisites are genuinely complete; conversely, being in the same wave does not authorize use of peer unmerged work. Never bypass gates or fabricate downstream masters, approvals, files, balances, users or selectors.
5. For every currently approved **or explicitly owner-authorized draft-source story**: implement real backend/API, permitted responsive Web and applicable Android, owned DB/transactions → independent expert **manual source review** (including database, idle-worker/egress, security, concurrency, observability, human errors and original UI/UX) → fix/re-review → trace **each** inline story QA case through real source → update its existing `tasks.md` execution progress. Draft status stays `IN_PROGRESS | approval=DRAFT_UNAPPROVED` until latest artifacts are formally approved and code is reconciled/re-reviewed. No CI/GitHub Actions, live builds/tests or claims of visual/performance PASS during Development. Actual runtime/device/PNG-motion comparison is separate authorized QA.
6. Before leaving a module, confirm current owner contracts and failure states work on their own; preserve all prior working flows; do **not** quietly defer an originally required business outcome. When a future owner introduces new source data, that **later owner** implements and QA-traces the true cross-module selector, role/permission, UI, API, privacy, and reporting integration with prior owners.

## Foundation-first delivery and safe parallel workstreams

**Planning review order stays CG-01 → CG-02 → … → CG-21; implementation order is different and strictly prerequisite-driven.** This schedule is for **2–3 developers**, each in a separately owned business module/feature branch. A "wave" opens only when all stated predecessor modules have **actually reached their approved delivery/QA gate and are integrated into the common baseline**. Passing source design review or writing a future interface does NOT satisfy a runtime dependency.

### Three-developer waves (preferred maximum safe concurrency)

The rows in a wave are **separately owned modules with no same-wave business dependency**. A later wave can start by individual module as soon as its exact predecessors are integrated, but it must never assume another still-unmerged developer's source exists. Wave numbers give a simple conservative schedule, **not mandatory release dates**.

| Parallel wave after F5 | Developer A | Developer B | Developer C | Entry/exit condition |
| --- | --- | --- | --- | --- |
| **P1** | **CG-09** Foundation finance/accounting | **CG-14** verified healthcare centers/doctors | **CG-10** employees/HR | All use F0–F5 only; deliver independently owned ledgers, provider master and employee master |
| **P2** | **CG-12** inventory/suppliers | **CG-15** patient schedules/booking | **CG-05** projects/tasks/field visits | CG-12 may integrate real CG-09; CG-15 requires completed CG-14; CG-05 may use delivered CG-10/09 but must never require a future beneficiary |

| **P4** | **CG-13** verified referrals/rewards | **CG-17** healthcare support/settlement | **CG-07** campaigns/donations | CG-13 uses CG-04/12/09; CG-17 uses CG-14/15/09/19; CG-07 uses CG-18/09/19/03 and actual CG-05 if project-linked |
| **P5** | **CG-08** CSR partnerships/funding | **CG-06** beneficiaries/assistance | **CG-11** payroll/compensation | CG-08 uses CG-05/09/19; CG-06 uses CG-05/12/09; CG-11 uses CG-10/09/03/19 |
| **P6 (integrated)** | **CG-20** source-backed MIS/reporting | — | — | Only after verified owner projections exist; final integrated coverage after all owners, and no fabricated values |

**For two developers:** Use **the same dependency graph**, not a separate plan: fill two available lanes from the earliest dependency-ready wave, and pick the remaining item when a slot frees **and its prerequisite owners are merged**. For example P1 begins with CG-09 and CG-14; CG-10 is the next safe P1 item. Never use a third developer's unmerged module as a dependency or claim parallel integration complete.

**Parallel compatibility ≠ source folders alone:** Parallel developers own their new `apps/backend/src/modules/cg-XX-.../`, new business migration(s), `apps/web/src/features/<owner>/` and owned Android features; each reads the existing approved API/permission/UX contracts. Shared files (`app.module.ts`, central permission catalog, route/sidebar registration, root lockfile, `packages/api-contracts` exports, shared theme, migration registry) have **one integration owner** and a short reviewed merge queue. Developers prepare a typed public owner interface but must **not independently rewrite the shared foundation** or insert placeholder future routes. Where legitimate shared-contract change is essential, agree and merge that smallest stable contract **before** consumers branch from it.

**Branching/DB/test isolation:** Cut each developer feature branch from the same already approved and integrated foundation HEAD; never merge it into another unfinished peer's branch. Use separate local database instances/Neon dev branches or equivalent isolated nonproduction schemas and separate auth/provider test configuration; never share a mutable dev database or test user namespace across independent feature QA. Name migrations uniquely with owner ID + reviewed ordering; before integrating, rebase against latest accepted baseline, resolve timestamp/ordering/unique index conflicts and check real Postgres migration order/rollback. Merge integration changes **serially** to one product integration branch with expert source review, backend authorization/DB contract check and existing CG-01/regression-story trace. Separate independently authorized runtime/manual visual QA checks apply only in QA, not as invented Development PASS; no CI/GitHub Actions.

**A parallel wave is BLOCKED if any of these are true:** (a) base foundation module not really delivered; (b) the proposed module needs an unmerged same-wave or later owner for its **main** use case; (c) two developers must simultaneously rewrite the same foundational auth/data/route schema; (d) DB migration sequencing or resource scopes are unresolved; (e) approved current-hash PRD/HLD/module/task/resolver gates are missing; (f) source QA cannot use real predecessor records. Resolve by splitting the truly optional integration into the *later introducing owner*, assigning a single integrator, or moving the prerequisite into an earlier wave. No speculative mocks or duplicate source masters.

## Integration ownership and circular-dependency guard

- **CG-01 ↔ CG-03:** CG-01's own auth/role actions are complete without CG-03. CG-03 subsequently owns the protected access-change application and review; it calls a guarded CG-01 apply-approved command *once*. CG-01 must not create an unfinishable pending-only approval screen.
- **CG-03 → CG-19 → CG-02:** CG-03's first real case targets an existing CG-01 account/role **without document attachments**, so it does not depend on CG-19. CG-19 then stores genuine protected CG-01/03 source files and issues safe download references. CG-02's seven-stage branch setup may now use **both actual CG-19 evidence and CG-03 final approval**; branch code appears only once after final approval. Do not add a CG-02-specific parallel approval engine or a CG-19 placeholder into CG-03's first case.
- **CG-21 does not take over CG-01's role audit.** CG-01 keeps the durable original access-audit record; CG-21 provides permissioned configuration and central audit presentation without a second security ledger.
- **CG-02 → CG-01:** CG-02's geography/branch source can extend CG-01's context-aware permissions only when real areas/branches exist; CG-02 owns the new selector/authorization/integration QA. No fictitious Foundation branches in CG-01.
- **CG-10/04/05/12/09 → earlier owners:** Any staff, volunteer, project, stock or budget selector is populated by the real delivered owning module, with a minimal permitted selector permission. A record selector is not automatically private master/ledger read authorization.
- **CG-14 → CG-18/15 → CG-16/17:** CG-14 owns center/doctor/fee truth; CG-15 owns doctor-wide slot occupancy and real full-fee booking without a CG-17 payment success; CG-16 owns released clinical reports; CG-17 later introduces genuine assistance and verified collection/reconciliation. No shadow doctors/appointments/patient files.
- **CG-09 → money consumers and CG-20:** CG-09 owns one balanced posting authority; donations, CSR, payroll, aid and healthcare settlement call its typed facade using immutable source-event idempotency. CG-20 reads only permission-filtered delivered projections; no second ledger or fake KPI numbers.
