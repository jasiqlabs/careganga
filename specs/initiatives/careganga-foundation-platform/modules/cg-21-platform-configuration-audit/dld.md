## Canonical source, authorization and data ownership

CG-21 owns versioned platform settings, integration verification metadata and protected credential references, read-only *central audit presentation* of genuine owner events plus CG-21's own setting/recovery audit, and privileged backup/recovery requests with genuine outcome evidence. CG-01 remains the sole authority for its original login/session/role/access audit facts and privileged MFA/access-policy enforcement. CG-21 must not create a competing security audit master, identity service, or dependence on future CG-03/CG-02/CG-18 records.

## Concrete security settings, audit and recovery contracts

platform_setting(id,foundation_root_realm_ref,key,value_class,typed_value,effective_version,updated_by,status,updated_at) is the **one effective typed nonsecret value per actual CG-01 Foundation-root/key**, enforced by UNIQUE(foundation_root_realm_ref,key) and allow-listed key/type/value. platform_setting_revision(id,setting_id,version,allowed_redacted_value,actor_ref,changed_at,correlation_ref) is append-only immutable version history with UNIQUE(setting_id,version), retaining only safe values, never raw credentials. Expected-version CAS writes effective value, one historical revision and redacted platform owner audit in a short transaction. CG-02 legal profile, CG-18 public toggles and CG-01 authentication-policy values are not duplicated; allowed session/password options shown in CG-21 use the **CG-01 protected policy facade** and display its actual effective result.

integration_connection(id,provider,purpose,scope_kind,scope_ref,secret_reference,credential_revision,status,last_checked_at,last_checked_credential_revision,last_result_class,version) stores only a protected external secret-manager reference, never the credential itself or raw provider payload. Initial scope_kind=FOUNDATION with nonnull actual CG-01 root scope_ref, enforced by CHECK and UNIQUE(scope_kind,scope_ref,provider,purpose); NULL-scope uniqueness bypass is forbidden. Future center-specific merchant is introduced only by its genuine later owner. Credential rotation increments credential_revision, resets status CONFIGURED_NOT_VERIFIED and invalidates earlier check. A genuine bounded on-demand provider check reports VERIFIED only when last_checked_credential_revision matches current credential_revision, with actual observed time; FAILED/UNAVAILABLE otherwise. Never use check to assert payment or delivery success, or schedule recurring provider calls while idle.

**Source audit ownership:** CG-01 original access_audit stays authoritative behind its protected bounded CG-01 read facade, never copied to a CG-21 audit table. CG-21 owns only append-only platform_operation_audit(id,foundation_root_realm_ref,actor_account_ref,operation_kind,resource_ref,outcome,correlation_ref,at,redacted_summary) committed with real settings/provider/recovery changes. The central read-only view composes only **delivered** authorized owner projections (initially CG-01 and CG-21), with bounded source calls, server-side scope, stable time+source+event cursor and capped export. On source outage, response is PARTIAL/UNAVAILABLE rather than an apparently complete empty log; future owners opt in only after actual delivery. Restrict high-risk audit export/detail separately and redact credential values, tokens, contacts, sensitive before/after content, private links, patient/bank/payroll records and diagnostic payloads.

recovery_operation(id,foundation_root_realm_ref,operation_type,backup_reference,requested_by,authorized_by,status,provider_operation_ref,verified_proof_ref,idempotency_key,requested_at,updated_at,version) uses UNIQUE(foundation_root_realm_ref,idempotency_key) and current-revision CAS. Each request/authorization requires genuine CG-01 active Super Admin/fresh MFA, with a distinct authorized approver only when adopted operational policy requires it. No unimplemented CG-03 case is needed. REQUESTED → PRIVILEGED_AUTHORIZED → RUNNING → VERIFIED_SUCCEEDED/FAILED/UNKNOWN is a guarded state machine. Missing actual secured backup/provider returns NOT_AVAILABLE, never fake RUNNING. Only the trusted operational adapter with real provider_operation_ref can mark RUNNING; VERIFIED_SUCCEEDED requires independent result and isolated restore-drill evidence. Unknown external result is re-queried with original idempotency key, never repeated destructively. Real production restore requires separate operations authorization, not a UI button/DB transaction; RPO/RTO are not claimed without measurements.

**QA:** unauthorized/expired-MFA recovery request; duplicate/concurrent setting and credential revision races; backend denial despite hidden UI; secret and token redaction; provider check unavailable/configured-only never shown VERIFIED; initial root-only CG-01 audit without CG-03/02/18; eventual owner feed PARTIAL; pagination/export scope/egress; no idle polling; false backup PASS and uncertain restore outcome.

## Real source integration and module-specific QA

**Critical acceptance:** CG-01 protected admin changes one permitted versioned setting with conflict protection, performs a real on-demand provider check **if configured**, and sees accurate VERIFIED/NOT_VERIFIED/UNAVAILABLE. Central audit reads existing protected CG-01 access events, not copied new audit records. Unauthorized restore, missing MFA, cross-scope export, concurrent writes and false restore PASS remain blocked; verified restore success requires independent evidence not created by planning.

**Contract availability:** The initial CG-21 settings/CG-01 audit/recovery-request journey requires only implemented CG-01, not CG-03 approvals, CG-02 branches, CG-18 publishing or external enabled provider accounts. Later owners expose permission-checked read projections of their original audit events; CG-21 adds feeds only after the corresponding source exists, never a duplicate audit log.

**API acceptance:** Commands validate current action + actual record scope, owner/source ref, expected revision and idempotency key on irreversible writes; responses distinguish confirmed, pending, invalid, forbidden, conflict, provider unavailable and unknown write status. Scoped options/search may show readable authorized labels without full master read. Each named story QA case traces the real channel -> request -> authorization -> transaction -> stored status -> permitted report/published view.

## Typed API and coordination

An authenticated `/api/platform-configuration-audit` owner facade exposes settings and provider operations, guarded recovery-request state, and a protected **bounded audit read projection** over real owners. Platform settings, secrets, recovery and audit are private; **there is no public CG-21 read or publication allowlist endpoint**. External/public visibility is decided only by the actual CG-18 owner when delivered. Each PRD command contract:
- **FR-075** — Super Admin manages platform: Configure Foundation/system settings, approved payment/messaging/map integrations and public visibility through the owning modules; sensitive credentials restricted. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.
- **FR-076** — Administrator audits or recovers: Show protected logs for login, approvals, money, provider verification, sensitive accesses and publishing; restrict backup/restore to approved operations and support privileged MFA/session controls. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.

Business outcome categories: `SUCCESS/SUBMITTED_PENDING/VALIDATION/DUPLICATE/FORBIDDEN/NOT_FOUND_OR_HIDDEN/CONFLICT/UNAVAILABLE/UNKNOWN_WRITE_STATUS`. External provider failure never becomes fake success. Use a DB transaction for state+audited result, optimistic revisions or narrowly scoped row locks for races and unique source idempotency. Cross-owner effects go through typed facades, not another module's repository. Approved HLD pattern (plain state guard, policy, adapter, facade) only where actual variation justifies it; reject universal DSL, speculative microservice or duplicated ledger. No unbounded idle polling or uncontrolled retries.


## CG-21 scenario-to-pattern decisions (CG-01 benchmark)

| Material scenario | Selected minimal pattern and authoritative owner | Rejected alternatives (including plain option) | Extension and test |
| --- | --- | --- | --- |
| Typed settings and concurrent edits | Plain CG-21 typed validator, CAS transaction, append-only history/audit | Unguarded single-value update loses edits; generic policy/settings DSL adds unjustified complexity | Review one allow-listed key and safe default per new setting; replay, race and history tests |
| Optional provider verification varies by integration | Small conditional provider adapter behind CG-21 readiness facade with credential-revision guard | Fake verified checkbox or UI direct provider access leaks secrets; generic Factory/Strategy hierarchy premature for no real variants | Add a real provider only through reviewed adapter; rotate invalidates checks; zero calls when idle |
| Read-only audit from CG-01 and CG-21 | Bounded source-facade composition using stable time/source/event cursor | Copying access audit into a second event ledger diverges; eager polling of future owners leaks work and data | Future source contributes only after delivered; paging/export/partial-feed isolation tests |
| Privileged recovery request and real external proof | Versioned state guard plus trusted operations adapter; CG-01 MFA/role authority | A boolean success toggle fabricates restore; future CG-03 approval dependency or Saga/microservice is unnecessary | No provider calls under DB lock; unknown result reconciliation, real isolated drill |
| Session/password policy option presentation | Typed CG-01 protected policy facade (CG-21 only presents actual state) | Duplicating authentication policy in platform_setting creates conflicting source truth | Verify CG-01 enforcement, revocation and no unsupported security control |

**Design economy:** no second auth stack, security audit ledger, generic event framework, new microservice, speculative queue or forced Strategy/Template Method inheritance. Add only a provider adapter when actual approved variation justifies it.

## CRITICAL PostgreSQL architecture, migration and recovery

- **Constraints:** One actual CG-01 root realm FK and UNIQUE(root,key) effective setting; append-only setting_revision UNIQUE(setting_id,version); integration CHECK(nonnull real_root scope) with UNIQUE(scope_kind,scope_ref,provider,purpose); recovery UNIQUE(root,idempotency_key), version-guarded status transitions and original CG-21 operation audit. No future CG-02/03/14/18 FK or duplicate CG-01 access_audit.
- **Atomicity:** CAS effective setting+revision+source audit in one short transaction, credential rotation+invalidated verification+audit in one transaction and recovery state change+audit under revision guard. Validate current CG-01 root/fresh MFA, source permission and trustworthy external proof. CG-01 facade, external secret-manager/provider and actual restore I/O occur **outside SQL locks**; unknown reply resolves by original key/status and never a duplicate destructive action.
- **Indexes and cost:** scoped settings(root,key), version history(setting_id,version DESC), integration(scope_kind,scope_ref,provider,purpose), platform audit(root,at,id) and recovery(root,status,updated_at,id), plus owner-idempotency UNIQUE. Stable paged audit filters and bounded per-owner source projection; cap export and avoid per-row N+1 / future owner fanout. Verify real index choices via disposable EXPLAIN, SQL counts, request bytes/egress and concurrency (all NOT_MEASURED until actual QA).
- **Migration:** CG-21 adds only owned tables to the **one CG-01 bootstrapped PostgreSQL migration history**. Actual DB engine/ORM version is UNVERIFIED. Additive migrations, staged backfill only when legitimate records already exist, safe re-apply and forward repair, no destructive down-migration of actual history, and independently tested disposable rollback/isolated restore. No fake production backup/restore facility, and independent qualified CRITICAL DB review, migration/run/restore remain NOT_RUN.
- **Security/idleness:** root server-scope guard for every list/option/detail/export/write; stricter current Super Admin/fresh MFA for recovery. Password/session policy remains CG-01 owned. No raw secrets/logs/PII, no false verified provider or restore state. Zero eligible provider/recovery work across many instances means zero CG-21 fast tenant scans or wake-up provider calls; bounded due claims when genuine work exists. Actual latency/RPO/RTO/egress are NOT_MEASURED.
