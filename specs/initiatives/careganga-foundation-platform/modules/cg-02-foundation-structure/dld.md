## Data ownership and decision boundary

CG-02 owns exactly one legal/operational Foundation profile, its real geography tree, editable seven-step branch registration, the approved branch directory, and **Foundation-wide or branch-scoped** departments/committees. CG-21 owns provider/system configuration and may read the real CG-02 profile, not duplicate it. CG-01 owns authenticated actors; CG-03 owns approval decisions; CG-19 owns protected file bytes. A business actor, not a fabricated employee, may be linked during the initial branch draft. CG-10 employment/CG-05 projects/CG-04 memberships/CG-09 budgets introduce their own real links after they exist.

Only a completed authorized CG-03 decision may activate a branch and issue its unique code. Draft and approved data remain distinguishable, with one idempotent finalization for one registration. Store all cross-owner references as verified opaque keys; render readable business names, not identifiers.

## Canonical database and workflow contracts

- `foundation_profile(id, foundation_root_realm_ref, legal_name, official_contact, postal_address, legal_registration_ref, registration_authority, registration_date, version, updated_at)`: One Foundation legal/operating master, unique real CG-01 Foundation-root realm; capture valid legal name, registered details, official contact/address, permitted settings, source audit and expected-version CAS. US-001 works with CG-01 only; CG-19 file is not required. CG-21 must not store this same legal profile; CG-18 later publishes approved subset only.
- `geography_area(id, foundation_root_realm_ref, level, parent_area_id, display_name, normalized_name, code, status, version)`: Same-root CG-01 FK and same-root parent FK (or equivalent strict DB constraint); canonical state→district→optional subdivision→block/area tree. Root partial UNIQUE `(foundation_root_realm_ref, level, normalized_name)` for null parent, child partial UNIQUE `(foundation_root_realm_ref,parent_area_id,level,normalized_name)` for non-null parent. Parent levels, optional district→block, self/cycle, status, concurrent reparent validated transactionally with a Foundation-root hierarchy lock. Deny foreign-root values and deactivation/reparent that strands ACTIVE branch/department scopes; preserve names/history and bounded geographic options. No second `geography_unit` master.
- `branch_registration(id, foundation_root_realm_ref, foundation_id, current_step, draft_version, status, requested_by, manager_account_ref, current_submission_revision, profile_payload, created_at, updated_at)`: Exactly one editable seven-stage source draft; same CG-01 root as Foundation profile, applicant and manager. Payload includes real branch name/type/opening date, geography/region, address/PIN/GPS, contacts, optional stage-1 photo/logo and stage-3/4 verified CG-19 file refs, current CG-01 manager and selected existing Foundation departments. Freeze original submitted revision, never mutate it; only RETURNED opens revised editable draft with new revision, rejected case stays terminal without explicit new application.
- `branch_registration_submission(id, foundation_root_realm_ref, registration_id, submitted_revision, source_submission_key, immutable_snapshot_payload, immutable_payload_digest, file_evidence_ref_versions, submitted_at, approval_case_ref, status)`: Append-only snapshot and file ref+version proof, same-root relation to original registration; `UNIQUE(registration_id,submitted_revision)`, `UNIQUE(registration_id,source_submission_key)` and unique non-null case. Snapshot pins actual manager/area/links and validated CG-19 evidence; CG-03 case binds source revision+digest+key. RETURNED resubmission creates new row/case with predecessor history; unknown case result stays SUBMISSION_UNCONFIRMED (not approved/pending). Former decisions cannot activate later edits.
- `branch(id, foundation_root_realm_ref, registration_id, approved_submission_id, geography_area_id, branch_name, branch_type, opening_date, postal_address, pin_code, gps_location, official_phone, official_email, manager_account_ref, current_evidence_ref_versions, branch_code, status, version, activated_at, closed_at)`: One operating branch for the exactly matching verified approved submission; same-root refs, `UNIQUE(registration_id)` and unique non-null issued `branch_code`. Initialize current fields from original approved frozen submission. Later authorized ACTIVE-branch `PATCH` may update name/type/real location/GPS, opening date, contacts, eligible manager and CG-19-protected photo/registration/agreement versions by CAS+idempotency; code and approved submission never change. `branch_profile_revision` (append-only CG-02 domain history, branch+version+accepted actor/time+previous/current field proof) stores every accepted current change. Read-only original CG-03 reviewer history remains separate; inactive/closed branches retain history, with no silent reopen/linked data delete.
- `branch_profile_revision(id, foundation_root_realm_ref, branch_id, branch_version, mutation_key, changed_at, changed_by_account_ref, change_reason, before_operating_payload, after_operating_payload, current_file_ref_versions, approved_submission_id)`: append-only, private and permission-filtered **CG-02 current operating-state change history**, including previous values rather than only opaque hashes; same-root FK, UNIQUE(branch_id,branch_version) and UNIQUE(branch_id,mutation_key). Created in the same short branch update transaction as current profile and accepted audit; do not edit prior revisions, original approved submission, CG-03 case or CG-19 stored-file bytes. Account access revocation must block new change, but not erase historical attributable actor details. History read/export must redact protected contact/GPS/media and use current CG-01 access checks.
- `department(id, foundation_root_realm_ref, scope_kind, branch_id, geography_area_id, parent_department_id, kind, name, normalized_name, opening_date, description, active, head_account_ref, version)`: One CG-02 department/committee master. Same CG-01 Foundation root across department, branch/area/parent and actual head account; optional real geography location is permitted for Foundation scope and must match the active branch's compatible geography for branch scope. Row CHECK enforces FOUNDATION⇒branch NULL, BRANCH⇒real branch NOT NULL; active branch/parent lineage/participant scope are locked cross-row checks. Foundation partial UNIQUE `(foundation_root_realm_ref,kind,normalized_name) WHERE branch_id IS NULL`; branch partial UNIQUE `(foundation_root_realm_ref,branch_id,kind,normalized_name) WHERE branch_id IS NOT NULL`. No CG-04/CG-10 person master or duplicate committee table.
- `department_participation(department_id, account_ref, office_role, active_from, active_until, created_by)`: One authorized real CG-01 account officeholder association to actual CG-02 department/committee, with same-root FK/guard, unique current assignment and retained history. Not a CG-04 member/volunteer or CG-10 staff assignment.
- `branch_department_link(id, branch_id, foundation_department_id, linked_at, linked_by, ended_at, ended_by)`: Versioned CG-02 association with same-root branch/Foundation-scoped department validation, real FKs and partial active UNIQUE `(branch_id,foundation_department_id) WHERE ended_at IS NULL`; existing approved links are inserted only at activation, later authorized unlink/relink preserves history. Hold branch lock and reject foreign/inactive/closed links. No future-owned project/employee/budget association.

Commands: Current-root filtered Foundation/geography/department/profile and participants APIs; POST/GET/PATCH seven-stage draft with CAS + idempotency; frozen snapshot submit/CG-03 source status; trusted owner-only finalization; **GET/PATCH current ACTIVE branch operational profile and branch profile revision history** with CAS, genuine CG-19 evidence versions and CG-01 manager proof; scoped branch directory/status/options/exports; branch-to-Foundation-department association history. All mutations require server-side CG-01 capability+actual CG-02 scope, and all lookups/exports omit foreign-root records. Human business references, not UUIDs.

**Submission and finalization boundary:** Before submit, validate CG-01 actor/owner and genuine CG-19 draft evidence without locks; briefly lock registration, confirm draft revision+unchanged file proof, freeze immutable snapshot+digest and commit. **After commit**, call CG-03 typed create-or-find with the same stable source key; unknown result stays SUBMISSION_UNCONFIRMED until confirmed. For finalization, prevalidate CG-03 current distinct Super Admin final decision and CG-19 scanned/not-revoked evidence outside transaction, then use **one short shared PostgreSQL transaction with narrow owner-local read-only proof guards**, introduced in CG-02 US-002 inside their actual CG-01/03/19 modules. Guards operate only on their own indexed tables using the shared transaction/owner facade (CG-02 never imports their repositories), with lock ordering CG-01 actor/root+manager → CG-03 actual case/decision → sorted CG-19 file versions → CG-02 registration/geography/departments/branch. Revocation writers must use compatible locking/fencing, so an earlier revocation fails the proof; only bounded, in-process transactional checks are permitted under locks, **never network/HTTP/provider scan, retry, remote facade or direct cross-owner table writes**. Check frozen revision/digest, current branch/geo/department source and unique effect, issue one code and ACTIVE row+links+audit, commit. If transactional guard is not implemented, activation stays UNAVAILABLE rather than unsafe. Replays return same result; old case/file proof, forged finalizer, area change and unknown commit cannot duplicate activity. Revocation after real activation is a separate historical compliance event and private-file access denial.

## PostgreSQL CRITICAL design, migrations and recovery (same repository)

- **Unique keys:** Foundation root has one legal profile bound to its real CG-01 root realm. Geography roots use partial UNIQUE(foundation_root_realm_ref,level,normalized_name) WHERE parent_area_id IS NULL; children UNIQUE(foundation_root_realm_ref,parent_area_id,level,normalized_name) WHERE parent_area_id IS NOT NULL. Normalize names consistently (case, whitespace and Unicode policy). Departments use row-local CHECK for FOUNDATION with null branch versus BRANCH with non-null branch, Foundation partial UNIQUE(foundation_root_realm_ref,kind,normalized_name) and branch partial UNIQUE(foundation_root_realm_ref,branch_id,kind,normalized_name), plus transactional parent/scope/active-branch checks. An FK cannot assert that the referenced branch is ACTIVE or a target department is FOUNDATION-scoped.
- **Cross-row locks/state:** Serialize geography reparent and ancestor/cycle changes on the real Foundation root lock before rechecking full ancestor paths. Branch department creation, link and ACTIVE to INACTIVE/CLOSED transitions share a fixed branch-row lock order and check current branch/department status in that transaction. Preserve history and prevent assignments on inactive/closed branches. CLOSED is not silently reopened; a future reopen rule needs approved change. For every submitted revision use immutable snapshot+digest, unique registration/revision, unique non-null CG-03 case ref, unique accepted decision effect and unique branch registration/code. Code generator may consume sequence gaps, never duplicate codes.
- **Constraints and links:** Genuine FK to existing CG-01 real accounts/realm and CG-02-owned parent/branch/department is allowed in the shared DB; never reference absent CG-04/05/09/10/14/18 tables. For officeholder participation, a partial unique active key under department/account/office_role prevents duplicate concurrent active assignments while retaining ended associations.
