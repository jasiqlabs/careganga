# CG-01 — Simplified Authentication: Product Owner Change Request (16 November 2026)

**FINAL ACCOUNT CREATION CLARIFICATION (owner 16 Nov 2026; greenfield):** The **first Foundation Super Admin** is provisioned **once by a protected operator-only script**, using unique mobile, optional email, name and password supplied securely at runtime. No public endpoint can bootstrap Super Admin. Thereafter the Super Admin (and administrators possessing explicitly granted `accounts.invite` + `roles.assign`) create **every user directly** in the original CareGanga **U03–U04 Add New Staff Account** drawer: **Full name + mobile (username) + optional email + initial password + chosen eligible role**. Account becomes **ACTIVE immediately**; no invitation, self-signup, authenticator setup or mobile/email verification. The user signs in using mobile/email + password. Super Admin may create users with **any permitted role**, subject to last-root, privilege-escalation and deliberately guarded sensitive-role rules. A user does **not self-register**, choose their own role or gain access from the public website's contact/join CTA. Later public member/patient application flows are separate domain flows and will not silently create elevated login. **Forgot Password alone requires real email OR SMS OTP** to a previously stored contact; no bypass on provider unavailability.

**Greenfield delivery directive (owner, 16 November 2026):** CareGanga has not been delivered to the client and has no functioning legacy deployment or users to migrate. **Backward compatibility (BWC), preserving unshipped TOTP/invitation contracts, and supporting legacy login are not requirements.** Implement one coherent clean-initial-database authentication solution, simplify/drop obsolete code and seed only genuine initial roles. Test on a new disposable PostgreSQL database; never imply existing data migrations, production runtime or completed QA. Security and permission enforcement remain mandatory.

## Owner decision (this supersedes the earlier complex all-staff authenticator UX)

The **same simple Admin-managed account creation, sign-in and recovery process** applies across every created role, including staff, volunteers, healthcare staff, managers, Finance and Super Admin. **There is no public self-registration** in this greenfield release. **No mobile OTP verification, email verification, authenticator enrollment, six-digit TOTP, or app-based MFA is mandatory for registration or routine login in this phase.** No role-based exception in login. Never bypass backend permissions or grant protected roles without authorization.

### Admin-created registration (no anonymous signup)

- **Minimum visible Admin form:** full name (to display the account), **mobile number**, password, **email (optional)**. The mobile number **is the username**; do not require an additional username field. If product UX retains an optional custom username in the future, it must be unique and cannot impersonate a mobile/email, but it is **not needed now**.
- Mobile validation: normalized Indian 10-digit number (as in BrickOps; if country support is later required, use E.164 in a separate scope). Unique per user in the single Foundation identity realm. Email, when given, is format-validated and unique after normalization, but **not verified** and must not be treated as ownership proof.
- User enters password once plus a show/hide control; a confirmation field may be present only if usability testing finds it necessary. Minimum password length at least eight characters with breached/common password rejection where practical; hash with existing secure credentials, never plaintext.
- Register transaction creates one real account, credential, audit row and safe status, **without** requiring OTP, email service, SMS provider, TOTP secret or future module tables. Handle repeated/double submit, duplicate phone/email, idempotency and concurrency.
- **Only an authorized Admin creates an account**, choosing a currently eligible role from the server. Account becomes ACTIVE immediately; no invitation or public registration. Protected Super Admin bootstrap is operator-script-only and protected-role grants follow CG-03 approval rules; nobody can self-assign staff, branch, clinical, finance or root authority.
- Initial Super Admin/root provisioning remains **operator-controlled**, not public self-registration; after creation, that account uses the **same mobile/password login UI**. Existing protected authority and last-root rules remain enforced.

### Login

- **One field:** `Mobile number or email` (or `Username / mobile / email` only if explicit separate username is implemented later).
- **One field:** `Password`.
- **No authenticator code input, enrollment/setup step, email OTP, mobile OTP or role-picker.** Same two-field form regardless of role in Admin Web, Internal Android, and public sign-in entry points when enabled.
- Backend normalizes and checks mobile/email, verifies password and active account, creates a revocable session and resolves **current** server-side roles/scopes before showing permitted menus. Invalid login returns a neutral failure; throttle credential stuffing and log only redacted events. Session revocation and role edits apply immediately on subsequent protected requests.
- Current code uses `SessionController.signIn` mandatory `totp`, `SessionService.signIn` and `verifySession` mandatory `mfa_verified_at`, `account.email_verified_at`, protected owner facade and numerous approval dependencies. **Do not remove UI fields without rewriting all server assumptions.** Migrate actual identifiers, session assurance and owner proof contracts consistently across CG-01, CG-03, CG-19, CG-21 and CG-02.

### Forgot password — email OTP or SMS OTP mandatory (latest owner decision)

- **Registration and normal sign-in do not require OTP, email verification, mobile verification, or authenticator MFA. The only required OTP in these everyday credential journeys is for Forgot Password.** This is an explicit exception to the no-OTP registration/login rule, not a reintroduction of mandatory MFA.
- **Single simple flow for every role, including Super Admin:** `Forgot Password?` -> enter registered mobile number or email -> request OTP to that account's matching contact via **SMS or email** -> enter one-time code -> set new password -> sign in with mobile/email + new password. If the account has both contacts, allow the user to select a supported destination without revealing a full contact value or exposing account existence to unauthenticated callers. If only one is stored, use that available configured channel. **At least one real provider-delivered OTP is required before reset.**
- **Email and SMS are alternative delivery channels**, not two required codes. Use a trusted SMTP/email service and SMS provider adapters; do not claim a code was sent if the provider is unavailable, and never display/reset with a locally generated code in the UI, logs or API. A neutral response should not reveal whether a username/mobile/email is registered.
- Generate a cryptographically random, short-lived OTP (e.g. 6 digits, expires in 10 minutes); store only a keyed hash/digest, bound to the account and password-reset purpose. Enforce attempt limits, expiry, replay prevention, rate limits per account/contact/IP, resend cooldown and a one-use atomic consume. On verified OTP + valid new password, change the credential, revoke existing sessions and increment the credential/account access version together with audit evidence.
- **There is no registration-stage contact proof**, so a registered address/number is initially unverified and may be mistyped, reassigned or controlled by someone else. A successful recovery OTP proves **current control of that reset destination**, not historic ownership. Protect high-risk accounts through independent admin notification, recovery audit, recent-contact-change lockout/controlled recovery or equivalent reviewed safeguards; never let an unauthenticated party update the destination inside recovery.
- If neither email nor SMS provider is configured, or delivery fails, show **recovery temporarily unavailable; contact support**, without bypassing OTP or creating an admin-generated plaintext-password shortcut. Support may assist through a separately audited secure identity process, but the normal Forgot Password route always requires a delivered email/SMS OTP.
- Implement this **once in CG-01** as the authoritative reset challenge flow for Admin Web, applicable public Web, Internal Android and Public Android. CG-19 may supply reusable *transport* only if it does not own the reset proof, OTP credential, challenge policy or security decision.
- Signed-in `Change password`: **current password + new password**, with permission/session validation; revoke old sessions upon success. No mandatory authenticator code for any role. Sensitive financial/approval actions may use fresh **current-password confirmation** plus separated approver permissions/dual control instead of authenticator codes; do not silently weaken existing CG-03/CG-21/CG-02 controls.
