Domain service composes narrow catalogue-policy, stock-ledger/transaction, purchase/receipt, transfer and expiry/disposition guards. Strategy/adapters only for genuinely distinct original owner interfaces; no generalized drug-order/dispensing workflow.

**Actual authenticated predecessors:** CG-01 current Foundation root/roles/capability and typed deployment flag; CG-14 real VERIFIED/PUBLISHED approved pharmacy center/location, provider association, legal readiness/current center assignment and `center_operational_capability(PHARMACY_ERP)`; CG-03's real review case/decision only where original protected approval required; CG-19's existing source-verified protected upload and notification APIs only as introduced by CG-22 purchase and alert stories. No imported peer CG-23/24 source.

**Capability predicates:** `cataloguePermitted(root,center,actor,operation)` requires a real CG-14 VERIFIED current pharmacy center and allowed CG-01 read/propose/review/current center association for private drafts; public publication additionally requires an independently CG-14 PUBLISHED center, but ignores global ERP stock toggle. Check independently for every side-effecting center and every private list/detail/selector/export/background job; for two-center transfer validate **both** current grants at reservation and completion. Backend OFF denies CG-22 operational endpoints including active stock/history/export and disables all pharmacy workers. Retain immutable rows and source events in PostgreSQL; original CG-21 canonical protected platform audit may expose only independently authorized minimal event metadata, never reopen the CG-22 operational API/exports while OFF. A controlled authorized later reactivation can reconcile retained source state. Public price catalog continues normally with OFF. A user interface toggle does not create an effective backend grant.

## 2. Canonical relational data design (single authoritative schema)

PostgreSQL uses immutable opaque internal UUID identities, UTC instants, explicit center-local calendar dates for expiry, integer base units for quantity, `BIGINT` paise for INR monetary fields and `revision BIGINT` compare-and-swap. Every private row has `root_id` referencing real CG-01 root and center/location scope where relevant. All own child tables enforce composite same-root and center identity FKs with parent `UNIQUE(root_id,id)` or `UNIQUE(root_id,center_id,id)`. Real cross-owner CG-14/01 FK only when its preceding schema exists; source facade additionally checks current status and rights. Status history is append-only; ordinary application never hard-deletes an accepted batch, price or stock effect.

| Canonical CG-22 table | Minimal state, keys, integrity and query path |
| --- | --- |
| `medicine_master` | `(root_id,id,normalized_product_code,display_name,generic_name,brand,strength,form,base_unit,pack_size_base_units,classification_ref_nullable,active,revision)`. `UNIQUE(root,normalized_product_code)`; validate normalized product, strength/form/unit and positive integral pack conversion. Alias/different pack must not silently collapse distinct actual SKU. No invented efficacy/controlled-drug dispensing rule from a name. |
| `center_medicine_price_revision` | `(root,id,center_id,medicine_id,revision,unit_basis,currency,mrp_minor,quoted_minor,discount_kind,discount_value,valid_from,valid_to,review_case_ref_nullable,approved_by,publication_state,source_digest)`. Same actual CG-14 center and medicine; MRP/quoted price must use the SAME exact pack/unit and source currency; nonnegative integer amounts and consistent deterministic fixed/percentage discount (do not store independent contradictory final prices). Immutable approved revision, protected review/author separation and version; one unambiguous approved ACTIVE effective window per root+center+medicine+unit_basis and policy precedence, enforced by exclusion range/guarded transaction + index, with safe end-exclusive `[from,to)`. |
| `pharmacy_batch` | `(root,id,center_id,medicine_id,manufacturer_or_marketer_ref,lot_normalized,expiry_date,manufacture_date_nullable,base_unit,condition_state,revision)`; `UNIQUE(root,center,medicine,manufacturer,lot,expiry)`. Expiry and medicine/pack identity cannot change after first verified receipt; current `ACTIVE/QUARANTINED/RECALLED` state and date-derived `EXPIRED` eligibility. Same lot transferred to other center creates/maps a **destination-scoped** batch identity with preserved original manufacturer+lot+expiry provenance. |
| `pharmacy_stock_movement` | Append-only `(root,id,center_id,batch_id,effect_kind,source_kind,source_ref,source_line_key,source_revision,effect_key,request_digest,base_unit_delta,related_transfer_ref_nullable,actor,created_at)`; UNIQUE `(root,center,source_kind,source_ref,source_line_key,effect_kind)` for one *actual immutable business event line* **and separate UNIQUE `(root,center,effect_key)` for transport idempotency**; matching replay returns original, changed request/source digest conflicts. For multiple partial receipts or reservation changes, create a distinct persisted original receipt/release event reference for each authorized event; do not reuse parent transfer/purchase key as the unique event identity. Effects: OPENING_RECEIPT, GRN_RECEIPT, MANUAL_CORRECTION, RESERVE, RELEASE_RESERVE, INTERNAL_ISSUE, SUPPLIER_RETURN, TRANSFER_DISPATCH, TRANSFER_RECEIVE, TRANSFER_RETURN, QUARANTINE_DISPOSITION only when supported. No generic user-editable movement. |
| `pharmacy_balance` | `(root,center,batch_id,on_hand_base_units,reserved_base_units,revision)` PK(root,center,batch), CHECK on_hand ≥0, reserved≥0, reserved≤on_hand; **physical_unreserved=on_hand-reserved**, while **issuable_available=physical_unreserved ONLY when current lot state is ACTIVE and expiry date is still eligible; otherwise issuable_available=0**. Quarantined/recalled/expired physical quantity remains recorded on_hand and is reported as unavailable/quarantined, never sellable. Every movement and balance change commits in one short transaction with batch/status guard first then scoped balance lock/conditional revision in globally consistent order; quarantine/recall transitions and issue/reserve serialize through that same guard. `ISSUE` decreases on_hand, and decreases reserved if it consumes an authentic reservation. No cached editable stock total. |
| `pharmacy_reservation` | `(root,center,batch_id,original_purpose,source_ref,quantity_base_units,state,expires_at_nullable,revision)`, unique real source key; only `RESERVED → ISSUED/RELEASED/EXPIRED_HOLD` under corresponding append-only movement, never a phantom patient cart or stock allocation to a nonexistent sale. Due release worker exists only when ERP ON and actual expiring reservations exist. |
| `pharmacy_supplier` | `(root,id,center_id,name,verified_supplier_license_ref_nullable,status,revision)`, real protected supplier evidence only in CG-19; center-private, not CG-12 Foundation supplier or CG-09 payee master. Supplier record does not itself demonstrate legally valid procurement. |
| `pharmacy_purchase` / `pharmacy_purchase_line` | `(root,center,purchase_ref,supplier_ref,invoice_evidence_ref_nullable,state,revision)` plus `(root,purchase_ref,line_ref,medicine_ref,ordered_base_units,unit_cost_minor,currency,accepted_base_units)`. One scoped purchase with many lines and real user authorization/optional CG-03 source approval; no automatic Foundation journal. Accepted means stock receipt proof, not supplier paid. |
| `pharmacy_grn` / `pharmacy_grn_line` | `(root,center,grn_ref,purchase_ref,source_invoice_ref_nullable,state,revision)` and immutable `(root,grn_ref,line_ref,purchase_line_ref,batch_ref,accepted_base_units,rejected_base_units,effect_ref)`. Idempotent one GRN line→one actual GRN_RECEIPT and aggregate `accepted≤ordered` under short locked original purchase line (allow explicitly approved excess correction only as separately reviewed version). No phantom stock from document upload. |
| `pharmacy_transfer` / `pharmacy_transfer_line` | `(root,provider_org_ref,source_center,destination_center,transfer_ref,status,revision,dispatched_at,received_at)` + `(root,transfer_ref,line_ref,source_batch_ref,destination_batch_ref_nullable,dispatch_base_units,cumulative_received_base_units,cumulative_returned_base_units,cumulative_loss_base_units,source_dispatch_effect_ref)`. Actual destination receipts and return/loss are **separate immutable per-event child records**, not one destination_effect_ref column (which could not represent multiple legitimate partial receipts). Same CG-14 legal provider with two approved distinct center locations; `received+returned+loss≤dispatched` under row lock/CAS, residual IN_TRANSIT until verified. No instant destination stock on dispatch, no cross-partner transfer by assumed same Foundation root. |
| `pharmacy_transfer_resolution_event` | `(root,transfer_ref,line_ref,event_ref,event_kind,quantity_base_units,source_center,destination_center,source_or_dest_batch_ref,movement_effect_ref,request_digest,actor,at)`; UNIQUE(root,transfer_ref,line_ref,event_ref,event_kind) for each genuinely authorized RECEIVE/RETURN/VERIFIED_LOSS. Multi-partial acceptance produces multiple distinct child receipt events and immutable stock movement keys while one transfer line maintains bounded cumulative totals; original repeated callback returns one event, changed digest conflicts. |
| `pharmacy_batch_status_event` | `(root,center,batch_id,event_key,from_state,to_state,reason,protected_evidence_ref_nullable,actor,approved_by_nullable,revision,at)`; UNIQUE(root,batch,event_key). Persist authorized QUARANTINE/RECALL/RELEASE with actual reason/evidence and optional independent reviewer; current batch state pointer updated under one transaction. No ordinary release of expired/recalled lot without actual lawful clearance and qualified role. |
| `pharmacy_due_alert` (only if genuine alert delivery is enabled) | `(root,center,batch_ref,alert_kind,due_at,threshold_version,source_key,status,attempt_count,next_retry_at,lease_until,original_cg19_notification_ref_nullable)`; UNIQUE source key/threshold period prevents repeat low-stock/near-expiry notifications. No always-on per-center counters, speculative additional queue infrastructure or duplicate CG-19 outbox. |

**Canonical names are authoritative**: do not create alternatives `medicine_prices`, `supplier_invoice`, `pharmacy_stock_transactions`, `stock_ledger` or `center_inventory` as competing sources. Query indexes are selective `(root,center,medicine,status/date)`, price active/effective lookup, lot+expiry, movement `(root,center,batch,created_at DESC,id)`, supplier/purchase current state, due alerts partial `(next_retry_at,id)` and transfer `(root,source/dest,status,updated_at)`. Never index every JSON/field. Use cursor+limit, safe sortable fields, per-query budget and owner cost telemetry. Test real scope, locks, backup/restore/rollback and EXPLAIN (read-only on representative DB) under appropriate non-superuser role before operational activation; `NOT_RUN`.

## 3. Story-level backend/API and transaction acceptance

### US-001 — Published medicine catalogue, reviewed partner price, public enquiry; ERP OFF independently

**Admin/Center API target:** `GET /api/v1/pharmacy/catalog?center&query&cursor&limit`; `POST /api/v1/pharmacy/catalog`, `PATCH /catalog/:ref` protected; `POST /prices/drafts`, `POST /prices/:ref/submit-review`, `POST /prices/:ref/approve|return|withdraw`, `GET /prices/history`. Current version/CAS/idempotency; actual CG-01 Foundation catalogue editor vs own CG-14 pharmacy staff price proposer/reviewer actions. For a configured independent multi-stage approval, CG-22 introduces a **genuine PHARMACY_PRICE_REVISION** source adapter/process into original CG-03, pins original revision/digest and then performs guarded CG-22 finalizer, never writes CG-03 case tables directly or trusts client `approved=true`. Reject proposer self-approval when policy requires separation; an otherwise authorized root reviewer must have a real current distinct action. No approval may publish stale revision, suspended center, withdrawn medicine, invalid unit/tax/discount or overlapping effective rule.

**Public source:** `GET /api/v1/public/pharmacies/:centerRef/medicines` returns ONLY actual CG-14 PUBLISHED/VERIFIED eligible pharmacy and CG-22 approved effective safe normalized name, form/pack, MRP/quoted price and validity/availability-of-information disclaimer, never actual stock, batch, supply promise, controlled prescription, personalized CG-17 grant, hidden private pharmacy contact or unmatched price. Safe HTML Next.js and native Public Android parity; source invalidation on center revoke or price withdrawal. Public enquiry uses existing legitimate CG-14 contact or CG-19 support if an actual permitted workflow exists; CG-22 does not create a second helpdesk. H12 price history and own-center current quote work with all ERP flags OFF and no CG-15 patient, CG-17 settlement or CG-20 reports.

### US-002 — Initial batch receipt and guarded stock movement; ERP ON

**API:** `POST /api/v1/pharmacy/opening-stock`, `POST /batches`, `GET /stock`, `GET /batches/:ref/history`, `POST /stock/reserve`, `POST /stock/release`, `POST /stock/issue-internal`, `POST /stock/adjustment-request`, `POST /stock/adjustments/:ref/approve`. Opening stock requires verified named provenance/evidence/authorized adjustment approval, not a fabricated supplier/GRN record that belongs in US-003. One original deterministic source_key+line+effect payload digest binds each receipt/reserve/adjust/issue. Validate CG-14 root+center grant and qualified accountable stock operator; both `balance` and `movement` update atomically under short lock. Pack quantity converts to **positive integral base units** before lock; no arbitrary float or unit-mismatch sum. An `INTERNAL_ISSUE` is a reason-coded stock-out, not sale/prescription/patient charge; if dispensing/patient supply is not separately approved, disable those actions even if H11 shows an issue button. Expired/recalled/quarantined batches never count as issuable. While ERP OFF all CG-22 stock/history operational endpoints remain denied; only original separately-authorized CG-21 audit metadata is available, no CG-22 history export until controlled reactivation.

### US-003 — Partner supplier, purchase and genuine partial receipt/GRN; ERP ON

**API:** `GET/POST /api/v1/pharmacy/suppliers`, `POST /purchases`, `POST /purchases/:ref/submit|approve|cancel`, `POST /grns`, `POST /grns/:ref/accept|reject`, `GET /purchases/:ref/history`. Authorize and freeze purchase source (supplier/license/evidence where required), currency and each line, real active provider center and optional CG-03 approval. Where scanned bill/proof is needed, US-003 registers **CG-22 purchase/GRN adapter in original CG-19 owner** and verifies its original protected file; no CG-22 file bytes. GRN acceptance locks purchase lines in sorted order and applies one `GRN_RECEIPT` movement per accepted line, with summed prior accepted quantity + new ≤ currently approved order. Duplicate/late GRN or return uses original line/effect key and cannot increment twice; source owner handles pending/unknown provider/file state safely. Partner purchase value is local cost evidence only, **not** CG-09 Foundation payable or CG-17 patient payable. Original CG-12 supplier and store still operate unaffected.

### US-004 — Two-center transfer and transit reconciliation; ERP ON

**API:** `POST /api/v1/pharmacy/transfers`, `POST /transfers/:ref/dispatch`, `POST /transfers/:ref/receive`, `POST /transfers/:ref/return|loss-review|reconcile`, `GET /transfers?center&status`. For each source/destination candidate use real CG-14 org+approved location and separate current PHARMACY_ERP grant, source custodian vs destination receiver auth, exact source lot/quantity and trustable original transport proof where required. Source inventory decrements only upon actual `DISPATCHED`, with one original movement and transfer in-transit liability; destination inventory increments **only for each separately verified RECEIVE event** with matching same lot/expiry and its own uniquely keyed `pharmacy_transfer_resolution_event` + `TRANSFER_RECEIVE` movement, not when merely created or pending. A partial receive leaves residual transit and is append-only per-event; refused/returned/verified lost quantity is resolved by a separate authorized immutable resolution event and corresponding source effect, never silently credited back or recognized as patient delivery. Concurrent receive/cancel/loss race uses one line CAS/row lock and enforced sum bound; sorted center/batch lock ordering avoids deadlock. When global OFF mid-transit, preserve unresolved history and deny new active commands; only controlled reactivation/reconciliation after real grant and authorization. No cross-provider stock merge or CG-12 movement.

### US-005 — Expiry/recall/quarantine and truthful reports/alerts; ERP ON

**API:** `POST /api/v1/pharmacy/batches/:ref/quarantine`, `POST .../recall`, `POST .../release-review`, `GET /reports/stock-aging`, `GET /reports/low-stock`, `GET /reports/near-expiry`, `GET /batches/:ref/status-history`. A real `RECALLED`, `QUARANTINED` or date-expired batch must be denied on the same original stock service at last-unit issue and transfer, **not just hidden by UI/reports**. Show on-hand/held/unavailable/available separately and calculate from original movement + current date/status; no screenshot mock KPIs. Recall of manufacturer+lot affects all actual scoped batches/sites through a bounded authorized investigation, without unbounded all-tenant auto-sweep. Release requires correct original reason, clear legal/professional evidence and independent reviewer if policy; expiry is not re-enabled by a normal release. Alert only actual eligible due events in indexed table and exact original CG-19 notification/outbox source; absent provider remains `PENDING/UNAVAILABLE`, never SENT. No loops that enumerate tenants/sites/medicine stock while OFF or no due alerts. Native Internal Android where original Foundation role has reporting permission shows safe summary, not partner stock editor. CG-20 may later consume controlled source aggregates without becoming mandatory first owner.
