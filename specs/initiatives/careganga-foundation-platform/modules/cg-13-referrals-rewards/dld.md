# CG-13 — DLD: Verified Referral, Points Ledger, Ranks and Rewards

**Authoritative sources:** [module](module.md), [UIUX B11–B16](uiux.md), [60 QA tasks](tasks.md), CG-13-BR01–08, FR-039–041/A-13, original [Admin screenshot audit B11–B16](../../../../../docs/research/CAREGANGA-ADMIN-PANEL-SCREENSHOT-UIUX-AUDIT.md), D-15/D-17. Original exact six source PNGs (2400×1440) inspected from SHA256-verified ZIP on 15 Nov 2026. **CRITICAL source design only**: actual qualified independent DB/privacy/stock review, SQL migrations+rollback, code/run, source-to-rendered pixel/motion comparison, Web/native/Play/worker load **NOT_RUN**.

## 1. Single business owner, source prerequisites and design patterns

**Canonical implementation:** extend the single CG-01 NestJS modular monolith/Next.js admin + public Web/native Public Android/Internal Android and one PostgreSQL migration tree. Use current real CG-01 root/role/session, optional current CG-02 Foundation branch, real CG-04 member/volunteer identity+membership/volunteer approval event, real CG-12 stock if **PHYSICAL** selected, genuine CG-03 case only when policy requires, real CG-19 file/notification if supported. No stock, accounting, gift-card-provider, membership, CG-18 CMS or CG-20 MIS tables created here.

**No premature sources:** US-001 programme/ranks and DIGITAL product require only CG-01/02, no actual member/CG-04 qualified event/CG-12/CG-09/CG-18. US-001 PHYSICAL mapping requires current CG-12 approved active item/location **only when chosen**. US-002 requires active US-001 policy and actual CG-04 verified eligible owner/outcome; no reward fulfillment prerequisite. US-003 DIGITAL reward requires true US-001/002 wallet and approved digital fulfillment method; neither CG-12 nor CG-09 is required. US-003 PHYSICAL requires current CG-12 reserve/issue/return and optionally a current CG-03 reviewer decision. CG-19 protected image/recognition file only when the selected reward promises a delivered document; if file provider not ready, show UNAVAILABLE not a fake entitlement. Source-private CG-12 supplier contacts never flow to product cards.

**Patterns:** small typed `ReferralQualificationPolicy` (actual programme-specific allowed CG-04 event and referrer eligibility), guarded `PointsAccount` ledger+balance, `RewardFulfillmentKind` with only DIGITAL proof vs PHYSICAL original-stock adapter, and narrow CG-04/03/12/19 facades. Existing same-DB short Unit of Work for CG-13+CG-12 reservation/point holds when typed CG-12 transaction facade supports it; otherwise one durable reconciliation state+source-key, never simultaneous direct repositories or universal Saga broker. No payment/gift card engine, automation DSL, extra service or second finance/wallet ledger.

## 3. US-001 — Settings/ranks/catalog source and APIs

Admin Web B11 rank/cards + B13 side drawer: `GET/POST/PATCH /api/v1/rewards/programmes`, `POST /programmes/:ref/activate-policy`, `GET/POST/PATCH /programmes/:ref/ranks`, `GET/POST/PATCH /rewards/products`, `GET /rewards/stock-options?programme=...&kind=PHYSICAL`. Actual role grants `rewards.programme.manage`, `rewards.catalog.manage`, `rewards.stock-option.view` separate, current root/CG-02 scope. Changes use expected revision and narrow CG-03 approval only when authorized policy requires. Settings B13 conversion is a **display conversion** with explicit noncash legend; a rank threshold must have deterministic single next level even after manual rank names/order changed. `min_redeem_points` and price >0, no auto expiry. Award/benefits activation pins version and effective date, concurrent modification conflicts rather than retroactive points/history changes.

**Original B14–B16 product UI:** public catalog `GET /api/v1/rewards/catalog` returns eligible active DIGITAL first, and PHYSICAL only when CG-12 permits an authoritative availability view. B16 screenshot's editable *Stock Units* is **not a CG-13 warehouse mutation**: physical maps actual CG-12 item/store and displays guarded available stock read-only; no selected stock, no physical publication/fulfillment, but digital catalog stays functional. Product images require CG-19 original safe file source or explicitly allowed HTTPS host with SSRF/sanitized proxy review; never accept arbitrary internal URL or expose private object keys. Deactivate/price edit after submission doesn't change pinned redemption cost; no retroactive financial postings/point expiry from UI toggle.

## 4. US-002 — Referral code, genuine qualification, points and ranks

**Capture flow:** existing CG-04 member/volunteer application fields already accept referral input. CG-13 introduces `CG13.validateReferralForApplication(root,programme,applicantAccountOrProtectedIdentity,sourceApplicationRevision,code,actor)` as a typed original **CG-04 application adapter**, resolving only safe active code/relationship, and freeze attribution on **committed CG-04 application submission**. An applicant clicking three links does not overwrite an accepted submission; one CG-04 application may only have one current attributed referrer per permitted program. A parent/child/self/duplicate applicant or same CG-01 account/relation cannot refer itself; circular chain/registered conversion loops and proxy accounts investigated under safeguarded configured policy without automatically exposing PII or presuming identity links not verified. No guaranteed points for anonymous share/click.

**Qualification:** `CG04.readCommittedReferralQualifyingEvent(root,applicationRef,eventRef,actor)`: actual member ACTIVE only after matching CG-03 approval and CG-09 verified join fee if applicable (or approved zero fee); volunteer ACTIVE only from genuine CG-04 approval; delayed/unknown remains PENDING. CG-13 uses original event/policy version to decide one winner per `root,programme,qualifyingApplicantIdentity,eventKind`, guarded by source idempotency and locked existing attribution/account, applying exactly one positive `points_event(QUALIFICATION)`. A changed source event digest conflicts rather than silently relabels. Paid membership renewal gives no second signup referral award by default; both volunteer and member under one account cannot earn two awards for the same applicant/outcome unless a *separate expressly approved policy* clearly distinguishes events.

**Reversal:** a genuine CG-04 verified invalidation/rejection/refund/eligibility correction emits source-owned durable negative compensating `points_event(QUALIFICATION_REVERSAL)` exactly once. If spend has already occurred, do not make `available<0` or silently claw back a delivered reward: set **REVIEW_REQUIRED_NEGATIVE_ADJUSTMENT** and bound future eligible credits/approved adjustment against original points account; refer to actual fraudulent issuance/return policies and record debt visibility privately for authorized staff. Never invent a CG-09 money debt. Rank snapshot/requalification uses versioned policy with signed source adjustment; no retroactive changes to closed original rank event. CG-04 applicant/referrer private records never appear in public ranked tables.

**Self-service APIs:** `GET /api/v1/referrals/my-code`, `GET /referrals/my-history`, `GET /points/my-balance`, `GET /rewards/my-rank`, private `GET /referrals/admin`, `GET /referrals/leaderboard` (Foundation Admin scope or opt-in pseudonymous public), `POST /referrals/resolve` rate-limited non-enumerating code validation. Access to a verified relationship uses actual CG-01 linked account and CG-04 current status/branch/purpose. Source qualification is consumed via a signed typed server-to-server facade/due-scoped source event read, not a public client-provided 'qualified=true'. If callback is lost, recover bounded committed CG-04 source events with advancing checkpoint; no idle scan of all members/volunteers.

## 5. US-003 — Points reservation, original stock issue, recipient fulfillment and compensation

**Requests and states:** member/volunteer Public Web/Public Android `POST /api/v1/rewards/redemptions` with eligible programme product, expected account/product revision and immutable idempotency. Revalidate actual CG-04 current eligible relationship, active CG-13 reward policy, allowed audience, price, current source availability and `availablePoints`. In one short PostgreSQL transaction acquire points-account lock and (for PHYSICAL) invoke **typed CG-12 store/last-unit hold source under same Unit of Work** if implemented. Accept only if enough points and real stock. Store immutable price/owner/product digest, make one `POINTS_HOLD` ledger event+projection and one original CG-12 reservation, or remain `PENDING_RESERVATION` if cross-owner reply unknown; losing concurrent claimant releases/never holds points and never reports success. Digital skip CG-12 entirely.

**Approval and fulfillment:** optional CG-03 `REWARD_REDEMPTION_REVIEW` case with frozen redemption source/revision (not self-approved); `POST /redemptions/:ref/submit-review|approve|reject` verifies actual current CG-03 decision before owner effect. DIGITAL: approved in-product recognition/CG-19 valid current certificate or authorized manual claim evidence, whose real delivery source exists, becomes `FULFILLED`; do not fabricate voucher numbers or external credit. PHYSICAL: `CG12.issueHeldReward(root,holdRef,sourceOwner=CG13,sourceKey,actor)` authentic original `CONFIRMED_ISSUE` → `ISSUED_AWAITING_HANDOVER`; separately authorized recipient/witness acknowledgement under current CG-13 scope → `FULFILLED`; two different original effects, no completion from worker dispatch alone. Exactly once `POINTS_SPENT` consumes previously held available points when fulfilled; no second negative wallet movement on duplicate ack. `GET /redemptions/my-history` and scoped `GET /redemptions/admin`, `POST /redemptions/:ref/record-handover|cancel|confirm-return` only when permitted; do not let clients set stock-issued or fulfilled boolean.

**Cancellation/return:** before issue, atomically release `POINTS_HOLD` and real CG-12 reservation, append one `CANCELLED` source; after physical issue, require original CG-12 **confirmed RETURN** or current policy-defined independently approved exception before releasing points or publishing restored physical stock. A return of damaged/nonrestockable item follows CG-12 original adjustment policy; CG-13 cannot increase stock. Duplicate cancellation/refund/return with same source key returns previous original effect; approved partial policy applies only when genuinely supported SKU unit and actual quantity, not screen-implied shipping. If digital gift proof cannot be delivered, remain `FULFILLMENT_PENDING/UNAVAILABLE` with bounded due-key recovery. Reversal after terminal FULFILLED needs exact linked corrective points source with checks against prior grant/spend and immutable audit, not deleting a redemption.

**Money boundary:** B13 `points_to_inr_display_ratio` may be shown as *indicative reference value*, with no bank/gift-card liability, no CG-09 payable and no equivalent cash checkout. If an explicitly client-approved cash/gift-card settlement later becomes real, only then create a separate authorized `CG09.submitApprovedRewardPayment(original redemption/source key)` adapter and reconcile true verified CG-09 disbursement; **not required** for first working digital/manual reward or physical reward, and no automatic entitlement-to-cash conversion.

## 6. Security, real channels, export, recovery and QA

**Original admin UI:** B11/B12 real seven sample rank labels as configured (never hard-coded immutable), member/volunteer tabs/filters, approved summary and source history; B13 Settings policy validation and effective versions; B14/B15 active digital/real physical catalog and source-safe price/availability; B16 side drawer. **Public Web and Public Android** provide same authenticated CG-04 relationship's code/share, my points/rank/history, eligible public catalog, redemption/own history and accessible retry. **Internal Android** only roles authorized for redemption review/stock field handover, with same actual eligible Web approval/fulfillment actions/options; full programme settings/catalog editing stays Admin Web under D-17. No health center/patient views, raw CG-12 store/supplier or anonymous named leaderboard.

**Authorization:** CG-01 actual principal and scope/version + CG-04 eligible member/volunteer relation + CG-02 branch if active on every protected list, detail, option, write, ledger, redemption, file/export and reviewer action; CG-12 original item/location authorization for stock; CG-03 actual reviewer for approvals, CG-19 original file for gift evidence. Anonymous public code resolve limited to nonidentifying programme label/status. Site is not allowed to parse QR/code as identity token. Public leaderboard only approved/opt-in pseudonymous rank and coarse totals, suppress sensitive cohorts. No points/bank/private-address/person PII in logs/notifications/error details. Rate-limit referral-code resolution, spam, self-referral attempts, public catalogs and export. The original CG-21 audit feed consumes redacted CG-13 source events only, no second platform audit.

**Failure/worker recovery:** guarded state+ledger tx and original owner effect key, `UNKNOWN_WRITE_STATUS` on uncertain CG-12 issue or handover; re-query the SAME source key before new action. Bounded due-index claim/lease + finite attempts for actual unresolved redemption/source-event integration; no full-root scans, zero queued jobs means no provider calls and no high-frequency per-tenant background timers. Exact read-after-write report projection with consistent root+period+policy version, keyset cursor and one-person attribution. Crash between CG-04 committed qualification and CG-13 credit recovered from original monotonic event checkpoint or actual existing owner outbox, never ad hoc full application import. Runtime SQL/race/backup/restore/network bytes/p95/negative balances/Android Play source-to-pixel tests **NOT_RUN**; validate at independent QA stage.

**Design alternatives rejected:** A second reward warehouse, plain mutable `wallet_balance` without event proof, generic blockchain/token currency, automatic INR cash payout, premature universal broker/Saga, duplicate CG-04 relationships, hand-coded fake inventory numbers and hard-coded ranks. Current HLD root isolation/one transaction engine and D-15 verified-only points win.
