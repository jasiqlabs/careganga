## 1. Single owner and independently delivered workflow

**CG-13 owns** programme and rank policy/version; eligible member-or-volunteer programme participation (no second person/account master); opaque referral code/short link attribution; qualification outcome and source-key; one **append-only points transaction ledger** with **single guarded balance projection** (not a second ledger); rank calculation/snapshot history; physical/digital reward product master with points price, artwork/active state and **optional real CG-12 item reference**; redemption/point hold/compensating events/fulfillment evidence; restricted B11–B16 operational summaries, referral/rewards history and safe leaderboard.

**CG-04 owns** genuine active member/volunteer relationship and application/paid-approval eligibility; membership/volunteer application referral input remains CG-04 source-owned. CG-13 US-002 introduces the **typed CG-13 referral validation + frozen attribution adapter into the real already-built CG-04 application action** and consumes only its committed verified qualifying/return/refund/inactivation source events. An anonymous link click or submitted/rejected application never earns points. No CG-13 duplicate applicant/member/volunteer record, fee history or welcome ID. A CG-01 principal may have both CG-04 relationship types: points participation is explicitly programme+eligible relationship scoped, but **the same qualifying applicant event must never credit both roles or multiple referrers**. No automatic wallet merging/cross-type spending.

**CG-12 owns** actual item, store, on-hand/reserved/available quantity and immutable original stock hold/ISSUE/RETURN. CG-13 US-001 may optionally map *one physical reward* to current CG-12 ACTIVE item/store through an authorized read facade; digital product and programme/rank setup run **with zero physical stock**. CG-13 US-003 introduces typed same-root source-keyed CG-12 reserve/issue/release/return on actual physical redemption only. Stock hold is neither physical issue nor recipient handover: show `HELD`, `ISSUED_AWAITING_HANDOVER`, `FULFILLED` separately. CG-13 never sets `stock_balance`, stores editable stock units or sells a CG-12 item.

**CG-03 owns** real approval cases and decisions when a configured reward/exception review needs independent authorization; CG-13 US-003 registers `REWARD_REDEMPTION_REVIEW` source/revision/digest only upon genuine submission, not in CG-03 initial migration. CG-19 owns protected reward artwork/proof/certificate/notification files and actual configured messaging; no CG-13 file store or invented delivery provider. CG-09 remains the only financial owner **only when** a genuine separately approved monetary cash/bank liability/payment is introduced: B13's points-to-INR conversion is a policy display/threshold, **not** a cash balance, automatically payable INR, gift-card code, CG-09 journal or legal tax treatment. Basic **DIGITAL** recognition/approved manual entitlement must work without CG-09, CG-12, gift-card provider or any future owner. CG-18 publishes optional editorial reward placement only when approved; CG-20 future centralized MIS isn't required for B11/B12/B14 native source reports. CG-21 reads current redacted event audit; no parallel platform audit.

## 2. Three source-complete vertical stories

### US-001 — Configure referral programme/ranks and real digital/physical reward catalog

Authorized Foundation programme manager uses original B11 overview/rank cards/B13 settings and B14–B16 Rewards Store/Add Product; creates versioned active rules (qualifying CG-04 event, points awarded, effective date, optional display INR conversion, minimum claim, optional rank auto-upgrade; **no automatic expiry by default** under D-15) and ordered non-overlapping named rank thresholds/benefits. Configure actual DIGITAL reward (no stock prerequisite), and optionally PHYSICAL reward selecting genuinely accessible CG-12 ACTIVE item/store with a **read-only live available amount** (B16 illustrated “stock units” cannot mutate stock). Snapshot price/category/artwork/public visibility, optional marketplace eligibility by CG-04 relation; old accepted redemption retains its original price/rule. B11/12 Admin Web + native/public safely see only authorized active programme/catalog source. **20 planned manual QA cases**. Starting dependencies: actual CG-01 current Foundation root/role and genuine CG-02 scope if configured; CG-12 needed **only** for real PHYSICAL product mapping, CG-04 not needed to create rules/catalog.

### US-002 — Register and qualify authentic referral; award/reverse points, calculate ranks and scoped history

Eligible existing CG-04 member/volunteer with actual linked CG-01 principal gets an opaque bounded referral code/link and shares it without exposing applicant/referrer private ID. Applicant applies through genuine CG-04 member/volunteer form (already has referral input); CG-13 validated immutable attribution source is pinned **at first actual eligible accepted CG-04 application submission** under configured attribution policy. Multiple clicks don't reassign a submitted applicant; self/circular, foreign-root, repeat qualified outcome and stale source never earn twice. One current eligible CG-04 verified **qualifying event** (active approved membership with genuinely verified required fee/valid zero fee; or approved active volunteer) credits one immutable event to eligible configured programme wallet; rejection/refund/reversal adds one linked compensating negative event, never deletes history. Rank and eligible own balance/history/leaderboard derive ledger and versioned thresholds. No CG-12 product/hold, CG-09 cash payout, CG-18 or CG-20 dependency. Public Web + **Public Android** own-referral/points/rank/history parity; Foundation Admin B11/B12 scoped fraud review and summary; Internal Android may show only roles actually granted referral reviewer actions, no full config. **20 planned QA**; US-001 real approved programme config + actual CG-04 source required.

### US-003 — Safely redeem, approve, fulfill, return and report real rewards

Eligible current CG-04 member/volunteer redeems a current permitted CG-13 product using one guarded **points hold**, and (if physical) a **CG-12 actual reserved stock hold** atomically in the existing modular monolith where supported, or durable source-key reconciliation with truthful `PENDING_RESERVATION`. CG-03 configured review never self-approves or changes the pinned points price. DIGITAL recognition becomes `FULFILLED` only on actual authorized CG-13 entitlement/CG-19-issued document/manual delivery proof—**never fabricate a voucher code/third-party promise or CG-09 money**. PHYSICAL starts `HELD`, then one real CG-12 `CONFIRMED_ISSUE`, then authenticated recipient handover/evidence `FULFILLED`; issue-to-field-worker alone is not recipient delivery. Terminal earned-spend points debit occurs exactly once on genuine fulfillment; pending holds reduce **available**, not lifetime earned or permanently redeemed. Cancel before fulfillment releases CG-13 hold and original CG-12 hold; after issued item, compensating refund/restock follows actual CG-12 authorized return and one linked ledger correction (no blind stock restoration). Same-ref replay and two redemptions racing one item or insufficient points never overspend or duplicate events. Admin B14–B16 catalog/member/volunteer redemptions and authorized Internal Android fulfillment have action parity; eligible public Web/Public Android self-service and genuine status/history/leaderboard reports, with privacy-safe unknown states. First DIGITAL redemption works without physical stock or CG-09 monetary provider. **20 planned QA**; US-001 and US-002 current real programme+eligible wallet required (genuine ledger balance can also derive from an explicitly policy-authorized true original positive event, never developer seed).
