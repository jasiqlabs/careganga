## Canonical source, authorization and data ownership

CG-19 owns protected file metadata/object keys, versioned templates, one source-linked issued-document authority, notice/delivery history/outbox and scoped Foundation support tickets. Existing CG-01/CG-03 are the **only first real file/document/event sources**. **CG-19 US-001 delivers actual protected case-file upload/validate/restricted reviewer-preview through a permissioned CG-03-case source adapter** (real CG-03 case, actual source revision, bounded file version/checksum, authorized reviewer). CG-03 owns any subsequent document-level approval decision, never CG-19; no prior CG-03 initial delivery depends on CG-19, and CG-19 must not create a duplicate case/reviewer-step table; CG-02 later integrates actual branch-registration evidence, while CG-04/09/10/14/15/16 introduce real member/receipt/staff/medical outputs and center support. CG-19 validates source/action/record scope via typed owner facades, not trusting an arbitrary `owner_type` or writing future owners' records. One NestJS module and existing shared PostgreSQL; do not invent an independent microservice, duplicate approval engine, general event framework or external queue.

## Actual first-release typed owner contracts and pattern decisions

**Existing owners only:** typed CG-01 `authorizeCurrentAccess(action,realRoot,resourceScope)`, CG-03 `getApprovedCaseSource(caseRef,expectedRevision)` and `getCommittedCaseDecision(eventKey)` are authorized source facades, not direct imports of CG-01/03 repositories. CG-19 validates actual current actor before **every** read, upload URL, scan, download, issue, recipient list, notice and ticket export. Initial support visitor has no CG-01 login and uses isolated public submission/opaque receipt guards; a center ticket is **not** a first-release API.

**Concrete protected API (NestJS under existing apps/backend):** `POST /api/documents/files/initiate` with `{owner:"CG-01"|"CG-03",realSourceRef,sourceRevision,classification,mime,size,uploadKey}` returns only bounded authorized upload intent; `POST /api/documents/files/:fileRef/confirm` verifies object bytes/hash/size and required scan state before giving VALIDATED, `GET /api/documents/files/:ref/download` issues short-lived current-scope bound private access, and `POST /api/documents/issues` accepts `{caseRef,approvedSourceRevision,templateVersion,issuanceKey}`, requires confirmed CG-01 owner effect, creates one PDF source item and audited issue status. `GET /api/documents/issues/:ref` is permissioned; public verification is **not** enabled for private access letters. All status reads use returned safe business references/labels, never raw object keys or signed URL in logs.

**Communication API and delivery event:** `POST /api/communications/notifications` accepts allow-listed template/channel, actually existing CG-01 recipient/audience, event source ref/digest, priority/expiry, immutable idempotencyKey. A real committed CG-03 decision is consumed **only after source commit** through an authorized source-event query/hint; CG-19 itself owns the outbox insertion+unique dedup, and the introducing integration adds a narrow after-commit event adapter to CG-03 if it does not already exist. If a source callback is lost, reconcile by original source event key, not synthetic new event. CG-21 exposes only optional provider refs/readiness; CG-19 is the only provider sender and delivery attempt/history owner. `GET /api/communications/notifications/:ref/status` differentiates QUEUED / PROVIDER_UNAVAILABLE / SENT_TO_PROVIDER / DELIVERED_IF_CONFIRMED / FAILED / EXPIRED. `POST /api/communications/notices` creates owned draft/approved/expired bulletin with actual audience snapshot and optional scheduled send; CG-18 later renders a **public-safe published projection** only after actual authorized website publication, not a second notice master.

**Foundation support API:** `POST /api/support/public/contact` takes small validated name/contact/topic/body and client request key, rate-limits against abuse without optional CAPTCHA/provider, creates one private CG-19 case and returns only opaque receipt/reference. `GET /api/support/receipt/:token` returns minimal protected status only after proof; Foundation Admin `GET /api/support/cases`, `POST /api/support/cases/:ref/reply`, `PATCH /api/support/cases/:ref/status` require current CG-01 support permissions and actual root scope, revision/CAS and audited append-only replies. CG-18 later **presents** this endpoint from public contact page; no CG-18 contact-message storage. CG-14 later adds center-scoped selection/access through an explicit owner facade and CG-19 ticket source, not a CG-14 ticket table.

## Concrete file, template, delivery and support design

`stored_file(id,owner_type,owner_ref,classification,object_key,checksum,mime,size_bytes,scan_status,created_by,created_at,revoked_at)` records only **verified** CG-01/03 source references initially; `owner_type` uses an allow-listed implemented owner adapter, not unchecked strings. Authorize the original source before issuing limited upload permission, bound content type/size; verify actual object creation, size/checksum and server-side media validation/required malware scan before marking `VALIDATED`. Unknown/rejected/expired upload never returns an accepted file ref; orphan objects receive bounded eligible cleanup, not full tenant scans. Restrict private objects with nonpublic storage keys and short-lived source-authorized signed downloads; audit sensitive read/exports, never expose raw keys, live signed URLs or identity files through public QR. CG-02 adds genuine branch ownership only when its source is delivered, without a speculative CG-02 DB FK today.

`document_template(id,type,version,allowed_fields,approved_by,status)` and `generated_document(id,root_realm_ref,source_owner,source_ref,source_revision,template_id,template_version,issuance_key,object_ref,checksum,status,issued_by,issued_at,revoked_at)` project **genuine CG-01/03 account/final approved-access case** evidence first, via a **private approved access-change confirmation letter** with safe allow-listed fields and an actual CG-03 approved case + CG-01 verified owner outcome. An unfinalized CG-03 approval cannot be documented as a confirmed CG-01 grant. `UNIQUE(source_owner,source_ref,source_revision,template_id,template_version,issuance_key)` enforces one accepted issuance per idempotent request; reissue/revocation creates audited history, not silently edited old file. **Initial private CG-01/03 letter uses no unauthenticated public QR lookup**. A QR for private evidence resolves only through a currently permitted signed-in owner verification path; public QR verification for *later explicitly approved publicly verifiable document types* may expose only minimal type/validity and never personal/account/medical details. A generated object is not issued before verified real storage and owner authorization. Later CG-04/09/10/15 source owners introduce document/card/receipt/appointment templates once real data exists; do not create mock ID-card/financial receipt masters in CG-19.

`notification(id,source_owner,source_event_key,recipient_ref,channel,template_id,template_version,status,created_at)` and `delivery_attempt(id,notification_id,provider_ref,provider_message_ref,attempt_no,next_retry_at,status)` own one durable notification/outbox authority with **unique source event + recipient + channel + template version** and bounded actual permitted recipient resolution. Real CG-03 case decision can generate one truthful notification; provider-readiness config from CG-21 is checked before dispatch. Insert the outbox with the durable owner event in the same local PostgreSQL transaction where available, otherwise use a committed source event/key and idempotent owner adapter. External sends happen only after commit; due-only bounded claims/lease, finite exponential backoff, timeout classification, provider callback/status reconciliation and terminal FAILED/EXPIRED are mandatory; an HTTP success-to-provider is not proof of actual DELIVERY. Zero eligible work causes zero per-tenant/per-branch scans/network requests (rare bounded crash-recovery query if justified, measured not asserted). No permanent import worker, Redis or speculative broker.

`support_case(id,root_realm_ref,source_channel,requester_account_ref_nullable,private_contact_ref,receipt_key_digest,request_idempotency_key,contact_visibility_scope,assigned_account_ref,assigned_center_ref_nullable,status,revision,created_at,closed_at)` plus `support_reply(id,case_id,actor_ref,visibility,body_ref,created_at)` owns one Foundation public-contact/support source, with **public submitter not required to hold CG-01 identity**, and real CG-01 operator. Endpoint validates small safe name/contact/subject/message, sanitizes HTML/file links, applies IP/request/content rate limits plus size/captcha-free abuse floor, stores private contact with encrypted/protected access and redacted audit, returns **only an opaque receipt** (store its digest, not raw token), and supports status/response only after proving receipt or a legitimate CG-01 session. No CG-18 public page is needed and CG-18 may not store a duplicate contact message. Center-linked tickets require a **real CG-14 center after its later delivery**, never a dummy initial center. Private contact/attachments are scoped to requester and permitted Foundation operator; future own-center support uses CG-14 verified affiliation and CG-19 same source. Reopen/close preserve comments/assignment history and source revisions. **QA:** expiring unauthorized signed link, file scan/outage, duplicate document/notification, provider timeout, restart retry, dormant worker/egress, public abuse and future center A/B isolation only after actual center source exists.

## CRITICAL PostgreSQL, migrations, idle-worker and recovery contract

**Only current owner tables and real FKs:** CG-19 adds `stored_file`, `file_upload_intent` (or equivalent upload-state rows), `document_template`, `generated_document`, `notice`, `notification`, `delivery_attempt`, `support_case`, `support_reply`. Each private row carries mandatory real CG-01 `root_realm_ref` FK; `stored_file.owner_type` allow-list initially **CG-01/CG-03 only**, with typed source authorization (not user-supplied arbitrary IDs and no FK to absent CG-02/04/14/15). `file_upload_intent` uses UNIQUE(root_realm_ref,upload_key) and bounded expiry/status; `stored_file` has server-verified checksum, MIME, size, immutable object key/version and source revision, with `CHECK(size_bytes>0)`, status constraints, optional non-null object key only after actual upload. A case evidence version is bound to the original CG-03 case+submitted revision before a signed download is ever issued.

**Documents/communications constraints:** `document_template` UNIQUE(root_realm_ref,type,version) immutable when issued; `generated_document` UNIQUE(root_realm_ref,source_owner,source_ref,source_revision,template_id,template_version,issuance_key) with real template FK, required issue/revoke states and immutable original checksum/object ref. `notice` has root, version, type, audience, priority, schedule/expiry and DRAFT/APPROVED/SCHEDULED/ACTIVE/CANCELLED/EXPIRED; it is CG-19 original, never CG-18 CMS master. `notification` UNIQUE(root_realm_ref,source_owner,source_event_key,recipient_ref,channel,template_version) with CHECK valid state/expiry, required recipient CG-01 scoped resolution and FK to actual immutable template when used. `delivery_attempt` UNIQUE(notification_id,attempt_no), provider request/callback correlation and state; provider acknowledgment is **not** confirmed delivery. `support_case` UNIQUE(root_realm_ref,source_channel,request_idempotency_key) for safely retried visitor contact; private contact ref protected, receipt digest unique/not reversible, requester CG-01 account optional, `support_reply` FK to case, immutable actor/time/audience; actual center FK is **not** introduced until CG-14 exists. Use UPDATE with expected revision for support state and guarded assignment, one original CG-19 audit event per successful mutation.

**Read-path indexes and privacy:** root-scoped file lookup by `(root_realm_ref,owner_type,owner_ref,created_at DESC,id)` and expiry cleanup partial index; document source+issue/status lookup; notification recipient/status and due retry `(next_retry_at,id)` partial over due-eligible state; notice status/audience/published time and support root/status/updated-at/time cursor. Query index shape must match actual compiled statements, cap page/export and byte responses, reject cross-root ID guessing and deep-link read even if table row exists. PII/logs redact sender contacts, notes, private object keys, raw signed URLs and message bodies; no public file CDN bucket or unrestricted public QR.

**Atomicity / idempotency:** initiate upload writes unique intent, validate confirmed bytes/checksum/scan server-side and finish metadata status within one short DB transaction—object storage and scanner network calls **outside locks**. Issuance claims a unique source/template/version/key before generating actual PDF outside the lock; reconciles final stored object/status atomically, retains incomplete UNKNOWN_UPLOAD/UNKNOWN_ISSUE for status lookup. For notification, a committed original CG-03 event+recipient/channel dedup inserts CG-19 outbox and redacted source audit in one CG-19 transaction; provider send **outside DB lock** uses stable provider idempotency token when supported, with duplicate/ambiguous callbacks reconciled by same original attempt key. Cannot guarantee exactly-once external network send; DB/visible business state must remain consistent under at-least-once execution. Support submission/reply/update uses unique key or CAS plus private audit. No provider/client ever determines CG-03 approval or CG-01 role truth.

**Zero-work background design:** New committed file/notification/notice job issues an **after-commit local wakeup hint** to the existing NestJS app worker (or a single same-codebase worker process if operationally justified). Durable job rows remain authoritative. For one/three instances and any number of inactive users/tenants, **zero eligible work means zero per-tenant/per-account polling/query loops and zero external provider requests**; an infrequent bounded indexed recovery due-row claim can run by one effective leader/claimed lease, not one scan per tenant/instance. Due rows claimed with `FOR UPDATE SKIP LOCKED` and short lease, strict bounded batch/concurrency, finite retries, exponential backoff/jitter, expiry, terminal failure and restart lease recovery; scanner eligibility is root/resource state and time, never unconditional startup scan. Record approximate workload math (`instances × due-row-claim queries per recovery × recovery runs/hour`) and measured p95/egress **only after actual runtime evidence**. Avoid Redis/broker/import worker, idle keep-alive loops, per-user mobile polling and full-table scan; actual scheduler interval is an operational choice justified by measured latency/volume, not invented in source design.

**Migration, compatibility, proof:** One additive set of **CG-19-owned** migrations within the shared CG-01 bootstrap PostgreSQL history, with real foreign keys only to delivered CG-01/03 source structures, safe UNIQUE/CHECK/indexes, no future owner tables or speculative backfill. For existing real data in later evolution use expand/backfill/reconcile/contract, review concurrent index locks and rollback/forward repair, retention/revocation and isolated encrypted object backup+restore together with metadata (DB restore alone is not a verified file restore). QA includes two parallel upload confirmations, duplicate document issue, unauthorized signed URL, delayed object/scan failure, provider timeout/restart/duplicate webhook, ticket spam/guessed receipt/foreign actor, zero-job many-instances and source-case revision mismatch. Independent CRITICAL DB reviewer, actual migration/EXPLAIN/load/restore, rendered Web/Android and live provider tests remain NOT_RUN.

## Real source integration and module-specific QA

**Critical acceptance:** From only real CG-01/03, safely store/scan and authorize a file linked to a genuine CG-03 case and issue a **private** verified CG-01/03 approved-access letter after confirmed final source effect, not a member/staff/receipt or public private-identity QR. Separately consume one genuine CG-03 decision event and persist one deduped notification/outbox; missing CG-21 external provider remains PROVIDER_UNAVAILABLE without blocking internal notification. Public Foundation contact can create/assign/reply/close case with no CG-18/14 records. Recover due retry after restart without duplicate recipient and no idle tenant/case scanner. No future member/card/receipt/patient/center file or fake delivered state is necessary; real runtime verification, provider bytes and restore tests remain NOT_RUN/NOT_MEASURED.

**Contract availability:** CG-01/03 are actual required predecessor source owners; CG-21 owns the protected provider configuration/readiness reference and cannot create delivery effects. CG-19 alone accepts a genuine source event, resolves permitted recipients, builds/queues the message and sends it through its own on-demand provider adapter, stores provider attempt and confirmed/failed outcomes. CG-02 later registers branch draft attachments via CG-19's genuine source-authorized facade. CG-04/09/10/14/15/16/18 later introduce their real document/notification and center/public journeys with integration QA. No startup/migration dependency on CG-02/04/09/10/14/15/16/18, no placeholder member receipt, salary slip, patient record or always-on import worker.

**API acceptance:** Commands validate current action + actual record scope, owner/source ref, expected revision and idempotency key on irreversible writes; responses distinguish confirmed, pending, invalid, forbidden, conflict, provider unavailable and unknown write status. Scoped options/search may show readable authorized labels without full master read. Each named story QA case traces the real channel -> request -> authorization -> transaction -> stored status -> permitted report/published view.

## Typed API and coordination

An authenticated `/api/documents-notifications` owner facade exposes source-checked upload/validate/download/revoke, approved document issuance/verification, due-only notification status and protected Foundation support history. The *minimal public contact submission and QR validity endpoint* are separately rate-limited and return allow-listed non-sensitive fields without browsing private owner records. Every other file, recipient, case, private audit or export endpoint requires real CG-01 scope; there is no generalized public listing or unrestricted download route. Each PRD command contract:
- **FR-070** — Business completes authorized document action: Generate versioned, permissioned membership/employee IDs, letters, donation/financial receipts, appointment slips and PDFs with source-linked status, print/share and safe QR verification. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.
- **FR-071** — Business event requires communication: Provide configured email/SMS/WhatsApp/push, broadcast notice, audience/priority/expiry/template control and observable delivery/failure history without duplicating module records. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.
- **FR-072** — Visitor or center requests assistance: Track public contact/helpdesk and center support tickets/FAQs, owner, replies/status and restricted identity; share support workflow across channels. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.

Business outcome categories: `SUCCESS/SUBMITTED_PENDING/VALIDATION/DUPLICATE/FORBIDDEN/NOT_FOUND_OR_HIDDEN/CONFLICT/UNAVAILABLE/UNKNOWN_WRITE_STATUS`. External provider failure never becomes fake success. Use a DB transaction for state+audited result, optimistic revisions or narrowly scoped row locks for races and unique source idempotency. Cross-owner effects go through typed facades, not another module's repository. Approved HLD pattern (plain state guard, policy, adapter, facade) only where actual variation justifies it; reject universal DSL, speculative microservice or duplicated ledger. No unbounded idle polling or uncontrolled retries.
