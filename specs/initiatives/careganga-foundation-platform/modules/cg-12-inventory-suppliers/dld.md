**CRITICAL DB constraints & locks:** Add real composite `UNIQUE(root,id)` to each referenced table and use `FOREIGN KEY(root,ref_id)` to actual parents, including root+request to request lines/hold and event→movement, never only UUID with application-only root checks. The DB-local `stock_balance` row `CHECK` prevents negative available on any committed mutation; all receipt, hold, issue, transfer, return and adjustment writes go through **one small transactional stock-domain command**, not route-specific `UPDATE stock_balance SET qty`. Materialized balance is permitted only as an **atomic projection of immutable source events** with a unique event key and exact reconciliation. It is not a second independent ledger. Preserve original signed movement immutable; reversed receipt fails or requires appropriate linked compensating stock availability if already issued. No silent negative adjustments.

**Line-to-hold and return provenance integrity:** A `material_request_line` additionally exposes `UNIQUE(root,id,item_id)`; `stock_hold` must use **composite FK(root,request_line_id,item_id)→material_request_line(root,id,item_id)** so a valid request for Item A cannot reserve Item B through separate valid item IDs. A request's location/branch remains exactly its permitted source; stock_hold item/location must match currently approved request line + warehouse policy under the same locked command, and `stock_hold_event` has a real same-root FK to original hold and unique event key. Every RETURN and receipt reversal references one actual same-root original confirmed ISSUE/RECEIPT event and the specific item/location/source line; under a short lock of original event+item/location, cumulative already-returned quantity plus new return must not exceed original issued quantity, accounting for all partial deliveries and prior returns. Original event and movement are immutable, return appends a new event. A request's `issued_qty` is **gross confirmed issued**; net delivered and RETURNED/PARTIALLY_RETURNED reporting derive actual linked return movements, not an editable second quantity. A returned fulfillment does not automatically reissue goods or re-hold stock. These are mandatory independent CRITICAL database race/negative cases, not model commentary only.

**Stock concurrency:** Short serializable transaction or ordered row locks `(root,item,location)`: read/initialize balance under unique key, check `available>=requested_hold/direct_issue`, then write original event and movement+balance or hold+reserve atomically with source status/audit. In transfer acquire both location locks in deterministic sorted order to avoid deadlock and move quantity only if after reserved amounts origin remains >=0; destination must be real authorized/ACTIVE. Replay same event returns same effect; a lost HTTP response uses source-event-key status lookup before retry. Two requests for last unit can't both reserve or issue. Keep user input as decimal strings and exact NUMERIC arithmetic; reject negative/zero/infinite/fractional for indivisible piece units, mismatched unit/currency, overflow and unknown conversions. **Stock quantity never uses money minor units or CG-09 chart accounting.**

**Review/hold lifecycle:** A submitted material request is a frozen revision; CG-03 case reviewers apply actual decision **per approved line quantity**, never client-supplied approved flag. A final approval can approve partial qty and still be unreserved if insufficient stock; show APPROVED_UNRESERVED/backorder as truthful distinct supply status, not held/fulfilled. An actual HOLD event requires eligible approved qty plus positive available after locks; partial hold allowed if policy enables it, otherwise explicit shortage. `issued_qty+current_hold_qty<=approved_qty` at each line. Release active hold on cancellation/rejection/new revised request and adjust `reserved_qty` in same transaction. An issue of held qty decrements `on_hand_qty` and `reserved_qty` together, while moving item physically via negative stock movement. Direct authorized issue deducts only available (not reserved for someone else). Audit every action including rejected shortages.

**Issue and reversal:** A single material fulfillment can be six of ten then four later; original line has `issued_qty` tied to distinct immutable issue event keys; extra issue conflicts. Return references original issue/movement/quantity with bounded `returned<=original_issued-not_previously_returned`, audited restocking, reason/authorization and scanned CG-19 proof if required; don't refund finance automatically. Transfer creates one event/two opposite movement rows and is atomic; canceled/timeout cannot strand stock in transit without explicitly modeled/approved transition. Stock adjustment requires real CG-03 STOCK_ADJUSTMENT_REVIEW when configured, a frozen counted-vs-system snapshot/reason/digest and independently approved final decision. An authorized positive stock correction produces source-linked positive movement; negative correction cannot break available or consume another request's held units. No hidden request rewrite after approval.
