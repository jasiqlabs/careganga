## Data ownership and decision boundary

CG-02 owns exactly one legal/operational Foundation profile, its real geography tree, editable seven-step branch registration, the approved branch directory, and **Foundation-wide or branch-scoped** departments/committees. CG-21 owns provider/system configuration and may read the real CG-02 profile, not duplicate it. CG-01 owns authenticated actors; CG-03 owns approval decisions; CG-19 owns protected file bytes. A business actor, not a fabricated employee, may be linked during the initial branch draft. CG-10 employment/CG-05 projects/CG-04 memberships/CG-09 budgets introduce their own real links after they exist.

Only a completed authorized CG-03 decision may activate a branch and issue its unique code. Draft and approved data remain distinguishable, with one idempotent finalization for one registration. Store all cross-owner references as verified opaque keys; render readable business names, not identifiers.

## Canonical database and workflow contracts

- foundation_profile(id, legal_name, official_contact, postal_address, legal_registration_ref, version, updated_at): exactly one verified Foundation legal/contact master with revision + audited changes; CG-21 must not store a competing legal profile. Fields are private until CG-18 publishes expressly approved content.
- geography_area(id, level, parent_area_id, display_name, normalized_name, code, status, version): one canonical real state/district/(optional subdivision)/block/area hierarchy, not a second geography_unit alias. The DLD migration must distinguish normalized **root uniqueness** (e.g. a partial unique index on `(level, normalized_name)` where `parent_area_id IS NULL`) from normalized **child uniqueness** within the same parent (`parent_area_id, level, normalized_name`, for non-null parent). A simple `UNIQUE(parent_area_id,...)` does not protect roots in PostgreSQL. Validate allowed parent levels and self/cycle bans atomically, including concurrent reparenting; scoped, indexed selectors never invent locations.
- branch_registration(id, foundation_id, current_step, draft_version, status, requested_by, manager_account_ref, current_submission_revision, profile_payload, created_at, updated_at): one revisioned seven-stage **editable draft**, holding validated branch/name/type/opening date/geography/address/PIN/GPS/contact details, only actual CG-19 protected evidence references, eligible CG-01 manager and stage-6 selections of existing CG-02 Foundation departments. A submitted revision is frozen; editing requires RETURNED and a new draft revision, never mutation of previously submitted evidence.
- branch_registration_submission(id, registration_id, submitted_revision, immutable_payload_digest, submitted_at, approval_case_ref, status): append-only submission/review-cycle ledger, `UNIQUE(registration_id, submitted_revision)` and `UNIQUE(approval_case_ref)` where non-null. The CG-03 case must bind to **this exact source revision and digest**; resubmission creates another row/case and keeps prior history. A missing/unknown CG-03 case creation is represented as SUBMISSION_UNCONFIRMED until source-key lookup resolves it, never a fabricated PENDING_APPROVAL or a second case. `RETURNED` may be corrected; `REJECTED` is terminal for that submission; the next draft uses a new revision/policy-permitted application path.
- branch(id, registration_id, geography_area_id, branch_name, branch_type, manager_account_ref, branch_code, status, version, activated_at, closed_at): UNIQUE registration_id and UNIQUE non-null approved business branch_code. Created once after real CG-03 approval using actual manager/geography, then managed via explicit active/inactive/closed transitions; never a provisional active row on draft.
- department(id, scope_kind, branch_id, parent_department_id, kind, name, normalized_name, opening_date, description, active, head_account_ref, version): one department/committee table; scope_kind FOUNDATION or BRANCH. A row-level `CHECK` enforces `(scope_kind='FOUNDATION' AND branch_id IS NULL) OR (scope_kind='BRANCH' AND branch_id IS NOT NULL)`; the **referenced branch being active** is a cross-row condition enforced under a transaction/appropriate locks plus an FK (not an impossible row-local CHECK). Same-scope parent validation/cycle prevention also needs locked transactional checks. Distinct partial unique indexes for Foundation rows (`kind, normalized_name WHERE branch_id IS NULL`) and branch rows (`branch_id, kind, normalized_name WHERE branch_id IS NOT NULL`) prevent NULL scope duplicates. Eligible real CG-01 accounts may head departments; CG-10 employment is linked later, not fabricated.
- department_participation(department_id, account_ref, office_role, active_from, active_until, created_by): one authorized membership/officeholder association of **real eligible CG-01 accounts** to a CG-02 committee/department, with appropriate unique active assignment and history; no CG-04 member/volunteer or CG-10 employee shadow master. Validate current actor and account scope; later modules introduce their own specialized relationships.
- branch_department_link(branch_id, foundation_department_id, linked_at, linked_by): authoritative **association**, not another department master; `UNIQUE(branch_id, foundation_department_id)`, FKs to real branch and FOUNDATION-scoped department, scoped authorization and auditable unlink/history. Stage-6 draft contains candidate Foundation-department refs without creating a branch; finalization under one source transaction revalidates them and creates links only after branch activation. Branch-specific departments may be created only after the real branch is active.

Commands: GET scoped geography/options, POST/GET/PATCH Foundation profile and department/committee participation and audited branch-department relations, POST/GET/PATCH branch-registration draft with expected draft_version, POST submit branch-registration (returns PENDING_APPROVAL **only after a real, revision-bound CG-03 case is confirmed**, otherwise SUBMISSION_UNCONFIRMED), GET current submission and immutable review history, and POST finalize-approved-registration (trusted CG-03-to-owner invocation only). Every write validates actor/capability/scope, expected revision and bounded source-idempotency key; all queries/exports/options are filtered server-side. Render readable business references, not raw implementation UUIDs.

Transaction: submission freezes the draft content revision and required genuine CG-19 document refs; create/lookup exactly one CG-03 case by its immutable source submission key, marking uncertainty truthfully. The owner finalizer locks the registration/current submission and unique decision/effect claim, checks authenticated CG-03 **Super Admin final decision for that exact revision and digest**, revalidates manager/geography/documents/stage-6 department choices, generates a DB-unique business code, inserts/activates one branch and its genuine branch-department links, writes a redacted source audit and commits in one short PostgreSQL transaction. A duplicate/retry returns the original confirmed result; an old approval, replaced evidence, inactive related geography, concurrent callback/code collision, foreign selector or absent file fails without partial activation. Never hold a DB lock while calling an external provider.

## Typed API and coordination

An authenticated `/api/foundation-structure` owner facade exposes business commands, filtered read-only queries, and minimal `options/search` projections for permitted selectors. Public reads require approved publication allowlist. Each PRD command contract:
- **FR-004** — Admin configures Foundation: Maintain organization details, geography, branches, departments/committees, managers and linked staff/projects/budgets with distinct approved publication. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.
- **FR-005** — Branch manager starts branch setup: Complete seven-stage draft/review/submit registration with contacts, location, documents, manager and linked resources; after required approval issue unique branch code. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.

Business outcome categories: `SUCCESS/SUBMITTED_PENDING/VALIDATION/DUPLICATE/FORBIDDEN/NOT_FOUND_OR_HIDDEN/CONFLICT/UNAVAILABLE/UNKNOWN_WRITE_STATUS`. External provider failure never becomes fake success. Use a DB transaction for state+audited result, optimistic revisions or narrowly scoped row locks for races and unique source idempotency. Cross-owner effects go through typed facades, not another module's repository. Approved HLD pattern (plain state guard, policy, adapter, facade) only where actual variation justifies it; reject universal DSL, speculative microservice or duplicated ledger. No unbounded idle polling or uncontrolled retries.

## Concrete DB, API and lifecycle extension (same modular monolith)

**Folder/owner:** CG-02 is one new sibling at `apps/backend/src/modules/cg-02-foundation-structure/` under the **existing** NestJS composition root, with its own ordered tables in the one shared PostgreSQL migration history. Web work lives in `apps/web/src/features/foundation-structure/`; only branch-manager draft/status/evidence controls are added to `apps/android-internal/src/features/foundation-structure/`. Reuse original CareGanga `packages/design-tokens`, CG-01 policy/options, CG-03 real approval facade, and CG-19 secured file refs. No new app, ORM, login provider, audit database, approval engine, storage worker, or direct imports into other owners' repositories.

**DB validity:** Use real FK to existing CG-01 accounts for manager/head/committee participants, but no FK to future CG-10 employees, CG-05 projects, CG-04 volunteers, CG-09 budgets or CG-18 CMS. Geography root/child and department Foundation/branch partial uniqueness are explicit; scope-kind/branch-present rules are row-local CHECKs, while **active referenced branch and parent/participant scope** are transactionally validated/locked. Keep cross-row history if a branch later closes: block new assignments, do not cascade-delete departments/old participation; transitions are audited and versioned. `branch(registration_id)` and approved `branch_code` are DB-unique; `(registration_id, submitted_revision)` and decision effect keys are also unique. Bounded collision retry must never issue two codes. Actual migration, rollback/forward-fix, Postgres version and any RLS decision remain unverified until implementation; no hardcoded sample records.

**One source-owned publication boundary:** Saving an internal Foundation identity, department or branch does **not** publish it. Only CG-18 publishes an allowed approved projection when that later CMS owner exists. CG-21 may configure platform services but does not write the legal Foundation profile. CG-01 may later consume real branch/geography selectors without importing this owner's tables; the CG-02 delivery provides typed authorized scope options and the source integration/regression test.

**Scope/rollback:** Queries and allowed option selections (including committee participants, geographic ancestors and branch-department links) are constrained to actual Foundation and branch contexts; do not require healthcare center/patient resource filters. A missing/lost response after submission/finalization is `UNKNOWN_WRITE_STATUS`; client refreshes real registration/case outcome rather than retries a new branch code. Reject foreign-area parent, cross-branch department parent, stale draft, insufficient evidence, unverified manager, invalid approval signature and forged callback with distinct safe categories. Every protected mutation writes one redacted audit event with its source transaction. On DB/API/provider failure, no partial branch code/active row or fictional approved state.

**No worker amplification:** Draft step saving and reviewer status loads are request-driven; CG-02 does not spawn a per-branch status poll/cron, image processor or document queue. CG-19 owns due-only protected file/notification processing; CG-03 owns real decisions. Zero pending branch work across idle browser/mobile sessions and multiple backend instances causes **zero periodic tenant/branch DB scans and external provider requests from CG-02**. Real requests use pagination, indexed filter/sort, bounded upload refs and finite retries (in the true owner only). Measure query/egress cost under authorized QA; state `NOT_MEASURED` until then.

**Human errors and structured observability:** The single existing safe error mapper returns `SUCCESS`, `DRAFT_SAVED`, `SUBMITTED_PENDING`, `RETURNED_FOR_CORRECTION`, `VALIDATION`, `FORBIDDEN`, `CONFLICT`, `UNAVAILABLE`, `UNKNOWN_WRITE_STATUS`; native/Web message catalog translates them, never prints raw IDs, SQL, exception or file tokens. Examples: “Draft saved.”; “Add the missing agreement before submitting.”; “This draft was updated elsewhere. Refresh to continue.”; “Your branch application was submitted for review.”; “We couldn't confirm submission. Check the application status before trying again.”; “You don't have access to this branch.” A business-safe reference/status appears in confirmation. Restricted logs link Web/Android action → typed API → CG-02 policy → DB transaction → CG-03/CG-19 calls through a redacted opaque correlation reference; never log legal IDs, private addresses, contact payloads or file bytes. Monitor bounded error, query/latency, conflict, file/approval failure and idle provider-call counters; no new observability stack.

**Acceptance/rollback:** Stage-by-stage save/resume and cross-client view are backed by exactly one source draft; each submission has its own immutable revision and CG-03 case. Returned branch corrections preserve previous CG-03 history and cannot accept stale decisions; Super Admin final decision authorizes only the matching current submission. One unique branch code and stage-6 department associations are committed under the same finalizer transaction; no duplicate activation/audit/links on concurrent callback. Branch closure never silently deletes historical department/committee membership. Independent CRITICAL schema review, isolated migration/rollback and responsive Web/Internal Android/source image/motion comparisons are **NOT_RUN** until authorized tests; no CI/GitHub Actions.
