## 1. Source owner boundaries, transaction map and precise capability

CG-11 is one NestJS domain in the CG-01 modular-monolith PostgreSQL migration history, **not** an accounting module or employee HR service. First scoped payroll config uses genuine CG-01 root (and CG-02 branch if applicable) plus real CG-10 ACTIVE eligible employee; the **first effective salary** must not require CG-10 promotion, CG-09 payment, CG-19 PDF or CG-20 report. CG-10/02 provide read-only current employee/branch/attendance/effective history; CG-03 supplies version-pinned approval case, CG-09 alone owns real expense, payable and verified settlement, CG-19 file bytes/templates/notification delivery, CG-21 read-only audit presentation, CG-20 eventual MIS safe aggregate. Introducing owner CG-11 implements only typed, source-bound adapters in already-delivered CG-03/09/19 when true payroll sources exist; no CG-11 migration into their pristine first modules, no alternate DB ledger.

**Authorized audiences:** Foundation Payroll/Finance Admin explicit root+branch, source row/role action; Super Admin final high-value/protected batch with fresh current-password confirmation and distinct initiator per D-05; CG-10 employee with CG-01 account may access **self** paid/approved salary and CG-19 original payslip only; authorized reviewer using Internal Android sees exactly scoped original CG-03 case and permitted amounts and decision actions. Public/center channels NO salary API or profile access. C14 Foundation cash/bank account belongs to CG-09; distinct **employee personal payout instruction** is part of CG-11 restricted compensation relationship, not a second Foundation bank account master.

## 3. US-001 — Effective salary & configuration

**Inputs:** actual CG-01 current actor/branch and protected payroll role, CG-10 real eligible employee snapshot; optional genuine CG-10 US-003 approved HR proposed salary/transfer source **does not change payroll until separately CG-11 approved**; actual CG-03 original source-bound decision and CG-19 evidence when policy requires. First salary setup works with real employee and configured real policy, no promotion, payment or future service.

**Typed routes** (versioned under current platform API): `GET/POST/PATCH /api/v1/payroll/policies`; `GET/POST/PATCH /api/v1/payroll/components`; `GET /api/v1/payroll/employee-options?branch`; `GET/POST /api/v1/payroll/employees/:employee/compensation`; `POST /api/v1/payroll/compensation-change/submit`; `GET/POST /api/v1/payroll/employees/:employee/payout-instruction`; `GET /api/v1/payroll/employees/:employee/salary-history`. All backend checks `payroll.policy.manage`, `payroll.compensation.view/edit`, `payroll.bank.edit`, `payroll.sensitive.approve` separately; finance signatory does not automatically see all employee bank data.

**Calculation policy:** India INR / April–March payroll-policy-derived period baseline per D-13 (NO CG-09 financial_year FK for US-001/002; map and validate against actual open CG-09 year at US-003 posting), with effective dates stored as business-zone-local dates and immutable UTC audit instants. Rules are approved and versioned: no invented PF, ESI, TDS, PT, overtime or gratuity rates, legal compliance assertion, tax exemptions or automated filing. A `tax_class` flag shown in C12/C13 is only metadata until legitimate reviewed rule exists. Payroll settings C11/C12 General/Salary Components/Allowances/Deductions/Tax & Statutory/Bank & Payment/Payroll Rules/Notifications are real typed settings only for fields backed by actual approved computation/CG-09/19 behavior, not arbitrary toggles. C14 Add Bank Account creates CG-09-owned Foundation bank record, never CG-11 `cash_bank_account`. Sensitive payout destination/compensation versions have explicit approval/masked confirmation, revocation and effective-date CAS; two concurrent revisions cannot overlap. A bank instruction changed after batch approval cannot silently redirect payout; require stop/review/version-pinned new instruction.

## 4. US-002 — Deterministic run, review, freeze, late attendance adjustments

Original C04 five-stage flow **Select Payroll Period → Validate & Calculate → Review & Adjust → Submit for Approval → Approval & Payment** and C05/C06 validation: `POST /api/v1/payroll/runs/draft`, `POST /runs/:ref/import-current-attendance`, `POST /runs/:ref/calculate`, `POST /runs/:ref/adjust`, `POST /runs/:ref/submit-review`, `GET /runs/:ref`, `GET /runs/:ref/validation`, `GET /runs/:ref/history`, `POST /runs/:ref/late-adjustment`.

**CG-10 exact source proof:** `CG10.readEmployeeAndApprovedAttendanceForPeriod(root,employee,period,actor)` returns effective branch/department/assignment, eligibility/exit/suspension, approved attendance/leave days, shift/policy version and immutable digest/source high-watermark. Absence/unverified attendance is **PENDING_VALIDATION** or excluded with explicit human reason and no assumed zero days. Freeze actual CG-11 effective policy/component/employee comp/destination-independent pay snapshot *for that period* (not today's salary). Mid-period transfer creates **one** entitlement and a separate source-valid split branch allocation only if policy supports it. Employees with hold/probation/exited/inactive status follow effective approved policy and cannot silently be marked payable. Old/overlapping salary/attendance revisions deny draft approval; no backdated mutation of approved run. Run amount in minor units plus clear gross, deductions, withheld, net and eligible bank count, with deterministic documented rounding stage/currency.

**Approval:** CG-11 introduces source-frozen `PAYROLL_RUN_RELEASE` case into CG-03; genuine different proposer/reviewer, D-05 final Super Admin authority/fresh current-password confirmation, exact run revision+salary snapshot digest. CG-03 decides final review; original CG-11 guarded `applyApprovedRun` effect checks actual current run source, eligible employee and digest with one transition `DRAFT/CALCULATED -> SUBMITTED -> REVIEW -> APPROVED_FROZEN`. An already approved run may not be rebuilt from a later CG-10 attendance version. Late authorized source revision creates `payroll_adjustment` reviewed and applied in distinct later correction/arrears, never rewrites the original gross/net or historical payslip. Repeated concurrent calculate/review/approve and multi-branch duplicate period employee race return original accepted or conflict, not double pay.

## 5. US-003 — Original CG-09 accounting, partial verified payout, original CG-19 slips

**Accounting boundary:** On real approved frozen payroll, request **exactly one** CG-09 original balanced **salary expense/payable accrual** for the recognized eligible payroll obligation with `sourceOwner=CG11,sourceType=APPROVED_PAYROLL_RUN,sourceEventKey,digest`; CG-09 owns actual journal, period/account/branch validation and liability. Net employee salary payable and legitimate statutory withhold payable remain separately classified under actual approved CG-09 accounts when configured; no assumed tax remittance without real payment. Each actual employee payout issues **only one** further CG-09 payable-clearing **cash/bank settlement**, never another salary expense for the same approved gross obligation. Where CG-09 policy does not permit an accrual, block posting until reconciled finance policy exists: do not silently substitute a second cash-basis salary expense or pretend a reserve is cash. Approved Payroll Reserve is a protected CG-09 budget/earmark when implemented; an on-screen reserve summary is not editable Foundation money.

**Payout state and action:** `POST /api/v1/payroll/runs/:ref/request-release` requires current original CG-03 final approved source/revision and D-05 required Super Admin; `POST /api/v1/payroll/batches` selects current CG-09 real Foundation bank account and **version-pins** each CG-11 encrypted payout recipient instruction. `POST /api/v1/payroll/batches/:ref/release` invokes original CG-09 `submitPayrollSettlement` typed adapter after auth/case/version and creates an append-only transfer attempt. Each subsequent **partial outstanding balance retry** requires verification of all earlier attempts or definite failure, and a separately authorized remainder attempt under locked `batch_item` totaling at most the source due; `GET /api/v1/payroll/batches/:ref/outcomes` re-queries original CG-09 source per employee; `POST /api/v1/payroll/batches/:ref/reconcile` rechecks original event key. Per item `PENDING_AUTHORIZATION -> PAYMENT_REQUESTED -> PROCESSING / UNKNOWN_WRITE_STATUS -> PAID_VERIFIED | FAILED | REVERSED`, each partial success is recorded without marking other staff PAID; overall batch `PARTIALLY_PAID` if appropriate, exactly verified cash proof required. A bank file ACK is just `PROCESSING`. No external API call while holding salary/CG-09 database locks. Timed-out result requery by **same** stable original attempt source key; only a verified failed/partially settled attempt permits a new separately approved remainder attempt with a **new linked** key (never replay the unknown original), under original employee due-minus-confirmed row guard. No new bank transaction on retry until original result resolves. Rejected payout correction must keep original bank failure and staff due, not rewrite historical paid lines.

**Payslip:** `POST /api/v1/payroll/runs/:ref/payslip-issue` passes immutable frozen CG-11 pay data and current accurate **independent** `PAID_VERIFIED/PAYMENT_PENDING/PARTIALLY_PAID` status to original CG-19 protected payslip issuer; CG-19 stores bytes, immutable version/hash/signed access, private issue/send outcome. `GET /api/v1/payroll/me/payslips` and `GET /api/v1/payroll/:run/:employee/payslip` require self employee account/same-root or exact payroll grant; `GET .../history` private. Download/print/reissue/email cannot create CG-09 financial effect or change original run; failed email doesn't reverse paid salary. C08 “Generate Payslip Again” is new CG-19 document issue version from same approved source, not a new payroll run. CG-10 B48 employee exit consumes typed `readExitPayrollDues(root,employee,exitRef,actor)` showing true `PENDING_DUES/APPROVED_NOT_PAID/PAID_VERIFIED/UNAVAILABLE`; no CG-10 writable paid flag. CG-21 audit presents actual CG-11 source events filtered, no copied payroll audit store. CG-20 reads later scoped summary only; original C01 dashboard/C07 history are CG-11 working even without CG-20.

## 6. Multi-channel, failure, privacy and background NFR

**UI contract:** original C01 KPI/dashboard and subnavigation, C02/C03 restricted payroll enrollment, B43 salary setup, B44 proposal, C04/C05/C06 wizard, C07/C08 private history/payslips, C09/C10 CG-21 read-only audit projection, C11/C12/C13 components/settings, C14 CG-09 bank dialogue, B48 exit dues. Exact authentic color/icon/type/rhythm tokens reused, no new theme; original screenshots don't show Android layout or animation timing. Foundation Admin Web owns full complex calculation/setup per client D-17. Native **Internal Android** owns self-pay/payslip and authorized **reviewer approval tasks**, with functional parity to their same authorized Web counterparts (source case/steps/status and no skipped options); deliberately not a second full Admin payroll UI. Public Web/Public Android/Center Portal explicitly NO private payroll operations. Real employee own record redacted from reviewer other than needed scope and fields.

**Auth and confidentiality:** current CG-01 root+CG-02 historical/current effective branch + CG-10 employee/principal + per-action role, payout destination, source/period/purpose checks at every list/options/filter/row/file/API/batch callback/summary/export. API rejects guessed employee ID, cross-root or revoked role after queued batch (automated revalidation of current authority/approved original financial obligation). Mask bank details and protect crypto keys outside DB, no bank/PII in logs, UI errors, browser cache, exports, notifications, CG-20 or CG-21 before/after snapshots. Employee cannot see others' salary; Payroll Officer may see source amounts and cases but need explicit separate grant to edit/view full payout destination. Separate accounting source posting never automatically grants full payroll personal read.

**Already-submitted transfer and revoked actors:** revoking a payroll officer or employee role blocks any NEW disbursement or bank-info read immediately, but genuine bank confirmation for an already authorized/dispatched instruction remains reconciled using frozen original CG-03 decision and trusted CG-09 source; never discard real paid money because the prior initiator has logged out. No expired MFA challenge is reused for new transfers. System reconciliation runs under distinct restricted service authority, not impersonation of a revoked user.

**Worker/error budget:** only real due external status reconciliation from persisted `payroll_payout_attempt` indexed on `(result,next_retry_at_nullable,claimed_until_nullable)` and linked locked `payroll_batch_item`, lease/claim/finite attempts with bounded backoff, post-commit wake-up and infrequent bounded recovery after restart. Zero eligible rows across many roots/instances = **no per-root scans or provider traffic**; no permanently running cron/polling per user/tenant. Rate-limit protected exports, paged source lists, bounded joins; measure query rows, unique retries, bytes/egress and provider calls later (currently NOT_MEASURED). Unknown settlement never maps to approved/paid, returned HR proposal never changes salary, CG-19 outage never turns bank SUCCESS into false failure. Require actual migration forward/rollback/restore, DB exclusion+CAS/race, two-person approval, bank partial/timeouts/reversal, cross-scope PDF access, C11 stat configured vs unconfigured, Play target/16KB/AAB, Web/native visual and reporting consistency in independent QA. These are **PLANNED**, not performed.

**Patterns chosen:** small typed `PayrollCalculator` taking immutable rules/attendance and exact-money engine; explicit guarded State transitions + CG-01 authorization predicates; original CG-03 approval, CG-09 settlement, CG-19 document **facades/adapters**. Do not create speculative Strategy per earning type, universal statutory formula DSL, new microservice/event bus/finance/payslip store or CG-11 accounting ledger. If statutory classes materially diverge when approved, choose a small narrow validated policy implementation then, not generic tax automation now.
