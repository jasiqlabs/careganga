## Data ownership and decision boundary

CG-02 owns exactly one legal/operational Foundation profile, its real geography tree, editable seven-step branch registration, the approved branch directory, and **Foundation-wide or branch-scoped** departments/committees. CG-21 owns provider/system configuration and may read the real CG-02 profile, not duplicate it. CG-01 owns authenticated actors; CG-03 owns approval decisions; CG-19 owns protected file bytes. A business actor, not a fabricated employee, may be linked during the initial branch draft. CG-10 employment/CG-05 projects/CG-04 memberships/CG-09 budgets introduce their own real links after they exist.

Only a completed authorized CG-03 decision may activate a branch and issue its unique code. Draft and approved data remain distinguishable, with one idempotent finalization for one registration. Store all cross-owner references as verified opaque keys; render readable business names, not identifiers.

## Canonical database and workflow contracts

- foundation_profile(id, legal_name, official_contact, postal_address, legal_registration_ref, version, updated_at): exactly one verified Foundation legal/contact master with revision + audited changes; CG-21 must not store a competing legal profile. Fields are private until CG-18 publishes expressly approved content.
- geography_area(id, level, parent_area_id, display_name, normalized_name, code, status, version): one canonical real state/district/(optional subdivision)/block/area hierarchy, not a second geography_unit alias. Validate permitted parent-level transitions, self/cycle ban, and normalized-name uniqueness **including root rows where parent_area_id IS NULL** (ordinary PostgreSQL UNIQUE with NULL does not protect roots). Scoped, indexed selectors never seed fictional locations.
- branch_registration(id, foundation_id, current_step, draft_version, status, requested_by, manager_account_ref, submitted_at, approval_case_ref, profile_payload): one persisted seven-step form with validated branch/name/type/opening date/geography/address/PIN/GPS, contact and registration details, **real CG-19 protected evidence references**, and a verified eligible CG-01 manager account. DRAFT → SUBMITTED → RETURNED/REJECTED or FINAL_APPROVED. Returned drafts can be revised/resubmitted using a new revision while retaining original reviewer history; only a real finalized CG-03 case authorizes approved state.
- branch(id, registration_id, geography_area_id, branch_name, branch_type, manager_account_ref, branch_code, status, version, activated_at, closed_at): UNIQUE registration_id and UNIQUE non-null approved business branch_code. Created once after real CG-03 approval using actual manager/geography, then managed via explicit active/inactive/closed transitions; never a provisional active row on draft.
- department(id, scope_kind, branch_id, parent_department_id, kind, name, normalized_name, opening_date, description, active, head_account_ref, version): one department/committee table; scope_kind FOUNDATION or BRANCH. FOUNDATION **requires branch_id NULL** so real Foundation departments exist even with zero branches. BRANCH requires an existing active branch; the parent, if any, belongs to the exact same scope; no cross-scope or cyclic parent. Unique normalized kind/name per Foundation or per branch (explicit NULL uniqueness). An eligible real CG-01 account may head a department; CG-10 employment is linked by CG-10 later, never a fake required FK.

Commands: GET scoped geography/options, POST/GET/PATCH Foundation profile and department, POST/GET/PATCH branch-registration draft with expected draft_version, POST submit branch-registration (returns PENDING_APPROVAL), and POST finalize-approved-registration (CG-03 protected owner callback only). For creation return saved reference + authoritative state; do not expose implementation UUID in UI. Every write verifies current actor/capability/scope, expected revision and source-idempotency key; authorized queries are bounded and filtered at the database.

Transaction: finalizer locks approved registration and unique-source claim, checks CG-03 final decision, generates unique code, inserts/activates branch, writes redacted audit, commits once. Conflicting callback, duplicate normalized geography, stale draft, inaccessible documents and foreign-branch department parent return distinct controlled errors without partial changes.

## Typed API and coordination

An authenticated `/api/foundation-structure` owner facade exposes business commands, filtered read-only queries, and minimal `options/search` projections for permitted selectors. Public reads require approved publication allowlist. Each PRD command contract:
- **FR-004** — Admin configures Foundation: Maintain organization details, geography, branches, departments/committees, managers and linked staff/projects/budgets with distinct approved publication. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.
- **FR-005** — Branch manager starts branch setup: Complete seven-stage draft/review/submit registration with contacts, location, documents, manager and linked resources; after required approval issue unique branch code. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.

Business outcome categories: `SUCCESS/SUBMITTED_PENDING/VALIDATION/DUPLICATE/FORBIDDEN/NOT_FOUND_OR_HIDDEN/CONFLICT/UNAVAILABLE/UNKNOWN_WRITE_STATUS`. External provider failure never becomes fake success. Use a DB transaction for state+audited result, optimistic revisions or narrowly scoped row locks for races and unique source idempotency. Cross-owner effects go through typed facades, not another module's repository. Approved HLD pattern (plain state guard, policy, adapter, facade) only where actual variation justifies it; reject universal DSL, speculative microservice or duplicated ledger. No unbounded idle polling or uncontrolled retries.

## Concrete DB, API and lifecycle extension (same modular monolith)

**Folder/owner:** CG-02 is one new sibling at `apps/backend/src/modules/cg-02-foundation-structure/` under the **existing** NestJS composition root, with its own ordered tables in the one shared PostgreSQL migration history. Web work lives in `apps/web/src/features/foundation-structure/`; only branch-manager draft/status/evidence controls are added to `apps/android-internal/src/features/foundation-structure/`. Reuse original CareGanga `packages/design-tokens`, CG-01 policy/options, CG-03 real approval facade, and CG-19 secured file refs. No new app, ORM, login provider, audit database, approval engine, storage worker, or direct imports into other owners' repositories.

**DB validity:** Use actual FK to CG-01 account IDs only where owned records reference an existing account; no FK to future CG-10 employee, CG-05 project, CG-04 volunteer, CG-09 budget or CG-18 CMS. Geography parent cycle rejection must be transactional, and root-level names need a unique policy that handles NULL explicitly. The one department table needs a CHECK for (FOUNDATION and no branch) versus (BRANCH and active real branch), plus scoped parent-chain validation under concurrent edits. Registration ID is unique in final branch; generated branch code has a DB unique constraint with safe retry under concurrency. No hardcoded location/case/evidence sample records.

**One source-owned publication boundary:** Saving an internal Foundation identity, department or branch does **not** publish it. Only CG-18 publishes an allowed approved projection when that later CMS owner exists. CG-21 may configure platform services but does not write the legal Foundation profile. CG-01 may later consume real branch/geography selectors without importing this owner's tables; the CG-02 delivery provides typed authorized scope options and the source integration/regression test.

**Scope/rollback:** Queries and allowed option selections are constrained to actual Foundation and branch contexts; do not require healthcare center/patient resource filters. A missing/lost response after submission/finalization is `UNKNOWN_WRITE_STATUS`; client refreshes real registration/case outcome rather than retries a new branch code. Reject foreign-area parent, cross-branch department parent, stale draft, insufficient evidence, unverified manager, invalid approval signature and forged callback with distinct safe categories. Every protected mutation writes one redacted audit event with its source transaction. On DB/API/provider failure, no partial branch code/active row or fictional approved state.

**No worker amplification:** Draft step saving and reviewer status loads are request-driven; CG-02 does not spawn a per-branch status poll/cron, image processor or document queue. CG-19 owns due-only protected file/notification processing; CG-03 owns real decisions. Zero pending branch work across idle browser/mobile sessions and multiple backend instances causes **zero periodic tenant/branch DB scans and external provider requests from CG-02**. Real requests use pagination, indexed filter/sort, bounded upload refs and finite retries (in the true owner only). Measure query/egress cost under authorized QA; state `NOT_MEASURED` until then.

**Human errors and structured observability:** The single existing safe error mapper returns `SUCCESS`, `DRAFT_SAVED`, `SUBMITTED_PENDING`, `RETURNED_FOR_CORRECTION`, `VALIDATION`, `FORBIDDEN`, `CONFLICT`, `UNAVAILABLE`, `UNKNOWN_WRITE_STATUS`; native/Web message catalog translates them, never prints raw IDs, SQL, exception or file tokens. Examples: “Draft saved.”; “Add the missing agreement before submitting.”; “This draft was updated elsewhere. Refresh to continue.”; “Your branch application was submitted for review.”; “We couldn't confirm submission. Check the application status before trying again.”; “You don't have access to this branch.” A business-safe reference/status appears in confirmation. Restricted logs link Web/Android action → typed API → CG-02 policy → DB transaction → CG-03/CG-19 calls through a redacted opaque correlation reference; never log legal IDs, private addresses, contact payloads or file bytes. Monitor bounded error, query/latency, conflict, file/approval failure and idle provider-call counters; no new observability stack.

**Acceptance/rollback:** Stage-by-stage save/resume and cross-client view are backed by exactly one source draft. If a returned branch is resubmitted, preserve its prior CG-03 review history, validate new required document refs and apply only final current approval. Single-source unique branch code under concurrent finalizer replay, no duplicate audit/activation. Independent CRITICAL schema review, isolated migration/rollback and responsive Web/Internal Android/source image/motion comparisons are **NOT_RUN** until authorized tests; no CI/GitHub Actions.
