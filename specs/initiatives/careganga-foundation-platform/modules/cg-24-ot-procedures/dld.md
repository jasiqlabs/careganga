## 1. Owner/source, permission, activation and module layout

One NestJS bounded module `apps/backend/src/modules/cg-24-ot-procedures/` in CG-01 modular monolith, a single Postgres history, `packages/api-contracts` typed routes, shared authentic CareGanga UI tokens, existing Next.js Foundation Admin + Center Portal + public pages and **existing** Public/Internal native Android packages. No new OT app, worker fleet, payment processor, patient/doctor/room stock parallel data system, broker, schema-per-tenant, generic clinical rules DSL or extra workflow document. Use narrow explicit command handlers and a common resource reservation invariant, not service-per-screen.

**Original owners remain authoritative:**
- **CG-14**: real provider/legal center/location and verification/licence, professional identity and effective center affiliations, published procedure *service* and approved effective provider fee/revision, center `OT_ERP` grant, public provider contact. CG-24 `ot_procedure_detail` references that real service, stores only procedure-specific verified descriptive/clinical prerequisites, **never a second current service fee** or CG-14 professional identity.
- **CG-01**: current authenticated actor/root/center/action and verified global boolean; **CG-15**: one patient, current verified patient/procedure consent and purpose; **CG-19**: protected file bytes and original notification outbox; **CG-03**: protected approval case if actually required; **CG-17**: original accepted fee, center patient charge, qualified benefit/settlement; **CG-09**: Foundation-only accounting; **CG-20**: broad MIS; **CG-12**: Foundation inventory (not partner OT equipment). Other CG-22/23/24 operational plans are peers, not prerequisites or shared masters. Doctor/OT nurse qualifications are verified by original CG-14 professional link; CG-24 tracks only specific case assignment and readiness.

**Backend predicates, evaluated at every entry point:** `publicProcedurePermitted` requires current real CG-14 VERIFIED/PUBLISHED center/service, current safe detail approval/version and source-safe published price; it ignores OT ERP flag. `otOperationPermitted(actor,root,center,action,patientPurpose?)` requires **exact backend `CAREGANGA_ERP_OT_ENABLED===true` after strict typed parse**; actual migrated and independently release-ready module; current CG-14 ACTIVE VERIFIED clinically suitable facility and **approved, unexpired `OT_ERP` center grant**; CG-01 action with true assigned center and current professional/clinical permissions; CG-15 consent where patient data is touched; CG-19 protected proof where applicable. Missing/malformed/unverified => OFF. Recheck all list/options/minimal selectors/detail/aggregate/download/export/job/retry/write/recipient, not only UI. ON never activates another center. OFF stops all CG-24 private operational APIs (including history), jobs and exports and keeps original append-only data; original CG-15/19 lawful patient data release and original CG-21 restricted event metadata remain separate owner paths, never a CG-24 read bypass. Zero due => zero provider sends/tenant-wide scan.

## 2. One canonical physical PostgreSQL schema

Use additive migrations within actual existing CG-01 Postgres, real same-root composite FK `(root_id,center_id,id)` to CG-24 entities and verified typed CG-14/15 owner facades where original FK constraints cannot directly target a heterogeneous owner. Opaque UUID database IDs are never user-visible titles. UTC `TIMESTAMPTZ` for clinical/reservation instants, center-local IANA timezone and date only for display/clinical scheduling policy, `BIGINT` INR paise only when referencing **original CG-14 fee** (no independent CG-24 financial totals); immutable `revision BIGINT`/request digests for optimistic concurrency, audit actor and source. Use `btree_gist` in separately verified disposable migration before enabling exclusion; if unsupported, **block OT activation** until an equivalently reviewed atomic constraint is proven, never silently remove exclusivity.

## 3. Typed APIs and five independent operational slices

### US-001 — Safe procedure details and actual public CG-14 service reference; ERP OFF independent

`GET /api/v1/public/healthcare/centers/:ref/procedures` reads **current CG-14** published procedure service/fee and source-safe CG-24 approved descriptive detail; `GET/POST/PATCH /api/v1/ot/procedure-details`, `POST /procedure-details/:ref/submit-review|publish|withdraw` for current authorized Foundation/Admin and own Center Portal source proposer. **This dedicated catalogue endpoint is allowed with ERP OFF** only for source-backed public detail plus separately authorized private pricing review; no private room, team, schedule, patient or hospital workstation is exposed. If an independent reviewer is configured, US-001 introduces the exact procedure-detail-source adapter in **CG-03 original approval owner** and finalizer pins original CG-14 service+fee revision and CG-24 content digest; no direct CG-03 writes, client `approved=true`, unapproved stale source or proposal self-approval. Source safe public price derives from **CG-14 current service**, never `price_minor` in CG-24. CG-18 uses approved editorial placement only, no second procedure catalogue/fee authority. No booking availability or promised 30% discount on public Next.js/Android.

### US-002 — Physical room/equipment and qualified-professional readiness; no patient

`GET/POST/PATCH /api/v1/ot/rooms`, `GET/POST/PATCH /resources`, `GET/POST/PATCH /requirements`, `POST /resources/:ref/readiness`, `GET /resources/:ref/history`. **ERP ON and genuine CG-14 OT_ERP grant required**, current legal facility evidence, independently verified actual CG-14 professional/center affiliation and service type, reviewer separation when configured, protected CG-19 evidence adapter introduced in US-002. Distinguish actual room/facility operational availability from published CG-14 service; unverified, expired, quarantined resource may remain physically registered but is not assignable. Two centers using same actual surgeon keep one original global professional ID, not duplicate staff row; shared equipment retains one physical asset identity. US-002 can run with no CG-24 procedure catalogue/CG-15 patient/CG-17 policy (real CG-14 service+professional owner still required for qualified requirement), so room readiness independently testable. Native Internal Android should match Foundation review actions offered to same role, while Center Portal performs partner-specific workstation operations.

### US-003 — Atomic case booking and full-resource reservation

`POST /api/v1/ot/bookings`, `GET /bookings`, `GET /bookings/:ref`, `POST /bookings/:ref/reschedule|cancel`, `GET /resources/available?window&procedure` with finite allowlisted filters; no public booking route. Validate true CG-15 current consent/purpose, current CG-14 approved service/fee revision, CG-24 actual approved procedure detail, room and physical asset readiness and full qualified surgeon/anesthesia/team requirement. Determine canonical physical ROOM, PERSON, EQUIPMENT keys. In one short Postgres tx: acquire stable ordered resource locks; check real live occupancy + current active slot/assignment/readiness; insert case, required roles, all `ot_capacity_reservation` rows or **rollback all**, with GiST exclusion for cross-center surgeon and shared asset. Duplicate idempotency key/same digest returns original; changed payload conflicts, never partial confirmed booking. Reschedule validates and creates new full reservation set **before** releasing old claims in the same transaction (no loss of existing confirmed booking on conflict); cancellation releases only actual correct case claims once with append-only status reason. Timezone/IANA/DST and duration/turnaround margin actual policy are explicit and bounded; do not invent mandatory travel margins. Team/room resource changes while case waiting move case to `REVIEW_NEEDED`, not auto reschedule with stale source.

**Overrun safety:** When actual procedure starts US-004 claims `ot_resource_live_occupancy` for all assigned resources. While active it persists past planned end; US-003 availability must not advertise an currently occupied room/person/equipment as immediately bookable, and a later overlapping procedure **start** is denied until actual source release. A prior scheduled next case receives `Needs review`, not a false clinical start/automatic cancellation. Any clinical emergency requires signed authorized escalation, not a consumer backdoor. No external provider call inside booking lock. A production-usable ot scheduler requires real SQL race proof before enablement.

### US-004 — Pre-op / active / post-op and source-correct clinical notes

`POST /api/v1/ot/cases/:ref/prepare|start|post-op|complete|cancel|correct`, `GET /cases/:ref/clinical-timeline`, `POST /cases/:ref/notes`, `GET /cases/:ref/documents`. Requires actual US-003 case/reservations, CG-15 current consent and CG-14 qualified assigned team, protected CG-19 original case-document source adapter **introduced inside CG-19 file owner by US-004**, actual reviewed clinical event evidence. The actual care team, not generic Admin, can transition `SCHEDULED → PRE_OP_READY → IN_PROGRESS → POST_OP → COMPLETED` if lawful gates satisfied; cancellation, failed readiness/transfer or correction creates true REVIEW_NEEDED/CANCELLED variant rather than fabricating a completion. Only actual START obtains all live occupancy claims under lock and ensures resource not occupied despite earlier planned window; qualified completion/release removes claims only with recorded actual end/evidence, not at the wall-clock scheduled end. Completed means qualified clinical event, **not patient PAID or Foundation SETTLED**. Notes and documents protected by original CG-19 signed retrieval and per-patient/role consent even when historical; never upload private file bytes to CG-24 or publish in provider directory. Late/duplicated/out-of-order event IDs with changed digest conflict; correction/reversal links original signed event, never replaces it. Genuine patient-only released status may be served from CG-15/19 original owner under independent approved patient-purpose policy; CG-24 public endpoint never exposes raw care plan.

### US-005 — Bounded utilization and conditional completed-service CG-17 adapter

`GET /api/v1/ot/reports/rooms|resources|case-status|case-timeline` original source aggregates by real center, current period, source revision/cutoff and scope. US-002 alone gives true room readiness/availability; US-003 supplies scheduled/occupied vs empty metrics; US-004 professionally verified actual procedure completion gives real completed/post-op counts. Do not infer true room utilization from planned future slots, or include public patient list, finance ledger and clinician notes in generic Foundation dashboard. Optional `CG24_OT_COMPLETED_SERVICE` immutable signal via `ot_case_financial_signal` is emitted **only after** US-004 genuine completed/approved case and with original CG-17 accepted center/service fee, effective approved benefit policy and exact patient authorization. US-005 introduces CG-24 source adapter in original CG-17 eligible-source registry (with full source cross-QA), CG-17 owns patient charge, separate center collection, Foundation liability and authorized reversal, CG-09 owns Foundation-only journal. No automatic sample 30% discount or commission; a corrected/cancelled case after accrual sends source-linked compensating original effect, not silently deletes history. CG-19 original notification/outbox only when actual targeted due/care reminder recipient with consent/current role and indexed due row exists; missing provider shows pending/unavailable, never 'Sent'. Global OT OFF disables workers, source reports/history/private export. CG-20 optional later consumer not prerequisite for any native CG-24 report.
