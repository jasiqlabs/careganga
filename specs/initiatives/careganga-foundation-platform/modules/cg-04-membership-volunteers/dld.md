## 2. Normalized PostgreSQL owner schema (additive, versioned, root-scoped)

All proposed tables below use opaque internal UUID keys, mandatory `root_id`, `created_at`, `updated_at`, `version` where mutable, source audit and restricted access. Add `UNIQUE(root_id,id)` on every referenced same-root entity; **all intra-CG-04 FKs are composite (root_id,ref_id)** so foreign-root data cannot be linked even if a backend guard fails. CG-01 and CG-02 cross-owner account/branch/department references are validated against genuinely delivered scoped contracts; use their existing supported same-root FK when safe, or a typed verified reference with current-eligibility checks. No new Foundation identity/approval/finance/document/CG-05 tables.

| Source-owned table | Key columns and required integrity | Record writer and responsibility |
| --- | --- | --- |
| `membership_tier` | root_id, id, unique normalized name within root, current_version_ref nullable, status DRAFT/ACTIVE/INACTIVE, version; `UNIQUE(root_id,normalized_name)`, no hard delete after usage | CG-04 US-001 catalog/appearance/order |
| `membership_tier_version` | root_id, id, tier_id, version_no, fee_minor BIGINT ≥0, approved currency, duration_unit+duration_count CHECK>0, description, benefits bounded structured list, icon + approved semantic color token, display_order, effective_from, published_at nullable, immutable after activation; `UNIQUE(root_id,tier_id,version_no)` | One current public-eligible version; old pinned versions remain for fees and terms |
| `membership_application` | root_id, id, unique human application_ref, applicant_account_ref nullable, private contact/address/reference, branch_ref nullable, tier_version_id, submitted source digest, accepted_fee_minor/currency, consent_version, case_ref nullable, application_status, payment_source_ref nullable (CG-09), payment_display_status derived, version; `UNIQUE(root_id,application_ref)` | CG-04 US-002 intake, return/correction, snapshot; CG-09 solely owns actual payment/refund fact |
| `membership_application_effect` | root_id, source_application_id, pinned_review_revision, exact approval_final_ref, source_effect_key, effect_kind (ACTIVATE/RENEW/PROTECTED_CHANGE), applied_at, current_result_ref; `UNIQUE(root_id,source_effect_key)` | Exactly-once guarded CG-03 final effect, not another case/decision engine |
| `member` | root_id, id, unique member_no per root, unique original_application_id, account_ref nullable, status ACTIVE/EXPIRED/SUSPENDED/CANCELLED, active_term_ref and version; `UNIQUE(root_id,member_no)`, `UNIQUE(root_id,original_application_id)` | Created ONLY by verified eligible finalizer, no number allocated on submitted/rejected application |
| `membership_term` | root_id, id, member_id, immutable pinned tier_version_id, snapshot fee, starts_on, expires_on, source_application_ref/renewal_key, status/current_marker; CHECK expires>starts and `UNIQUE(root_id,renewal_key)`; prevent overlapping active term by guarded lock and constraint/validation | Every renewal adds one term (never mutate prior term), historical fee/benefit always reconstructable |
| `member_branch_history` | root_id, id, member_id, actual CG-02 branch_ref nullable, effective_from/to, reason, revision; one current association within business policy, no cross-root/closed new branch | Membership branch association owned CG-04, CG-02 unchanged |
| `volunteer_application` | root_id, id, unique application_ref, applicant_account_ref nullable, first/last name, restricted DOB/gender/contact/address, optional blood_group nullable, CG-02 scoped requested department/branch, skills/experience, selected availability (FULL_TIME/PART_TIME/WEEKENDS/FLEXIBLE), referral input, document evidence ref, consent_version, status, submitted_digest, CG-03 case_ref nullable, version | U15 genuine public/admin enrollment; protect all fields and record return/review |
| `volunteer` | root_id, id, unique approved original_application_id, generated volunteer business_ref, account_ref nullable, status ACTIVE/INACTIVE/SUSPENDED, current_allowed_scope_version; `UNIQUE(root_id,original_application_id)` and unique per root business ref | Approved CG-04 volunteer only, no automatic employee or CG-01 staff role |
| `volunteer_affiliation_history` | root_id, id, volunteer_id, actual CG-02 branch/department refs, effective_from/to, eligibility/consent_revision, authorized actor and reason; one current eligible appointment under current policy | CG-04 records branch/department preference/current assignment; CG-05 owns subsequent task and visit |

**Do not create:** A CG-04 membership-payment ledger, refunds table as money authority, approval decision/case table, CG-19 file store, CG-18 nav flags/CMS pages, CG-05 task/GPS store, CG-13 points ledger or second CG-01 identity. Retain personal data only under approved retention/deletion rules; preserve legally required financial and approval audit, no hard-delete referenced history.

**Indexes and scoped reads:** root-first `membership_tier(root_id,status,display_order)`, `membership_application(root_id,branch_ref,application_status,submitted_at,id)`, `member(root_id,status,member_no)`, `membership_term(root_id,member_id,expires_on)`, `volunteer_application(root_id,branch_ref,status,applied_at,id)`, `volunteer(root_id,status,id)`, `volunteer_affiliation_history(root_id,branch_ref,effective_to,volunteer_id)`. Allowlisted keyword search on normalized business labels/contact only under authorized private read; keyset/cursor pagination, bounded exports, no entire tenant table or N+1 proof/approval/claim scans. Count only actually accepted source states. Public queries never search protected applicant/KYC/volunteer lists.

## 3. Exact state guards and one-effect transactional sequences

**US-001 tier:** permission `membership.tier.manage` + real CG-01 account/root → create draft version with validated amount/term/benefits/icon/order → activate/publish approved CG-04 current version using optimistic expected version and legal no-expired/current policy → one safe public GET. Tier change/deactivation does not mutate application snapshots or member historical terms. A wrong-root/edit race returns CONFLICT; old tier is not silently repriceable.

**US-002 apply:** CG-04 receives verified applicant/session or verified-contact proof from real CG-01 policy → resolve currently eligible active tier_version and optional real CG-02 branch → validate consent/required documents via **CG-19-owned pre-case protected draft evidence adapter introduced by CG-04** → snapshot amount/terms/referral input/branch, assign one unique *application reference*, save DRAFT/SUBMITTED with idempotency key and audit. Introduce actual `MEMBER_APPLICATION` process definition and source revision/digest adapter **in existing CG-03** during US-002; CG-03 U11–U13 is the sole decision authority. If required proof missing or selected fee path unavailable, show PENDING/UNAVAILABLE; never mark paid/approved.

**Fee/approval join:** CG-04 US-002 introduces narrow membership collection/refund source reason and stable event key **inside original CG-09 payment/reconciliation authority**. CG-09 is authoritative for confirmed bank/cash/gateway capture or authorized zero-fee, partial/unknown/failed payment and exact full joining-fee refund. CG-03 may approve before CG-09 verifies; activation gate requires both matching final CG-03 source digest and current CG-09 VERIFIED fee (or true zero-fee policy). A short locked CG-04 transaction applies one member + unique number + first membership_term + owner audit, keyed by immutable final-decision+original finance source. Duplicate approval callbacks or lost-response retry must return original member number, never allocate another. No external provider call while holding member row lock.

**Rejected paid case/refund:** CG-03 REJECTED leaves membership_application REJECTED and no member number/card. If joining fee already verified, CG-04 issues exactly one authorization-requiring full refund request against original CG-09 receipt; display REFUND_PENDING while finance verifies, REFUNDED only after genuine CG-09 confirmation; failed/uncertain bank response is not success and never changes rejection. Duplicate gateway/webhooks and mismatched source amount fail closed. Never refund by merely changing CG-04 application enum or issuing a second journal.

**Term/renewal/correction:** Real active/expired member chooses an eligible current tier and renews with new exact original CG-09 payment and policy-required CG-03 decision; lock current term and append distinct membership_term with original fee/version, forbid overlap and duplicate event, preserve old PDF/expiry historical facts. If allowed to extend active term, next term begins per approved Foundation business-local policy without gap/overlap; no invented dates based on client clock. Protected name/photo/address/branch change is versioned, follows configured CG-03 review and CG-19 evidence before updating current profile/CG-19 reissued card; an old approval cannot apply a later edit. CG-04 member status EXPIRED follows actual term boundary, not a per-tenant idle scan; due-only bounded scheduling if needed with safe repeated reconciliation.

**US-003 apply:** Public/Admin U15 writes true volunteer_application; U16 options are CG-02 *real authorized department* plus CG-04 availability/skills policy, U17 full-time/part-time/weekends/flexible. Optional volunteer blood-group is a private self-provided profile input, not verified diagnosis/clinical care. CG-04 US-003 introduces `VOLUNTEER_APPLICATION` source case/finalizer and CG-19 pre-case ID evidence adapter inside those actual owners. CG-03 approval + identity-proof checks commits once one volunteer profile/business reference and effective CG-02 affiliation; no generated employee identity, automatic CG-01 login, scope/role or CG-05 work. Optional CG-19 volunteer ID issue uses original file/template owner and separate authorized public-proof fields.

**Volunteer role and work:** A privileged current CG-01 operator may separately associate a verified volunteer to a CG-01 account and assign a narrowly scoped role via actual CG-01 grants; volunteer approval alone never does so. When actual CG-05 exists, CG-04 US-003 exposes only `getEligibleVolunteerAssignees(root,branch,actor,scope)` permitted minimal active/eligible source_ref/linked_account/current_branch/revision/label, never contact/KYC/blood group. CG-05 A09 task and A04 field visit remain CG-05 writes with explicit current CG-01 permission and CG-04 source recheck on change/check-in. Revocation/branch transfer blocks future work and private A05 GPS, preserves historical legitimate task/visit and audit. CG-04 enrollment must work without CG-05.

**CG-09 volunteer reimbursement / original U42:** Eligible active volunteer with genuine linked CG-01 account/branch uses the CG-04-specific U42 Web/Public Android form with applicant, amount/date, expense category, preferred payment method, optional CG-05 project/UTR evidence, purpose/remarks and actual CG-19 validated receipt. A user-entered UTR is NOT verified paid money. The original U42 'Submit for Invoice Creation' sends at most one real CG-09 `expense_claim` request for approval, not an instant authorized invoice. CG-09 alone owns claim, CG-03 finance decision, payable/voucher/journal and actual `PAID_VERIFIED`; CG-04 owns only volunteer eligibility and person-specific UI. Unavailable owner or unknown provider response is honestly PENDING/UNAVAILABLE, never 'Invoice created' or 'Paid'.

## 5. Required database/security/NFR review and migration gates

- **Transactions:** actual composite root FKs, unique business source keys, check constraints for fee/term/consent, immutable historical version, one current affiliation, no destructive table overwrite. Root/capability/branch authorization server-side for list/filter/options/detail/import/export/write/card/QR; public searches expose only strictly published tiers and opaque self-status proof. Source CG-09 payment and CG-03 decision validated at finalizer, not just frontend.
- **Races:** same membership number/effect under duplicate CG-03 decisions, duplicate verified receipts, two applicants with same verified subject, simultaneous renewals, concurrent tier edits, branch transfer vs volunteer task, refund callbacks, expired/returned KYC and stale public CTA. Use unique DB constraints + short row locks/CAS and exact event keys; recovery status for mid-process failures.
- **Versioned migration order:** additive tier/version → application/member/term/member affiliation → volunteer application/profile/affiliation/skill → source adapters into existing CG-03/09/19 (only as each story requires). No foreign keys to CG-05/18/13. All actual migration paths, realistic privacy-safe seed-free disposable DB, restore/rollback, reenact retries, bulk import invalid/duplicate, EXPLAIN scoped lists, query/count/egress and p95 measurement **NOT_RUN**; before release independently qualified CRITICAL DB/privacy review mandatory.
- **Data integrity/recovery:** no hard-delete approved member/term/finance/case/file evidence; changes to policy and card fields reissue immutable history. Bounded due-only notification/expiry reconciliation, no cron per tenant doing idle scans; retry only eligible outstanding jobs, no unknown payment replay as success. Import creates validated draft only, bounded upload/preview, never bulk auto grants or payment.
- **Android compatibility:** native `apps/android-public` Join/Status/Claim and `apps/android-internal` authorized existing CG-05 My Tasks/Visits only, original token design, explicit camera/files/data privacy, Back/TalkBack/keyboard, modern stable compatible package pins plus API36/16KB SDK Index checks before actual build.
