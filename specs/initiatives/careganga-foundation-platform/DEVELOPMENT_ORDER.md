For example P1 begins with CG-09 and CG-14; CG-10 is the next safe P1 item. Never use a third developer's unmerged module as a dependency or claim parallel integration complete.

**Parallel compatibility ≠ source folders alone:** Parallel developers own their new `apps/backend/src/modules/cg-XX-.../`, new business migration(s), `apps/web/src/features/<owner>/` and owned Android features; each reads the existing approved API/permission/UX contracts. Shared files (`app.module.ts`, central permission catalog, route/sidebar registration, root lockfile, `packages/api-contracts` exports, shared theme, migration registry) have **one integration owner** and a short reviewed merge queue. Developers prepare a typed public owner interface but must **not independently rewrite the shared foundation** or insert placeholder future routes. Where legitimate shared-contract change is essential, agree and merge that smallest stable contract **before** consumers branch from it.

**Branching/DB/test isolation:** Cut each developer feature branch from the same already approved and integrated foundation HEAD; never merge it into another unfinished peer's branch. Use separate local database instances/Neon dev branches or equivalent isolated nonproduction schemas and separate auth/provider test configuration; never share a mutable dev database or test user namespace across independent feature QA. Name migrations uniquely with owner ID + reviewed ordering; before integrating, rebase against latest accepted baseline, resolve timestamp/ordering/unique index conflicts and check real Postgres migration order/rollback. Merge integration changes **serially** to one product integration branch with expert source review, backend authorization/DB contract check and existing CG-01/regression-story trace. Separate independently authorized runtime/manual visual QA checks apply only in QA, not as invented Development PASS; no CI/GitHub Actions.

**A parallel wave is BLOCKED if any of these are true:** (a) base foundation module not really delivered; (b) the proposed module needs an unmerged same-wave or later owner for its **main** use case; (c) two developers must simultaneously rewrite the same foundational auth/data/route schema; (d) DB migration sequencing or resource scopes are unresolved; (e) approved current-hash PRD/HLD/module/task/resolver gates are missing; (f) source QA cannot use real predecessor records. Resolve by splitting the truly optional integration into the *later introducing owner*, assigning a single integrator, or moving the prerequisite into an earlier wave. No speculative mocks or duplicate source masters.
