## CG-18 public Login/Join/Volunteer navigation publication (FR-066 / CG-18-BR09)

**Authoritative owner:** Only CG-18 stores the three explicit versioned desired visibility flags for **Login/Profile, Membership Join/Apply and Volunteer Join/Apply**, along with currently effective public publication revision; CG-21 platform_setting never stores them. CG-01 owns actual login/account authorization; CG-04 (delivered later) owns real membership/volunteer registration and its source/permissions. The audited Admin C50 screenshot provides visible styling only, not business/data ownership.

**Minimal data and transition:** One CG-18-owned `cms_public_navigation_revision(id,revision,login_enabled,member_join_enabled,volunteer_join_enabled,created_by,created_at,approval_ref,status,published_at)` with unique revision, immutable approved/published snapshot and one effective published pointer protected by expectedRevision/CAS. Draft → Preview → genuine authorized CG-03 review/approval when required → Published → Unpublished/superseded, with source audit. A stored desired flag is **not** proof its target route exists. The public projection computes `visible = published_flag && real_route_available && real_audience_allowed`; if CG-04 does not yet provide a real join route, the join action is NOT_AVAILABLE_FOR_PUBLICATION and never rendered as a working link. CG-01 login route exists as an earlier genuine predecessor. Do not invent CG-04 entities, registration forms or a CG-21 settings mirror.

**Cross-channel API:** CG-18 private Admin Web editor provides guarded settings preview, permissioned publication transition and real source status. The same minimal allow-listed public-navigation projection and effective revision drive public Next.js Web **and Public Android native navigation**; never leak unpublished labels/admin configuration, tokens or irrelevant private data. Publisher disable/unpublish invalidates the public cache/version for both clients; deep links still recheck their actual CG-01/04 owner authorization. Publish-result uncertainty and concurrent edits resolve via original revision/key and current effective status, not duplicate public toggles.

**QA / NFR:** Validate independent Login toggle with real CG-01 authentication and no CG-21/04 business records, hidden/unpublished/private navigation in Web/Public Android, no CTA to missing member/volunteer route, permission denial, stale/old cached revision, optimistic conflicts, source-safe 404/forbidden route guard, proper Admin C50-like styling and native accessibility. No CG-18 native Admin editor; Public Android is a required consuming surface, and actual device/visual/runtime QA remain NOT_RUN.

## CG-18 presentation-only contact, notices and media (CG-19 source)

- **Public contact** belongs to **CG-19 support_case**: CG-18 US-003 publishes its own verified Contact page and embeds/links CG-19's already working validated public form/receipt endpoint; submission, private contact, assignment, replies and response history are stored and authorized **only by CG-19**. No CMS `contact_message` table/CRM inbox, no rewritten receipt/security logic. Frontend unavailable state is truthful if real CG-19 endpoint cannot be reached.
- **Notices:** Original notice content, audience, send schedule, outbox and provider delivery are **CG-19**. CG-18 owns only optional separate approved *public website publication* of an authorized allow-listed CG-19 notice projection with independent publication state/revision; a CG-19 notice sent to internal roles is not automatically public. CMS must never edit original CG-19 notification recipients or delivery status.
- **Media:** Secure file bytes, validation/scan and private status are **CG-19 file** source. CG-18 owns its gallery/page placement, visible metadata and public publish decision, only after a real CG-19 VALIDATED object is intentionally eligible. No duplicate file bytes, fake upload, accidental private signed URL leak or future business master. QA in CG-18 US-003 verifies contact/notice/media presentation only; original CG-19 privacy/DB/provider tests remain CG-19's own.

## Typed API and coordination

An authenticated `/api/cms-public-content` owner facade exposes business commands, filtered read-only queries, and minimal `options/search` projections for permitted selectors. Public reads require approved publication allowlist. Each PRD command contract:
- **FR-066** — Admin edits Foundation site: Manage homepage, About/Our Work, projects, team, hero images/typography, CTAs, website navigation and public Login/Join visibility with authorized preview/publish controls. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.
- **FR-067** — Admin edits NGO impact/transparency: Publish editable Impact groups, geography/charts/stories with appropriate provenance; maintain 80G/PAN/registration, annual and financial disclosure pages/documents. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.
- **FR-068** — Admin publishes reusable content: Manage galleries, videos, publications, media, articles, updates, events, notices and public enquiries with controlled fields, review, ordering, preview and status. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.
- **FR-069** — Healthcare content is published: Show approved directory/category cards, provider profiles, doctors, current price/facility/benefit messaging; don't allow CMS to overwrite provider verification, scheduling or contribution ownership. Validate current actor/real scope, source record/status, revision/idempotency key, and accept only a legitimate source-owner transition.

Business outcome categories: `SUCCESS/SUBMITTED_PENDING/VALIDATION/DUPLICATE/FORBIDDEN/NOT_FOUND_OR_HIDDEN/CONFLICT/UNAVAILABLE/UNKNOWN_WRITE_STATUS`. External provider failure never becomes fake success. Use a DB transaction for state+audited result, optimistic revisions or narrowly scoped row locks for races and unique source idempotency. Cross-owner effects go through typed facades, not another module's repository. Approved HLD pattern (plain state guard, policy, adapter, facade) only where actual variation justifies it; reject universal DSL, speculative microservice or duplicated ledger. No unbounded idle polling or uncontrolled retries.
