## 2. US-001: profile, review, links and source-safe search

**Lifecycle axes (not one conflated enum):** `verification DRAFT -> SUBMITTED -> UNDER_REVIEW -> VERIFIED / RETURNED / REJECTED`, with corrected resubmission as new source revision/case; independent `lifecycle ACTIVE / INACTIVE`. A rejected request is not automatically a deleted beneficiary. Initial draft profile with no CG-05 project and even no available CG-19 evidence may be saved if policy allows; claims of verified require actual approved evidence and CG-03 decision when configured. Authorized actor can view only own purpose/branch, status, current projects, limited protected history.

**Typed source contracts:**
- `POST /api/v1/beneficiaries`, `GET /api/v1/beneficiaries?state&district&block&project&status&cursor`, `GET/PATCH /api/v1/beneficiaries/:ref`, `GET /api/v1/beneficiaries/options`; scoped DTOs validate actual allowed gender/age filtering only when data and lawful purpose exist.
- `POST /api/v1/beneficiaries/:ref/submit-verification` and original CG-03 case/decision adapter only when required; `GET .../:ref/verification-history`, `PATCH .../:ref/lifecycle` as separate permissioned operations.
- `POST/DELETE /api/v1/beneficiaries/:ref/project-links` checks `CG05.readEligibleProject(root,branch,projectRef,actor)`, same-root, current approval/eligibility, actor project-link permission. No dummy future CG-05 visit required. Multiple real project linkages and independent privacy-preserving unlink history; project deactivation prevents new aid linkage but preserves past support.

User-visible duplicate candidates require current profile-read scope and masked similarity; a shared number or two genuinely distinct beneficiaries may coexist. Optimistic `profile_revision` and idempotency prevent silent overwrites/double intake; safe `CONFLICT` prompts refresh, `NOT_FOUND_OR_HIDDEN` hides guessed identity. No direct public lookup by mobile/virtual ID.

## 3. US-002: approved assistance, actual stock/payment effects, partials and corrections

**Single aid case:** `DRAFT -> REQUESTED -> REVIEW_PENDING -> APPROVED -> PENDING_FULFILLMENT -> PARTIALLY_DELIVERED -> DELIVERED`, with `RETURNED_FOR_CORRECTION / CANCELLED / UNAVAILABLE` and later linked `CORRECTED / REVERSED` events. Appending a source event and updating guarded case revision is atomic. Actual approval uses current CG-01 role and **CG-03 original review process** for policy-required high-risk/disbursement decisions; neither an `APPROVED` label nor super-admin UI button bypasses its original signed outcome. Once approved, freeze quantity, amount, policy and recipient snapshot; editing creates a new approved revision and cannot backdate historical proof.

**Material path (real CG-12 only):** validate current beneficiary/actor+branch+project, original CG-12 store/item/available/reserved and officer permission, then invoke `CG12.issueApprovedMaterial(root,store,item,quantity,sourceKind=CG06_AID,sourceKey,actor)` under one short same-PostgreSQL transaction **if supported** or preserve a durable `PENDING_STOCK` source command with idempotent bounded due-row reconciliation. Only `CG12.CONFIRMED_ISSUE` for this **actual aid source plus authorized evidence of real recipient handover** makes a CG-06 `DELIVERED` event. A store-to-field-worker transfer is `ISSUED_AWAITING_HANDOVER` and not counted as beneficiary aid delivered; an undelivered stock return uses original CG-12 return and preserves both histories. Unknown response re-queries the SAME source key; never retries under new key or assumes issued. Two simultaneous last-item deliveries cannot create negative stock. A second partial 6+4 must use distinct unique approved partial-event keys, with total <= approved and current item/unit/recipient. Return uses original `CG12.returnIssue` only against genuinely issued balance; one linked correction event, never delete past help.

**Money path (CG-09 only):** actual authorized `CG09.submitAidExpensePayment(root,beneficiaryAidRef,amount,currency,sourceKey,approvalEvidence)` then inspect original `CG09.readVerifiedAidDisbursement` (real posted balanced journal **and verified beneficiary/payment handover as applicable**), not a draft voucher/payment initiation or screenshot amount. One original CG-09 posted/disbursed source drives one CG-06 financial-delivery event and original CG-09 reverse/refund source drives correction; never create cash/bank or reserve balance in CG-06. If payment provider unavailable or unknown after commit, remain `PENDING_FINANCE`, re-query exact original source key before claiming paid; do not automatically send another payout. Stock items must never emit a CG-09 payment by default.

**Optional contextual source:** CG-05 project's current approved link; task/visit/activity when genuine original CG-05 delivered, valid same-root/branch/project/consented staff. `GET /api/v1/beneficiaries/visit-summary?visitRef` returns **only** permitted aggregate count and minimal scope-safe link/availability to CG-05 A05; full case needs a second explicit CG-06 permission. A07 campaign filter may use real approved CG-07 campaign attribution **only if an actual linked aid source exists**; no required campaign record/dummy selector or parallel campaign entity. CG-19 protected delivery proof links original file with separate download guard. CG-12 B19 never gets a public beneficiary roster.

**Routes:** `POST /api/v1/assistance` request, `POST /api/v1/assistance/:ref/submit` approval, `POST /api/v1/assistance/:ref/deliver-material`, `POST .../deliver-financial`, `POST .../return`, `GET .../:ref/history`; all accept typed original immutable `sourceKey`, current expected revision, allowed actor/root/branch and return true owner outcome + safe `PENDING/CONFLICT/UNKNOWN_WRITE_STATUS`. No generic `force-delivered` route or client-supplied "paid" boolean.
